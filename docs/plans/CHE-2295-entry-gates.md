## Problem Statement

Status rules such as "an issue enters `in_review` only with a non-draft PR whose CI is green" live in skill prose and a client-side script (`run-in-review-gate`, CHE-2336). The server does not enforce them. Agents and people can still write `in_review` directly, and every new rule adds more prose. `AGENTS.md` "Settings-first features" asks for the opposite: catalog-based status entry conditions attached to workflow columns, with modes `off | warn | block`.

## Decisions recorded (Cheese, 30/10/2026 ICT, decision records on CHE-2295)

- Settings-first direction (message `01a188f5-0765-73dd-9740-0497c948c031`): add new settings, not prose rules.
- Gate primitive first (message `01a188f8-27f3-7d3f-83dd-6affd501dbff`): before presets (CHE-2295 step 3) and before run-budget UI (waits on CHE-2297).
- Approach B (message `01a18902-3c2f-7a9a-b630-0e12f2f64bfe`): entry conditions on each workflow step, reusing the existing guard catalog.

Ruled out:
- A, hard-coded `in_review` check in the status handler: a one-off check, the pattern `AGENTS.md` forbids.
- C, workspace-level gates keyed by status: duplicates the workflow step concept; projects on different workflows could not differ.

- Facts: `issueworkflow.Facts` (`edges.go:187`). Child PRs count only when the workflow sets `IncludeChildPRs` (`issueworkflow.go:194`).
- Step model: `issueworkflow.Step` (`issueworkflow.go:169`); persisted through `storedStep` + `DecodeSteps`/`EncodeSteps` (`issueworkflow.go:210-286`), which copy fields one by one.
- Write path: every API status write, single or batch, reaches `workflowWrite.verify` (`server/internal/handler/issue_workflow_write.go:130`), either through `lockIssueAndVerify` (`:171`) or directly from `updateIssueAtomically` (`issue.go:3863`). Workflow edge, CI-green and run-budget moves also pass here via `moveIssueOnEdge` (`issue_workflow_ci_advance.go:106`) with a zero-value caller.

## Design

```mermaid
flowchart LR
  M["Request status write: member, agent, CLI, API, create, batch"] --> C{"Status changes into a step with entry gates?"}
  S["System move: edge, CI-green, run budget, sweeper, task reset, remap"] -- "system=true, gate skipped" --> OK
  C -- no --> OK["Write status"]
  C -- yes --> F["Load Facts inside the write transaction"]
  F --> G{"Every enabled gate holds?"}
  G -- yes --> OK
  G -- "no, mode=warn" --> W["Write status + one warn activity per issue, step, head"]
  G -- "no, mode=block" --> O{"Human credential, every failed block gate allows override, reason given?"}
  O -- yes --> OK2["Write status + override activity with reason"]
  O -- no --> B["409 entry_gate_failed: failed guards + fix"]
```

### Data shape (inside existing step JSON)

```json
{
  "status_key": "in_review",
  "entry": [
    { "guard": "pr.ready",        "mode": "block", "member_override": true },
    { "guard": "pr.checks_green", "mode": "block", "member_override": true }
  ]
}
```

- `guard`: any guard from the catalog except `agent_done` and `agent_verdict(...)`, which describe an agent's own write, not a state. Rejected at validation.
- `mode`: `off | warn | block`. No `entry` means no gate (today's behavior).
- `member_override`: default `true`. A human passes a `block` gate only with a reason. Agents and machine credentials never override (see "Override authorization"). The "Cheese strict" preset (CHE-2295 step 3) sets `false`.
- At most 8 entry gates per step (same as `MaxEdgesPerStep`).

No database migration: `entry` lives in the existing steps JSON. It still needs code in each place that copies step fields (see slice 1).

### PR semantics for entry gates

Exit guards use "any PR" (`anyPR`), and `pr.checks_green` counts drafts (`open()` includes `draft`, `edges.go:234`). Evaluated one guard at a time, a non-draft red PR plus a draft green PR would pass both `pr.ready` and `pr.checks_green`. Entry gates therefore split the catalog into three families. Scope follows the workflow's `IncludeChildPRs` for every family. Exit-guard behavior does not change.

| Family | Guards | Entry evaluation |
| --- | --- | --- |
| Open-PR state | `pr.ready`, `pr.checks_green`, `pr.checks_red`, `pr.review_approved`, `pr.review_changes_requested` | **Per PR**: every linked open or draft PR in scope must satisfy all of the step's open-PR gates together, and at least one such PR must exist. |
| Terminal PR state | `pr.merged`, `pr.closed_unmerged` | Each gate holds or fails as the exit catalog already defines it (`Facts.holds`, `edges.go:216-218`): `pr.merged` = at least one merged PR and no open or draft PR; `pr.closed_unmerged` = at least one closed PR and no open, draft or merged PR. No open-PR requirement. |
| Non-PR | `children_done`, `issue_status(id, status)` | `Facts.holds`, unchanged. |

Every guard in the catalog except `agent_done` and `agent_verdict(...)` stays allowed. A step may mix families. Each gate is evaluated in its own family, then its own `mode` applies: a failed `warn` gate writes the status with a warning, a failed `block` gate refuses it unless the override rule admits it. Validation does not reject any mix. Some mixes cannot all hold at once (a terminal guard requires zero open PRs; the open-PR family requires at least one); with both in `block`, entry needs a human override.

Expected results (gates enabled on the target step):

| Linked PRs in scope | Gates | Result |
| --- | --- | --- |
| One merged PR | `pr.merged` | pass |
| One merged PR | `pr.ready` | fail: no open or draft PR |
| One closed-unmerged PR | `pr.closed_unmerged` | pass |
| One closed-unmerged PR | `pr.merged` | fail |
| No PRs | any PR gate, either family | fail |
| Open red PR + draft green PR | `pr.ready` + `pr.checks_green` | fail: red PR fails `pr.checks_green`, draft PR fails `pr.ready` |
| Open red PR + draft green PR | `pr.checks_green` | fail: the open red PR fails |
| Open green PR, children done | `pr.ready` + `pr.checks_green` + `children_done` | pass (per-PR family + non-PR family) |
| One merged PR, children not done | `pr.merged` + `children_done` | fail: `children_done` |
| One merged PR | `pr.merged=block` + `pr.ready=warn` | enters with a warning: `pr.merged` holds, `pr.ready` fails in `warn` |
| One merged PR | `pr.merged=block` + `pr.ready=block` | 409: `pr.ready` fails; a human override with a reason admits it when `member_override` is true |

Self-hosted VCS PRs carry no checks (`workflow_edges.sql:26`), so `pr.checks_green` can never hold for them. The step editor shows a warning next to a `pr.checks_green` gate; the server does not try to detect self-hosted projects (no speculative validation).

### Enforcement

- One evaluation point: `workflowWrite.verify`. It runs the gate only when the write changes the status **into** a gated step. Title, description and other edits on an issue already in that step are never gated.
- `workflowWrite` gets an explicit `system bool`. `moveIssueOnEdge` (edge, CI-green, run-budget moves) sets it, so those moves skip entry gates. Other system writers that do not use `workflowWrite` are unchanged and listed in a regression test: failed-task reset (`service/task.go:7142`), runtime sweeper (`runtime_sweeper.go:725`), PR auto-complete (`pr_auto_complete.go`), GitHub merge handling (`github.go`), Qoder lifecycle, Jev routing.
- The workflow-edit remap (`issue_workflow.go:710`) moves issues because a member edited the workflow; it is a system move (`system=true`), not a gated write.
- Create runs the same gate: an issue cannot be created straight into a gated step. `IssueService.Create` (`service/issue.go:256`) does not call `workflowWrite.verify` today, so slice 1 adds an in-transaction hook there. The hook checks the **effective** initial status: the requested `status`, or the default the service picks when the caller omits it. A pre-transaction check alone is not enough.
- Batch updates report per-item failures instead of the current silent `continue` (`issue.go:5067`, `5111`). Wire shape is additive: `updated` and `updated_ids` stay exactly as today (`issue.go:5219`, `packages/core/types/api.ts:139`); a new optional `failed: [{ id, code: "entry_gate_failed", failed_guards: [...] }]` lists refused items. A refused item stays unchanged; items already written stay written and stay listed in `updated_ids`.
- Facts are loaded with the transaction's queries (`qtx`), not `h.Queries`, so the decision and the write see the same snapshot.
- Override: `PUT /api/issues/{id}` gains optional `entry_gate_override_reason` (string, 1–500 chars). It applies only when all of the following hold; otherwise the 409 stands:
  - every failed `block` gate on the target step has `member_override: true`;
  - a reason is given;
  - the caller is a human (see "Override authorization").

#### Override authorization

`resolveActor` answers "who authored this write", not "is this a human". It returns `member` for any request without trusted agent headers (`handler.go:942`), including a cloud-node machine credential (`X-Actor-Source: cloud_pat`, `middleware/auth.go:251`), which may write issues. So the override check uses the authorization signal, not authorship: the caller is human only when `resolveActor` returns `member` **and** `isMachineCredentialActor(r)` (`actor_guards.go:42`) is false. `X-Actor-Source` is server-set; the auth middleware strips any client-supplied value. Normal (non-override) issue writes keep today's authorization: machine credentials can still write issues; they only cannot override a failed `block` gate. This is the approved rule "agents never override", applied to every machine credential.

Regression tests (slice 1):

| Credential | Override with reason on a failed `block` gate |
| --- | --- |
| Agent task token (`task_token`) | refused, 409 |
| Cloud-node credential (`cloud_pat`), no agent headers | refused, 409 |
| Human JWT or PAT (`interactive_jwt`, `cli_jwt`, `pat`) | allowed, override activity carries the reason |
| Machine credential (`task_token` or `cloud_pat`) with a client-forged `X-Actor-Source: interactive_jwt` header | middleware strips the forged value and stamps the real source; refused, 409 |
| Human, gate has `member_override: false` | refused, 409 |
| Human, no reason | refused, 409 |
- `warn`: the write succeeds. One activity row per (issue, step, PR head SHA); dedup by reading existing activity rows of type `entry_gate_warning` for that key (no new table). One issue comment on the first warning only.
- `block`: HTTP 409, code `entry_gate_failed`. Body lists each failed guard, the fact behind it (for example "PR #533 is draft", "checks FAILURE on head 1574ce1") and the action that fixes it. The CLI prints the same text and exits non-zero.

### Preservation and security

- `entry` is part of the bound-write hash: add it to `stepToPayload` so `workflowWriteField` (`issue_workflow_bound_write.go:57-90`) classifies a gate change as a steps change, not `workflow.instructions`. Otherwise an agent holding an instructions-only decision could remove gates.
- A step write that omits `entry` keeps the stored `entry` (merge-preserve, like `SetIssueWorkflowHandoff` keeps `Edges` at `issue_workflow.go:1294`). An explicit `"entry": []` clears it. This protects gates from the current web editor, which rebuilds steps field by field (`workflow-editor-page.tsx:404-413`), and from older desktop clients.

### UI and CLI

- Settings → Workflows step editor: "Entry gates" section per step, one row per gate: guard picker, mode control (`Off / Warn / Block`), member-override toggle.
- `multica workflow get` shows `entry`; `multica workflow update` accepts it with no new command; `multica issue status` accepts `--override-reason`.
- Issue status menu: a gated target shows a lock or warning badge with the failed guard text before the write.

## Success Criteria

- An agent writing `in_review` on an issue whose linked PR is draft or red receives 409 `entry_gate_failed` with the failed guard text; read back shows the status unchanged.
- A human override writes the status and the activity row carries the reason; the same override from an agent task token or a cloud-node credential gets 409.
- `pr.merged` and `pr.closed_unmerged` entry gates pass on a sole merged or sole closed-unmerged PR respectively.
- A mixed batch returns `updated`, `updated_ids` and `failed`; refused items are unchanged.
- `warn` mode writes the status, one activity row per (issue, step, head) and one comment on the first warning.
- Editing the title of an `in_review` issue with red CI still succeeds.
- A workflow save from an older client that omits `entry` leaves stored gates unchanged.
- System moves listed above behave exactly as before (regression test).
- After slice 3, the `in_review` section of `multica-cheese-work-issue` shrinks to "the server enforces the Default workflow's entry gates".
