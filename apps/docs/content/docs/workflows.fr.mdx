Un workflow fixe les étapes que suivent les tâches d’un projet, qui s’occupe de chacune et ce qu’il faut y faire.

Par exemple, un workflow de livraison peut suivre ce parcours :

| Étape | Responsable | Travail à effectuer |
|---|---|---|
| Développement | Un agent de développement | Réaliser les modifications et les préparer pour la revue. |
| Revue | Un agent de revue | Vérifier le résultat, puis le transmettre à la QA ou le renvoyer pour correction. |
| QA | Un membre de l’équipe | Essayer le résultat et décider s’il est prêt à être terminé. |

Passer une tâche en revue la confie à l’agent de revue. La description, les échanges et les résultats précédents restent dans la même tâche pour que le prochain responsable puisse prendre la suite.

Le modèle **Livraison** suit exactement cette structure. Les projets sans workflow choisi utilisent **Default** : tous les statuts sont disponibles et rien n’est confié automatiquement, comme auparavant.

## Créer un workflow

Un `owner` ou un `admin` de l’espace de travail peut créer des workflows dans l’application web ou de bureau :

<Steps>
<Step>

Ouvrez **Paramètres → Workflows**, puis **Nouveau workflow**. Partez de zéro ou utilisez le modèle **Livraison**, **Contenu** ou **Communauté**.

</Step>
<Step>

Nommez le workflow et choisissez ses colonnes de statut. Faites glisser les colonnes du milieu dans l’ordre souhaité.

</Step>
<Step>

Sélectionnez une colonne et choisissez ce qui se passe quand une tâche y entre : **Pas de relais**, **Confier à un agent** ou **Confier à un membre**. La liste des membres propose aussi **Responsable du projet**.

</Step>
<Step>

Pour une étape confiée à un agent, écrivez ce qu’il doit faire, puis choisissez **Une fois terminé, passer à** (si vous ne choisissez rien, la colonne suivante, en sautant les colonnes de clôture comme Won't Fix ; une colonne Terminé ou Fermée ne mène nulle part par défaut) et **En cas de rejet, renvoyer à** (quand cette étape juge le travail reçu insuffisant et qu’il doit être repris). Si l’étape ne peut pas continuer pour une raison extérieure, utilisez **Blocked** plutôt que le renvoi ; l’étape renvoie la tâche à la place seulement si le workflow n’a pas de colonne Blocked, ou si elle est elle-même une colonne Terminé ou Fermée.

</Step>
<Step>

Prévisualisez les consignes que l’agent recevra, puis enregistrez.

</Step>
</Steps>

Si vous avez ajouté un nouveau statut, enregistrez d’abord le workflow avant de configurer son passage de relais.

Sans passage de relais, le responsable ne change pas. Confier la tâche à un membre change le responsable sans lancer d’agent. La confier à un agent lui demande de commencer cette étape. Vous devez avoir le droit de l’appeler et son ordinateur doit être en ligne pour l’exécuter.

Une étape avec `keep_other_assignee: true` saute le passage de relais lorsque le responsable actuel a été choisi volontairement : il n’est ni le responsable de cette étape ni celui de l’étape que la tâche quitte. Il garde la tâche, et un agent responsable lance une exécution pour cette étape. L’option est désactivée par défaut et se définit via l’API ou la CLI. Elle est temporaire : les workflows par tâche (CHE-5024) la remplaceront.

Une étape avec `chain_same_owner: true` ne lance aucune nouvelle exécution lorsqu’un agent y déplace la tâche et que ce même agent est le responsable de l’étape, à condition que l’étape dans laquelle son exécution a démarré ait le même type de responsable (agent, responsable du projet, etc.). L’agent poursuit dans son exécution, et la réponse de changement de statut contient les instructions de l’étape dans `step_brief` ; `multica issue status` l’affiche. Un autre agent, un type de responsable différent ou une personne qui déplace la tâche lancent une exécution comme avant. Une mise à jour par lot n’enchaîne jamais. L’option est désactivée par défaut et se définit via l’API ou la CLI.

Une étape peut porter son propre `auto_close: {"mode": "off|warn|block", "top_level": true|false}`. Le paramètre d'espace de travail `auto_close` sur `off` est l'interrupteur général et l'emporte toujours. Sinon, le mode de l'étape remplace celui de l'espace de travail pour les tâches qui entrent dans cette étape, et une étape sans `auto_close` suit l'espace de travail. Avec `top_level: true`, une tâche racine peut aussi être fermée : la vérification du parent est ignorée, et une tâche enfant attend toujours un parent non arrêté. Sur une étape en mode `block`, une arête `pr.merged` vers `done` dont la fusion est arrivée mais dont les vérifications de fermeture échouent ne déplace pas la tâche vers `done`. Elle prend aussitôt, une seule fois, le statut `on_timeout` de l'arête, sans attendre l'échéance. Le champ est désactivé par défaut ; définissez-le par l'API ou la CLI.

## L’utiliser dans un projet

Ouvrez un projet et choisissez son **Workflow**. Les `owner`, les `admin` et le responsable du projet, s’il s’agit d’un membre, peuvent modifier ce choix.

La confirmation indique quelles tâches gardent leur statut. Si certaines utilisent un statut absent du nouveau workflow, choisissez où les placer. Changer de workflow ne transmet pas les tâches à un autre responsable et ne lance pas d’agent.

Le tableau du projet suit désormais les colonnes du workflow. Chaque tâche propose uniquement les étapes de ce workflow dans son choix de statut et indique qui prend le relais. Les projets sans autre workflow utilisent **Default** ; vous pouvez y revenir plus tard.

## Choisir un workflow selon le type du titre

Un propriétaire ou administrateur peut définir `workflow_by_type` dans les paramètres de l’espace de travail, par exemple `{"design": "<id du workflow>", "plan": "<id du workflow>"}`. Une nouvelle tâche dont le titre commence par un type associé, comme `design(x): …`, suit ce workflow au lieu de celui de son projet. `--workflow` (CLI) ou un choix explicite l’emporte toujours. Un type sans entrée, ou dont le workflow n’existe plus, garde le workflow du projet. `multica issue create` affiche le workflow choisi. La fenêtre de création affiche les statuts et le passage de relais du workflow choisi dès que le titre a un type associé. L’association est une règle de l’espace de travail : elle s’applique à tous les créateurs, agents compris, sans la vérification du budget d’exécutions qu’un `--workflow` explicite subit pour les appelants non interactifs. Si deux clés ne diffèrent que par la casse, la première par ordre alphabétique l’emporte. Modifier le titre plus tard ne change pas le workflow ; la réponse de mise à jour contient un `workflow_hint` d’une ligne (affiché par `multica issue update`) avec la commande qui le déplace.

Un propriétaire ou administrateur peut définir `quick_first` dans les paramètres de l’espace de travail pour essayer le workflow Quick sur une partie des nouvelles tâches : `{"workflow_id": "<id du workflow Quick>", "types": ["feat", "fix"], "starts_at": "<RFC 3339>", "ends_at": "<RFC 3339>"}`. De `starts_at` (inclus) à `ends_at` (exclu), une nouvelle tâche racine dont le type de titre figure dans `types` et qui suit déjà un workflow complet (celui de son projet ou un workflow nommé par `workflow_by_type`) est tirée selon son numéro : un numéro pair démarre dans le workflow Quick sur `todo`, un numéro impair garde son workflow. Une sous-tâche suit le workflow Quick de son parent. Une tâche est exclue si l’appelant a choisi le workflow avec `--workflow`, si son statut n’est pas `todo` ou `backlog`, si elle est assignée à un membre ou à une équipe, ou si son projet a un test A/B dans sa fenêtre. Un agent nommé comme assigné est conservé comme auteur de la tâche. Le paramètre est désactivé tant qu’il n’est pas défini ; sans lui, la création ne change pas.

Chaque rattachement au workflow Quick écrit une ligne `quick_entry` dans l'activité de l'issue : le tirage en écrit une pour les deux bras (`source` `arm`, `arm` `Q` ou `D`), et un remplacement au niveau de l'issue vers Quick en écrit une avec `source` `override`. Quick est le workflow nommé `Quick`, ou celui que nomme `quick_first`. `full_workflow_id` est fixé par le serveur : c'est le workflow que l'issue suivait juste avant. Pour le tirage, c'est la route que garde un numéro impair ; pour un remplacement, c'est le remplacement précédent de l'issue, sinon l'entrée `workflow_by_type` de son type de titre, sinon le workflow de son projet. Il est omis quand l'issue n'en avait aucun. Un appelant ne peut pas le nommer.

`multica issue workflow escalate <id> --reason "..."` fait passer un ticket qui suit Quick au workflow complet nommé par sa ligne `quick_entry` la plus récente ; l'appelant ne peut pas nommer la cible, et les champs inconnus de la requête sont refusés. Un ticket sans ligne `quick_entry`, ou dont la ligne ne nomme aucun workflow, est refusé avec `no_full_workflow` ; un ticket qui ne suit pas Quick est refusé avec `not_quick`. Depuis `todo` ou `investigating`, le ticket exige une ligne `Estimate:` dans sa description ou un commentaire, sauf si la raison est `rollback` ; sinon l'appel est refusé avec `estimate_required`. Une seule transaction écrit une ligne `workflow_escalated` (la raison et la cible) et une ligne `intake_call` avec `call` `escalated` et l'estimation, puis enregistre le changement. Sans tâche active, le ticket entre aussitôt dans l'étape du workflow complet, avec une exécution pour le responsable de cette étape ; avec une tâche active, le changement reste en attente et s'applique après la fin de la dernière tâche. Un ticket terminé suit le workflow complet sans être confié à personne ; un ticket Quick rouvert passe à son workflow précédent, avec une exécution pour l'étape où il se trouve. Le mouvement inverse est contrôlé : un agent qui place un ticket dans Quick (`issue update --workflow`) ouvre une carte d'approbation pour les propriétaires et ne change rien tant qu'elle n'est pas approuvée, alors qu'un membre change immédiatement. Un agent muni d'un jeton de tâche qui déplace un ticket vers un projet qui suit Quick (`issue update --project`, avec `project_id` pour seul champ ; tout autre champ est refusé avec `quick_move_alone`), ou qui fait passer un projet à Quick (depuis une exécution sur un ticket), ouvre une carte d'approbation du propriétaire et ne change rien tant qu'elle n'est pas approuvée ; un membre le fait immédiatement. Les cartes sont `issue.project.quick_set` et `project.workflow.quick_set` : chacune scelle l'affectation vue par le propriétaire, le serveur la recalcule sous verrou à l'approbation, et toute différence termine la carte en `stale_base`. Tout autre identifiant d'agent reste refusé avec `budget_rebinding_requires_interactive`.

## Router le travail par capacité

Le paramètre d’espace de travail `capability_routing` associe un type de ticket à un agent auteur et à une liste ordonnée d’agents relecteurs, par exemple `{"feat": {"author": "<id de l’agent>", "reviewers": ["<id de l’agent>"]}}`. Les clés sont des types en minuscules, les identifiants doivent être des agents de l’espace de travail, `reviewers` n’est pas vide et l’auteur n’est pas relecteur. Il est vide par défaut ; vide, le comportement ne change pas. Seuls les gestionnaires **Author** et **Reviewer** le lisent. Il ne change que par une carte `workspace.settings` (`multica config propose workspace.settings --set 'capability_routing:=<json>'`) ; un enregistrement générique des paramètres conserve la valeur stockée. Lisez-le avec `multica workspace capability-routing` ; la commande affiche `{}` s’il est vide.

**Author** est un gestionnaire pour une étape comme En cours. Un ticket qui entre dans l’étape va à son auteur : la personne ou l’agent qui a le dernier pris le ticket dans cette étape, sinon l’`author` que `capability_routing` indique pour le type du ticket (le préfixe Conventional Commit du titre, comme `feat`). Modifier la table conserve l’auteur déjà établi ; une personne qui réassigne le ticket en devient l’auteur pour l’entrée suivante. Sans l’un ni l’autre, l’étape ne passe la main à personne, et le lint du workflow avertit (WF015) quand l’espace de travail ne route aucun auteur. Définissez-le avec `multica workflow handoff set <workflow> <status-key> --handler author`.

Une étape `reviewer` confie la tâche au premier relecteur joignable listé pour le type de la tâche (le préfixe Conventional Commit du titre) dont le laboratoire est connu, diffère de celui de chaque auteur et qui n’est pas auteur. Un remplacement, un responsable persistant ou un responsable nommé dans la même écriture suit la même règle. Si aucun ne convient, ou si le type de la tâche n’a aucune entrée de routage, le passage est refusé avec `409 review_independence`, en nommant les laboratoires, et la tâche reste inchangée.

Une étape `same_as` confie le ticket à l’agent qui a traité en dernier une autre étape du workflow sur ce ticket, afin qu’un même agent puisse le suivre sur plusieurs étapes. Définissez-la avec un gestionnaire `{"type": "same_as", "step": "<status-key>"}`. L’agent est l’assigné du ticket tant qu’il est dans cette étape, sinon celui qu’il avait en la quittant la dernière fois. Un agent archivé ou disparu est considéré comme introuvable. Si aucun n’est trouvé, l’étape utilise l’agent de l’`id` facultatif du gestionnaire, sinon le gestionnaire de l’étape nommée. `step` doit désigner une autre étape du même workflow, et une étape ne peut pas revenir à elle-même par d’autres étapes `same_as` ; un enregistrement qui enfreint l’une de ces règles est refusé. `multica workflow get` affiche le gestionnaire sous la forme `same_as: <status-key>`. Sur l'étape `agent_review`, l'agent trouvé doit aussi respecter la règle d'indépendance du relecteur (un auteur, ou un agent du même laboratoire qu'un auteur, est refusé avec `review_independence`).

## Passer à l’étape suivante

Changez le statut d’une tâche ou faites glisser sa carte vers une autre colonne. Si cette étape prévoit un passage de relais, vérifiez le destinataire et, pour un agent, les consignes qu’il recevra.

<WorkflowDemo />

Si vous créez une tâche dans un projet et que son statut prévoit un passage de relais, elle est confiée directement au responsable de cette étape, même si vous avez choisi un responsable ; un agent commence aussitôt. La fenêtre de création indique à qui elle sera confiée. Pour la créer sans rien lancer, placez-la dans Backlog.

Si le responsable précédent est un agent dont l’exécution est encore en cours ou en attente, la confirmation propose en plus de l’arrêter ou de l’annuler, option cochée par défaut. Laissez-la cochée, sauf si vous voulez que les deux agents travaillent en même temps ; ses commentaires publiés et le travail déjà enregistré sont conservés.

**Une fois terminé, passer à** et **En cas de rejet, renvoyer à** indiquent à l’agent où déplacer la tâche ensuite. La fin d’une exécution ne fait pas avancer la tâche à elle seule : c’est le membre ou l’agent responsable de l’étape qui met à jour son statut. Quand un agent fait entrer la tâche dans l’étape suivante, le passage de relais de cette étape se déclenche de la même façon.

Le passage de relais et ses consignes restent dans l’historique de la tâche. Le menu du workflow sur le tableau du projet permet d’afficher le parcours complet.

## Quand une PR est fusionnée [#pr-merged]

Une fusion change un statut grâce à un seul réglage de l'espace de travail : **Paramètres → Code → Après la fusion des PR, passer la tâche à**. Voir [Intégration GitHub](/github-integration). La règle se définit et s'affiche uniquement là. Le tableau et l'éditeur du workflow ne la dessinent pas, et elle n'est jamais enregistrée dans le workflow. Avec **Ne pas changer**, une fusion ne déplace aucune tâche. Si le workflow ne contient pas le statut que nomme le réglage, la tâche ne bouge pas.

Quand cette étape a un responsable, la fusion lui confie la tâche et démarre son exécution, comme pour tout autre déplacement.

### La transition `pr.merged` est obsolète

Un ancien workflow peut enregistrer une transition protégée par `pr.merged`. Tant que le réglage n'est pas **Ne pas changer**, une transition `pr.merged` enregistrée ne déplace plus les tâches elle-même : elle lance la même vérification que le réglage. La liste des conditions de l'éditeur propose toujours `pr.merged`, mais tant qu'un statut de fusion est choisi, un enregistrement qui en ajoute une est refusé avec un message qui renvoie à Paramètres → Code. Avec **Ne pas changer**, les transitions enregistrées fonctionnent comme avant. Elles seront supprimées dans une prochaine version.

## Ajuster un workflow

Plusieurs projets peuvent partager un workflow. Les modifications enregistrées dans **Paramètres → Workflows** s’appliquent à tous les projets qui l’utilisent. Pour changer le parcours d’un seul projet, dupliquez le workflow et choisissez la copie dans ce projet.

Les administrateurs peuvent aussi configurer un passage de relais depuis le tableau du projet : survolez l’en-tête d’une colonne et cliquez sur **Confier à…**, ou sur le responsable déjà affiché. Si d’autres projets partagent le workflow, la question **Où appliquer cette modification ?** s’affiche. Choisir uniquement le projet actuel crée une copie du workflow pour lui, sans changer les autres projets.

Retirer une colonne peut vous demander de choisir un nouveau statut pour les tâches qui s’y trouvent. Les autres restent en place et ce déplacement ne lance pas d’agent. La bibliothèque de statuts, sous la liste des workflows, permet de modifier les noms et les couleurs ; ces changements s’appliquent partout où le statut est utilisé.

Définissez **Exécutions max par ticket** dans l’éditeur de workflow pour limiter le nombre d’exécutions qu’un ticket peut lancer avant que le workflow le bloque (de 1 à 1000 ; laissez vide pour la valeur par défaut de 15). La modification exige une session web ou bureau connectée ; un enregistrement qui ne touche pas ce champ fonctionne depuis n’importe quel client. L’interrupteur **Inclure les PR des sous-tickets** à côté contrôle si les garde-fous de PR lisent aussi les PR des sous-tickets (activé par défaut) et suit la même règle. Un agent ou un jeton ne peut modifier aucun de ces champs directement : il reçoit `budget_requires_decision` et propose la modification avec `multica config propose workflow.budget`, puis un propriétaire l’approuve avec une clé d’accès. La même limite s’applique quand un agent ou un jeton crée un ticket, ou le rattache à un workflow dont le budget est plus large (`budget_rebinding_requires_interactive`). Elle demande la même décision : `multica issue create` et `multica issue update` acceptent `--workflow <id> --decision-id <id>`. La décision doit être de classe `spend` et son propriétaire ne doit pas être en récupération de clé d’accès. Tant que le garde-fou de clé d’accès de l’espace de travail est sur `block`, le propriétaire doit aussi avoir répondu avec une clé d’accès ; sinon l’écriture est refusée et nomme la condition manquante. Depuis une exécution d'agent, `multica issue update <id> --workflow <workflow-id>` avec un budget plus large n'a pas besoin de décision : la commande ouvre une carte d'approbation pour les propriétaires de l'espace de travail, affiche son identifiant d'action et son URL, et laisse le ticket inchangé jusqu'à ce qu'un propriétaire l'approuve avec une clé d'accès. L'approbation échoue avec `stale_base` si le workflow du ticket, celui de son projet ou son budget a changé après l'ouverture de la carte.

Sur un ticket avec budget d’exécutions, la barre latérale affiche un compteur : exécutions utilisées, restantes, alerte à 80 % et état **Budget d'exécutions épuisé**. **Augmenter** et **Recharger** demandent à un propriétaire de l’espace d’approuver des exécutions supplémentaires. Si vous êtes propriétaire, vous approuvez sur place avec votre passkey ; sinon, le propriétaire reçoit la demande. Dans la liste et sur le tableau, un ticket arrêté par le budget affiche une pastille **Budget utilisé** à côté de son statut. Une fois qu’un propriétaire a approuvé, la carte décidée et le panneau d’approbation affichent la nouvelle limite et ce qu’est devenu le ticket arrêté (exécution en file, exécution démarrée, statut rétabli, ou raison de la non-reprise), et se mettent à jour sans rechargement.

Pour supprimer un workflow, passez d’abord les projets qui l’utilisent à un autre workflow. Les tâches gardent leur statut actuel.

Si **Paramètres** ne contient pas **Workflows**, la fonctionnalité n’est pas encore disponible dans cet espace de travail ; les statuts se gèrent toujours dans **Paramètres → États des tâches**.

## Retenir les nouvelles demandes d’un projet [#intake-hold]

Un espace de travail peut garder les nouvelles demandes de premier niveau dans **Backlog** pendant une fenêtre de temps, pour que des personnes les lisent et les libèrent avant que les agents ne commencent. La règle est le réglage d’espace de travail `intake_hold` : une liste avec une entrée par projet. Chaque entrée contient `project_id`, `mode`, `starts_at`, `ends_at`, `exempt_types`, `exempt_labels`, `exempt_escalation_classes`, `exempt_autopilot_ids`, `exempt_issue_ids` et `source`. Un agent la modifie avec le correctif des réglages de l’espace de travail, qu’un propriétaire approuve avec une clé d’accès. Un projet sans entrée n’est pas concerné. `source` est obligatoire et chaque ID est un UUID en minuscules avec tirets ; une valeur qui enfreint l'une de ces règles est refusée à l'enregistrement.

Les modes sont `off` (rien n’est retenu), `warn` et `block`. Une tâche est retenue tant que toutes ces conditions sont vraies : la fenêtre de l’entrée est ouverte (de `starts_at` inclus à `ends_at` exclu) ; la tâche a été créée à `starts_at` ou après ; elle n’a pas de parent ; elle est dans Backlog, ou y a été mise en attente par une demande de décision ; aucune personne ne l’a libérée ; aucune exemption ne s’applique. En mode `block`, un changement de statut qu’un agent ou un jeton fait sur une tâche retenue est refusé avec le code HTTP 409 et le code `intake_hold`, que la tâche soit dans Backlog ou mise en attente depuis Backlog ; le corps contient `ends_at`, `fix` et `release_paths`. Un déplacement vers `cancelled` n’est pas refusé. La création par un agent ou un jeton, dans le projet, avec un statut autre que `backlog` ou `cancelled` est refusée de la même façon ; une création sans statut arrive dans Backlog, et la nouvelle tâche reçoit la clé de métadonnées `intake_hold` égale au `source` de l’entrée. Le déplacement ou la création d’une personne n’est jamais refusé. En mode `warn`, rien n’est refusé et le serveur écrit une ligne de journal `intake_hold_warn`.

`GET /api/issues/{id}` renvoie un champ `intake_hold` avec `source`, `held`, `owned`, `reason`, `ends_at` et `exempt_after`. `owned` reste vrai après `ends_at`, ce qui distingue une tâche que la retenue a couverte d’une tâche qu’elle n’a jamais couverte. Le champ est absent pour une tâche qui a un parent et pour un projet sans entrée. Les endpoints de liste ne le renvoient pas. `reason` vaut `held`, `ended`, `not_started`, `mode_off`, `created_before_start`, `left_backlog`, `released_by_member`, `exempt_type`, `exempt_label`, `exempt_escalation_class`, `exempt_autopilot` ou `exempt_issue_id`. Une tâche dont le titre n’a pas de type, comme `plain words`, est retenue. La priorité n’exempte rien.

Quand un agent a besoin de la décision d’une personne sur une dépense, un déploiement, une publication, une action irréversible ou une orientation produit, il la demande par une demande de décision. Si l’entrée liste cette classe dans `exempt_escalation_classes`, la réponse de la personne lève la retenue de cette seule tâche, 10 minutes après la réponse. Jusque-là, `held` reste vrai et `exempt_after` indique l’heure à laquelle l’exemption commence. Une réponse retirée n’exempte rien, et une demande `reversible` n’exempte jamais. Tant que l’issue est retenue, la demande garde son déroulement complet, mais la remise de sa réponse, ou de tout autre événement de décision (retirée, expirée, reposée, rétractée), ne démarre aucune exécution. La remise est réglée comme `skipped_ineligible` et n’est pas relancée. En mode `warn`, la remise s’exécute comme d’habitude. Il en va de même pour un épisode d’attente dans une étape « personne responsable » (il se ferme et se règle comme `skipped_ineligible`, sans exécution de reprise), pour le message de discussion d’une personne sur une carte d’action ouverte (le commentaire est enregistré et le réveil vaut `skipped_ineligible`) et pour l’annulation, par une personne, d’une action exécutée (l’annulation est enregistrée et aucune exécution ne démarre). L’exécution qui a créé l’issue retenue peut aussi ouvrir cette demande sur elle, tant que cette exécution est en cours ; un agent qui n’a pas créé l’issue ne le peut pas, et une demande `reversible` de l’exécution créatrice est refusée. L’exécution créatrice doit d’abord publier un commentaire sur l’issue, car la demande cite un commentaire de cette issue.

Une personne libère une tâche de deux façons. Soit elle la déplace hors de Backlog dans l’application web, l’application de bureau ou la CLI, connectée en son nom ; soit elle la déplace hors d’un statut où la tâche avait été mise en attente depuis Backlog, et le serveur enregistre la libération. Un jeton qui appartient à un agent ou à un runtime cloud ne libère jamais une tâche. Le serveur enregistre la libération dans la ligne de statut de la personne, avec la clé `intake_release` dans ses détails, égale au `source` de l’entrée. Il n’écrit cette clé que pour un déplacement de personne qui change le statut vers autre chose que `backlog`, et seulement tant qu’une entrée ouverte couvre la tâche. La mise en attente, la reprise, les déplacements système et ceux d’un agent ou d’un runtime cloud ne la portent jamais. Un déplacement hors de l’état en attente libère la tâche grâce à cette clé, même s’il a été demandé avant la mise en attente et enregistré après.

En mode `block`, une tâche retenue ne démarre non plus aucune exécution qui en dérive : mention ou réponse d’un agent, assignation à un agent ou à une équipe, réveil créé par un agent, exécution d’un autopilote, relance ou nouvelle tentative automatique. Chacune est refusée avec la raison de dispatch `intake_hold`, visible dans `trigger_outcomes` ou dans `last_error` du réveil. La mention d’un membre et le réveil créé par un membre démarrent toujours une exécution. Une tâche qu’une personne a libérée, ou dont la réponse d’escalade est effective, n’est pas retenue : ses exécutions démarrent. Une exécution d’alerte d’un garde (garde d’attente de décision, garde de tâche démarrée inactive, réparation de demande) sur une tâche retenue est refusée de la même façon, et le garde enregistre le refus.

## Conditionner une étape à l’intake ou à la preuve QA [#intake-qa-gates]

Une étape peut porter des garde-fous d’entrée : des conditions qu’un changement de statut vers l’étape doit remplir. Deux garde-fous lisent ce qu’un agent a écrit sur le ticket. Ajoutez-les à la liste `entry` de l’étape, par exemple `{"guard": "intake_simple", "mode": "warn", "param": "1"}`. Le mode est `off`, `warn` ou `block` ; un garde-fou absent de la liste est désactivé, et si tous le sont, un ticket change de statut comme avant. En `warn`, le changement passe et le ticket reçoit un seul avertissement ; en `block`, il est refusé avec le fait en cause et un correctif, et une personne peut le forcer avec un motif, sauf si le garde-fou définit `member_override` à `false`.

- `intake_simple` est satisfait quand la description ou les commentaires du ticket contiennent les lignes `Estimate:`, `Repos:`, `Schema change:`, `Security change:` et `Human decision:`, et que les réponses indiquent un ticket simple. La ligne la plus récente de chaque type compte. Il échoue si une ligne manque ou est illisible, si l’estimation (par exemple `1h` ou `45m`) dépasse le `param` du garde-fou (en heures, supérieur à 0 et au plus 24), si `Repos:` cite plus d’un dépôt, si une ligne oui/non vaut `yes`, ou tant que le ticket a une demande de décision ouverte. `param` est obligatoire.
- `qa_proof` est satisfait quand l’agent qui effectue le changement a écrit, depuis l’entrée du ticket dans l’étape courante, un commentaire avec une ligne `QA:` contenant un lien (`https://…`) ou suivie d’un bloc de code, et que cet agent a lui-même défini la métadonnée `post_close_work` du ticket (sa dernière écriture ; une valeur laissée par un autre acteur ou une exécution antérieure ne compte pas). Il n’accepte pas de `param`. Le commentaire de quelqu’un d’autre ne compte pas.

Les deux garde-fous échouent par défaut : une valeur illisible compte comme un échec. Aucun n’est accepté comme garde de transition. À chaque contrôle de `intake_simple`, l’activité du ticket reçoit une ligne `intake_call` avec `call` (`simple` ou `rejected`), le `estimate` brut et le `step`.

`pr.none_open` est un troisième garde-fou d’entrée, qui lit les PR et non ce qu’un agent a écrit. Il est satisfait quand aucune PR ouverte ou en brouillon n’est liée au ticket, ni à ses enfants quand le workflow inclut les PR des enfants. Les PR fusionnées ou fermées ne le bloquent pas, et un ticket sans PR passe. Placez-le sur l’étape où un agent clôt (par exemple `agent_accepted`) et donnez à l’étape précédente une arête `agent_done` vers elle : un agent peut alors clore un ticket `in_review` sans rien à fusionner. Un agent ne peut jamais utiliser ce raccourci tant qu’une PR est ouverte : le refus liste chaque PR ouverte (par exemple `acme/widget#12 (draft)`) avec le correctif, qui est de la fusionner ou de la fermer. Comme les autres garde-fous d’entrée, il n’est pas accepté comme garde de transition, et `multica workflow lint` l’accepte dans `entry`.
