Le CLI Multica sert à la fois à connecter des runtimes locaux et à gérer, depuis le terminal, les espaces de travail, les tâches, les agents et les automatisations. Cette page présente les parcours courants ; les options prises en charge par la version installée sont toujours définies par le `--help` de chaque commande.

## Installation

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
```

Si Homebrew est installé, vous pouvez aussi exécuter :

```bash
brew install multica-ai/tap/multica
```

</Tab>
<Tab value="Windows">

Dans PowerShell, exécutez :

```powershell
irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex
```

</Tab>
</Tabs>

Vérifiez l'installation :

```bash
multica version
```

## Première connexion

Choisissez le service auquel vous vous connectez :

<Tabs items={["Multica Cloud", "Instance auto-hébergée"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="Instance auto-hébergée">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup` enregistre l'adresse du serveur, ouvre un navigateur pour finaliser la connexion et démarre le daemon. Une fois l'opération terminée, vérifiez :

```bash
multica auth status
multica daemon status
```

Si vous devez seulement vous reconnecter sans écraser le reste de la configuration, exécutez `multica login`. Sur une machine sans navigateur, créez d'abord un jeton d'accès personnel dans les paramètres web, puis saisissez-le avec :

```bash
multica login --token
```

La commande vous invite à coller le jeton dans le terminal, ce qui évite que sa valeur complète n'apparaisse dans l'historique du shell.

## Choisir un espace de travail

Listez les espaces de travail et changez celui par défaut :

```bash
multica workspace list
multica workspace switch <slug>
```

Les commandes suivantes utilisent cet espace de travail. Une commande isolée peut le remplacer avec `--workspace-id`, ou vous pouvez définir `MULTICA_WORKSPACE_ID`.

Inviter des membres :

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## Opérations courantes sur les tâches

```bash
# Consulter et rechercher
multica issue list
multica issue get MUL-123
multica issue search "échec de connexion"

# Créer et mettre à jour
multica issue create --title "Corriger l'échec de connexion"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# Commentaires et exécutions
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "Vérifiez d'abord les tests de régression"
multica issue comment update <comment-id> --expected-revision 2 --content "Vérifiez les tests de régression et les notes de version"
multica issue runs MUL-123
```

Lisez les descriptions ou commentaires longs depuis stdin pour ne pas avoir à gérer les retours à la ligne et les guillemets :

```bash
multica issue create --title "Notes de mise à niveau" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

Consulter, arrêter ou relancer une exécution :

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123 --fresh
```

Ajouter un commentaire à une exécution encore en cours, au lieu de mettre une exécution de suivi en file d'attente (uniquement les exécutions qui acceptent des messages supplémentaires, et seulement pour un agent que votre commentaire pourrait démarrer) :

```bash
multica issue comment add MUL-123 --content-file note.md --steer <task-id>
multica issue comment add MUL-123 --content-file note.md --steer-active
```

Un commentaire d'une tâche d'agent qui mentionne un membre (`[@Nom](mention://member/<id>)`) n'est accepté que comme demande de décision, comme commentaire `--decision-intent`, `--decision-record` ou `--decision-veto`, ou avec `--notify-only`. Utilisez `--notify-only` pour une simple information qui n'attend pas de réponse. Il n'ouvre jamais d'attente et ne compte jamais comme demande de décision. Il ne se combine pas avec les options de décision. Le contrôle lit le lien de mention, pas le texte, et un lien dans du code compte. Le réglage d'espace de travail `ask_guard_mode` (`off`, `warn`, `block`) décide si un commentaire refusé est seulement journalisé ou renvoie 422. Les tâches de chat et les appels sans tâche sont seulement journalisés. Une modification qui ajoute une mention de membre suit la même règle.

```bash
multica issue comment add MUL-123 --content-file fyi.md --notify-only
```

Si une tâche ouverte portant le même titre (sans tenir compte de la casse ni des espaces en trop) existe déjà sous le même projet et le même parent, `issue create` refuse et indique cette tâche. Pour en créer une autre malgré tout, ajoutez `--allow-duplicate`. Pour marquer une tâche comme doublon d'une autre, utilisez `multica issue status MUL-124 cancelled --duplicate-of MUL-123`.

### Chronologie

`issue get` montre la tâche telle qu'elle est maintenant. `issue timeline` liste dans l'ordre les changements de statut, de priorité, d'assigné, de titre et de dates ainsi que les résultats des exécutions, entremêlés avec les commentaires. C'est la commande pour savoir « quand est-elle passée en in_review » ou « depuis combien de temps est-elle bloquée dans ce statut » :

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only` retire les commentaires et garde tous les enregistrements d'activité ; `--action` ne renvoie que les actions indiquées, peut être répété et implique `--activity-only`. Le serveur limite l'historique qu'il lit ; si le résultat est tronqué, un avertissement s'affiche sur stderr, et il ne faut pas en déduire de durée.

```bash
multica issue description history MUL-123
multica issue description diff MUL-123 --from 30 --to 35
```

`issue description history` liste les révisions enregistrées de la description d'une tâche, de la plus ancienne à la plus récente, avec le numéro de révision, l'heure (ICT) et l'auteur. `issue description diff` affiche un diff unifié entre deux d'entre elles. Le numéro de révision est le compteur de révision de la tâche. Seules existent les révisions enregistrées après la mise en service de l'historique ; pour chaque tâche, la première entrée est un état de référence de la description à ce moment-là. Une révision qui n'a pas modifié la description renvoie le dernier texte antérieur. Une révision inconnue renvoie 404. `--output json` est disponible pour les deux.

### Lire de longs fils de commentaires

Sur une tâche très commentée, tout lire un par un coûte beaucoup de tokens à un agent. Parcourez d'abord les fils, puis ouvrez celui qui vous intéresse :

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only` ne renvoie que les commentaires de premier niveau, chacun avec son nombre de réponses et l'heure de sa dernière activité.
- `--summary` réduit chaque commentaire à un court aperçu.
- `--compact` s'applique à la sortie JSON et retire les champs sans information (comme l'`issue_id` répété et les tableaux vides).
- `--recent N` renvoie les N fils les plus récemment actifs avec toutes leurs réponses, ce qui peut être long.
- Les fils résolus sont repliés par défaut sur le premier commentaire et la conclusion ; ajoutez `--full` pour le texte complet.

Les listes peuvent aussi se limiter aux champs utiles : `multica issue list --output json --fields id,identifier,title,status`. Le filtrage a lieu dans la CLI : il réduit la sortie et le contexte, pas la requête.

### Réveils

Un réveil lance une exécution ordinaire d'un agent quand un événement se produit, qu'une condition devient vraie ou qu'une heure arrive. Les règles complètes figurent dans [Réveils de tâche](/issue-wakeups).

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "Quand ils répondent, mettre à jour le devis d'après leur réponse"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "Vérifier si le fournisseur a répondu"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

Créer un réveil depuis un terminal en tant que membre demande `--agent-id` ; un agent qui en crée un pendant sa propre exécution se réveille lui-même par défaut.

Une règle qu'une personne peut déclencher est une règle d'événement sur un commentaire, un changement de tâche, une réaction ou une pièce jointe, dont le filtre d'acteur n'exclut pas les membres. Quand le paramètre d'espace `ask_guard_mode` vaut `warn` ou `block`, un agent ne peut pas enregistrer seul une telle règle, sauf dans l'un de ces cas :

- `--decision <request-id>` lie la règle à une demande de décision de cette tâche. La demande doit être posée ou répondue, et concerner le membre de `--filter-actor-id` s'il est donné. Une demande lie une seule règle active à la fois.
- `--purpose observe` marque une règle qui n'attend pas une personne. Chaque déclenchement causé par un membre est enregistré comme événement d'audit.
- `--filter-actor-type agent` sans `--filter-actor-id` correspond à n'importe quel agent et à aucun membre.

En mode `block`, le refus est un 422 dont le message donne la commande de correction. En mode `warn`, la règle est créée et un événement est enregistré.

### Règles de réveil

Les règles de réveil d'espace de travail et de projet (voir [Réveils de ticket](/issue-wakeups)) ont leur propre commande, avec `create` et `get` à côté de celles-ci :

```bash
multica wakeup-definition list [--project <project>] [--output json|table]
multica wakeup-definition preview [--project <project>] [--rule <rule>] [--output json|table] --config-file rule.json
multica wakeup-definition update <rule> [--project <project>] --revision <n> --config-file rule.json
multica wakeup-definition delete <rule> [--project <project>] --revision <n>
```

`--revision` est la révision que `list` affiche ; `update` avec `--revision 0` crée une surcharge. `preview` n'enregistre rien : il affiche la règle résolue. Pour une règle de condition, `already_satisfied` compte les tickets qui correspondraient immédiatement et `issues` les nomme (`--output table` les affiche en liste). L'aperçu examine les 200 premiers tickets du périmètre et évalue ceux qui sont ouverts et hors backlog ; si le périmètre en contient davantage, `truncated` vaut `true` et d'autres tickets peuvent correspondre. Une règle d'événement n'a pas de prédicat : son aperçu n'a pas de `already_satisfied` et ne correspond à aucun ticket existant. Seul un propriétaire ou un administrateur peut modifier ou supprimer une règle. Tout membre humain peut la prévisualiser ; un agent ou une autre identité machine reçoit `403`, et une règle créée par un agent reste désactivée jusqu'à ce qu'un humain l'active.

### Suivre la progression dans un DM

Un DM suit les tickets que son agent crée pour vous. Les membres gèrent les suivis uniquement dans un DM qu'ils ont créé, avec `--chat`. Un agent exécute `multica issue follow <issue>` sans `--chat` : le DM vient de sa propre tâche, et une tâche sans DM est refusée. Les sous-tickets héritent du suivi actif de leur parent.

```bash
multica issue follow MUL-123 --chat <chat-session-id>
multica issue mute-follow MUL-123 --chat <chat-session-id>
multica issue unmute-follow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id> --scope root
multica issue follows --chat <chat-session-id>
```

`unfollow` met fin au suivi de ce ticket. Avec `--scope root`, il met aussi fin aux suivis que ses sous-tickets en ont hérités ; un sous-ticket suivi manuellement reste suivi. Un sous-ticket que vous avez cessé de suivre n'est pas suivi à nouveau à la création d'un autre sous-ticket.

## Agents et skills

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

Lorsqu'un import rencontre un skill du même nom, le comportement par défaut est de s'arrêter sans modifier le contenu existant. Choisissez selon votre intention :

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite` n'est autorisé que pour le créateur du skill et conserve l'ID d'origine ainsi que les liaisons avec les agents.

Les variables d'environnement et la configuration MCP contiennent souvent des tokens. Une valeur tapée sur la ligne de commande reste dans l'historique du shell et dans la sortie de `ps` ; passez-les plutôt par les formes `-file` ou `-stdin` :

```bash
multica agent create --name "Assistant ops" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- Les options `--custom-env` n'existent que sur `agent create`. Pour modifier les variables ensuite, utilisez `agent env set`, qui remplace l'ensemble ; les clés dont la valeur est `****` gardent leur valeur actuelle.
- `agent update --mcp-config null` efface la configuration MCP.
- `--custom-args` est un tableau JSON placé à la fin des arguments de lancement. Choisissez le modèle avec `--model` ; certains outils refusent un `--model` dans les arguments personnalisés.
- `--permission-mode` détermine qui peut invoquer l'agent : `private` pour le propriétaire seul, ou `public_to` avec `--public-to-workspace` ou `--public-to-member <user-id>`. `--visibility private|workspace` est l'ancienne forme, convertie en `--permission-mode` ; si les deux sont fournis, `--permission-mode` l'emporte.

## Daemon et runtimes

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

```bash
multica daemon autostart enable
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "Wrapper Claude interne" \
  --command-name ccms --runtime-type claude
```

`daemon autostart` enregistre le profil courant pour qu'il démarre à l'ouverture de session ; les différences entre plateformes sont décrites dans [Démarrage à l'ouverture de session](/daemon-runtimes#autostart). `runtime usage` couvre 90 jours par défaut, et `--days` va jusqu'à 365. `runtime update` demande au daemon de cette machine de mettre sa CLI à jour vers la version indiquée ; `--wait` attend la fin de la mise à jour. `runtime profile create` indique l'outil compatible avec `--runtime-type` (l'ancien `--protocol-family` fonctionne encore) ; les arguments fixes ne se définissent pour l'instant que dans l'application web.

La suppression d'un runtime auquel des agents actifs sont encore liés est refusée par défaut. `multica runtime delete <id> --cascade` dissocie ces agents, préserve leur configuration et leur historique, et annule leurs exécutions actives.

`multica runtime breaker list` affiche le disjoncteur de chaque fournisseur ; `multica runtime breaker reset <provider>` le ferme de force (propriétaire ou administrateur uniquement). Voir [Disjoncteur de fournisseur](/daemon-runtimes#provider-breaker).

Consultez [Daemon et runtimes](/daemon-runtimes) pour son fonctionnement et les profils personnalisés.

## Projets, espaces de travail et automatisations

```bash
multica project create --title "Campagne d'été" --lead "Lei Li" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "Opérations" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "Rapport de ventes hebdomadaire" --agent "Assistant ops" \
  --mode create_issue --issue-title-template "Rapport de ventes {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Europe/Paris
```

- `--lead` prend le nom d'un membre ou d'un agent. `--default-branch-hint` indique seulement à l'agent la branche par défaut du dépôt ; il ne change pas de branche.
- Le `--context` d'un espace de travail est fourni à tous ses agents. `--slug` ne peut plus être modifié après la création. `--issue-prefix` est mis en majuscules ; le changer renumérote toutes les tâches existantes, et les anciens identifiants cités ailleurs ne mènent plus nulle part.
- `multica workspace update --routing-agent <agent-id> [--routing-fallback-agent <agent-id>]` désigne l'agent qui prend les étapes de workflow de simple routage (par défaut `todo`, `blocked`, `merged`, `need_decision` ; modifiable avec `--routing-statuses`, et `--routing-overrides todo=<agent-id>` envoie un statut à un autre agent). L'agent de repli prend le relais quand cet agent est archivé ou quand son exécution échoue à cause du fournisseur. Une clé de remplacement `<workflow-id>:<status>` limite ce remplacement à un seul workflow. `none` désactive un champ. Seul un propriétaire ou administrateur humain peut le modifier, et chaque changement est consigné dans le journal d'activité.
- `--issue-title-template` ne remplace que `{{date}}` (UTC, `YYYY-MM-DD`) et refuse tout autre `{{...}}`. Le `--timezone` d'un déclencheur planifié vaut UTC par défaut.
- `--mode script --script <name> [--arg <value>]...` exécute un script autorisé sous le jeton de tâche de l'agent, sans session de modèle. `--script` et `--arg` exigent `--mode script`, et `--mode script` exige `--script`. `--description` n'est jamais exécuté. Sans liste d'autorisation du démon, toute tâche de script échoue de façon sûre. `--output json` affiche le nom du script et ses arguments dans `script_config`. `autopilot update --mode <autre>` efface le script. Le serveur supprime le jeton de tâche à la fin de la tâche, au mieux. Si la suppression échoue, le jeton reste valide jusqu'à son expiration ; rien ne le révoque plus tôt. Le résultat de l'exécution consigne sous `script` le nom du script, un SHA-256 de la liste d'arguments, le code de sortie et la durée, et définit `token_revoke_failed` lorsqu'une suppression a échoué.

### Propositions de changement de configuration

`multica config propose` construit le fichier d'action pour un changement de configuration de l'espace de travail. Il lit la valeur en vigueur, calcule `before_sha256` et `after_sha256` avec les mêmes recettes que le serveur, et écrit le fichier que prend `multica decision request --action-file`. Il n'envoie rien et n'écrit aucun secret. Une personne approuve toujours avec une passkey.

Champs : `agent.instructions <agent-id>`, `squad.instructions <squad-id>`, `workspace.context`, `workflow.steps <workflow-id>`, `workflow.step.instructions <workflow-id> --status-key <key>`, `workflow.budget <workflow-id>` et `workspace.settings --set clé=valeur|clé:=<json>`. Les champs texte prennent `--file` (UTF-8, sans octet NUL). `workflow.steps` prend le tableau d'étapes tel que le renvoie le GET du workflow ; modifiez cette sortie, car le serveur refuse la demande (`after_digest_mismatch`) s'il normalise vos étapes autrement. Pour `workflow.step.instructions`, le serveur calcule l'empreinte « after » : le fichier n'a pas de `after_sha256`, et l'empreinte affichée sert seulement de comparaison. `--out <chemin>` écrit le fichier ; `--dry-run` affiche les deux empreintes et l'action sans rien écrire. `--expires-in <secondes>` fixe l'expiration.

`workflow.budget <workflow-id>` prend `--max-runs <n>` (de 1 à 1000 ; 0 efface le plafond) et `--include-child-prs=<true|false>` à la place de `--file` ; indiquez-en au moins un, et un champ omis garde sa valeur enregistrée. Un agent ne peut pas écrire ces deux champs directement sur un workflow (`budget_requires_decision`) : proposez la modification, demandez la décision, et le serveur l'applique à l'approbation si le workflow correspond encore à l'empreinte lue par la CLI.

Un agent avec un jeton de tâche ouvre la carte en un seul appel : `multica workflow update <workflow-id> --max-runs-per-issue 40 --issue <issue> --for <user-id>` lit le workflow en direct, propose `workflow.budget.set` avec seulement les options de budget indiquées, affiche l’URL de la carte et n’écrit rien avant l’approbation du propriétaire. Répéter l’appel renvoie la même carte. Un appel de budget n’accepte ni `--name`, `--description`, `--steps-file`, `--start-status`, `--map` ni `--dry-run` ; la commande les refuse avant toute requête, lancez donc deux commandes. `--print-hash` affiche `before_sha256` et `after_sha256` de la modification de budget. `multica config propose workflow.budget` nomme la même option `--max-runs`. `multica issue update <issue> --workflow <workflow-id>` et `multica issue create --workflow <workflow-id>` acceptent les mêmes `--print-hash` et `--decision-id` (champ `issue.workflow`) quand le workflow a un budget plus large ; les deux commandes suivent une seule règle, et la session interactive d’un propriétaire n’exige aucune décision.

Tout autre champ est refusé avec `denylisted` avant toute lecture : `project.description`, passkeys et porte de décision, membres et rôles, transfert de propriété, secrets d'authentification et d'intégration, suppression de l'espace de travail, registre des actions et `delegated_governed_writes`. Une clé de réglages hors de la table autorisée du serveur est refusée de la même façon, et un patch qui mêle clés autorisées et refusées est refusé en entier. Le serveur revérifie à la demande et à l'approbation.

```bash
multica config propose workspace.context --file ./context.md --out ./action.json
multica config propose agent.instructions <agent-id> --file ./instructions.md --dry-run
multica config propose workflow.step.instructions <workflow-id> --status-key review --file ./step.md --out ./action.json
multica config propose workflow.budget <workflow-id> --max-runs 40 --include-child-prs=false --out ./action.json
multica config propose workspace.settings --set compact_prompt="..." --set wakeups_paused:=false --out ./action.json
multica decision request --issue MUL-123 --for <user-id> --class reversible --ask-file ./ask.md --action-file ./action.json
```

## Vue d'ensemble des commandes

| Commande | Rôle |
| --- | --- |
| `issue` | Créer, mettre à jour, assigner et rechercher des tâches ; gérer les commentaires, les abonnés, les étiquettes, les propriétés, les réveils, la chronologie et les exécutions |
| `project` | Gérer les projets et leurs ressources |
| `label`, `property` | Gérer les étiquettes et les propriétés personnalisées de l'espace de travail |
| `agent`, `skill`, `squad` | Gérer les agents, les skills et les squads |
| `autopilot` | Gérer les automatisations, les déclencheurs et l'historique des exécutions |
| `workspace` | Créer, consulter et changer d'espace de travail, et inviter des membres |
| `repo` | Gérer les dépôts de l'espace de travail et les extraire localement |
| `daemon`, `runtime` | Démarrer et arrêter le daemon local ; consulter et gérer les runtimes |
| `attachment` | Envoyer ou télécharger des pièces jointes |
| `user profile` | Consulter ou mettre à jour le profil de l'utilisateur actuel |
| `auth`, `login`, `setup` | Se connecter, vérifier l'état de l'authentification et initialiser une connexion |
| `config` | Consulter ou modifier la configuration locale du profil CLI actuel |
| `update`, `version` | Mettre à jour le CLI ou afficher la version |
| `guard` | Vérifier les appels d'outils des agents selon la politique de l'espace de travail |

`multica chat` lit **la session de messagerie externe qu'un agent traite actuellement** ; elle sert surtout aux agents des intégrations de messagerie et n'est pas une commande générale pour parcourir n'importe quelle discussion de l'espace de travail.

### Rapport shadow

Tout membre de l'espace de travail lit le rapport shadow de System 1 :

```bash
multica decision shadow-report [--since <RFC 3339>] [--until <RFC 3339>] --output json
```

Les blocs `decision` et `routing` couvrent toute la période. Le bloc `route` couvre la fenêtre `[since, until)` : `--since` et `--until` prennent des dates RFC 3339, `--until` vaut par défaut maintenant et `--since` 24 heures avant `--until`. Le serveur refuse une date invalide ou un `--since` postérieur à `--until` avec un 400.

Le bloc `route` compte une seule population d'événements : les changements de statut d'un agent marqués comme sortie d'une étape de routage (`eligible_exits`) et les étiquettes de route qui portent le même identifiant d'événement (`matched_labels`). `label_coverage` vaut `matched_labels / eligible_exits` et ne dépasse jamais 1. `via_route_share` est la part des événements appariés dont la première étiquette vient de `issue route`, et non du repli sur le statut. `duplicate_labels` compte les étiquettes qui partagent un événement avec une étiquette plus ancienne (cible 0). `labels_total`, `owner_only_labels` (une route qui a gardé le statut, donc sans événement) et `non_routing_labels` (une route depuis une étape sans agent de routage) restent hors de la couverture. `overridden` compte les étiquettes d'agent qu'une personne a inversées en moins d'une heure, et `override_rate` vaut `overridden / labels_total`. Le bloc contient aussi `decided`, `predicted`, `agreed`, `coverage` et `precision` par classe.

## ID et formats de sortie

Les tâches utilisent des clés comme `MUL-123` ou des UUID complets ; les préfixes courts d'UUID ne sont pas acceptés.

Pour les autres ressources, les commandes `list` affichent généralement des ID courts copiables et prennent en charge `--full-id` pour obtenir l'UUID complet. Lorsqu'un ID court est ambigu, le CLI demande davantage de caractères ou l'UUID complet. Les ID courts d'exécution exigent aussi `--issue` pour identifier la tâche à laquelle ils appartiennent.

De nombreuses commandes prennent en charge une sortie structurée :

```bash
multica issue list --output json
multica agent list --output json
```

Les scripts doivent utiliser la sortie JSON plutôt que d'analyser les tableaux destinés au terminal. Les formats de sortie et les options de pagination pris en charge par chaque commande sont définis par `multica <command> --help`.

## Profils et configuration

La configuration par défaut se trouve dans `~/.multica/config.json`. Utilisez `--profile <name>` pour isoler un ensemble distinct d'adresse de serveur, de jeton, d'espace de travail par défaut et d'état du daemon :

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

Les profils nommés se trouvent dans `~/.multica/profiles/<name>/config.json`. Inspectez les valeurs actuelles :

```bash
multica config show
multica config show --profile staging
```

Ne définissez pas `MULTICA_DAEMON_PORT` dans le shell hôte, le service Compose ou le point d'entrée du conteneur qui démarre un daemon. Le daemon hôte déduit son port de contrôle de santé de `--profile` et injecte lui-même cette variable dans les exécutions d'agent. Supprimez complètement la variable des anciens environnements de démarrage : sinon, les versions 0.4.22 et 0.4.23 prennent ce shell pour une exécution gérée et refusent la connexion. Les versions plus récentes permettent à la connexion humaine protégée et à `daemon status` de se rétablir lorsque le port est le seul signal d'exécution, mais les commandes API ordinaires et celles qui résolvent un profil restent volontairement bloquées (fail-closed) tant que la variable n'est pas supprimée.

Lorsque le CLI tourne au sein d'une exécution d'agent gérée par le daemon, il ne charge ni ne modifie ces fichiers de profil qui appartiennent à l'utilisateur humain. Les commandes de l'API Multica s'authentifient avec l'identifiant limité à l'exécution que le daemon injecte. `config show` et `config set` utilisent un état privé, local à l'exécution ; les commandes humaines ou locales comme `login`, `logout`, `setup`, `workspace switch`, les modifications de chemin des profils de runtime locaux, `daemon start` / `stop` / `restart`, `daemon logs` et `daemon probe-runtimes` sont indisponibles. Dans ce contexte, `auth status` n'affiche aucun élément de jeton.

`daemon status` et `daemon disk-usage` restent disponibles pour qu'un agent puisse inspecter le runtime qui l'héberge, dans les limites de ce runtime : `status` interroge le port de contrôle de santé injecté par le daemon, et `disk-usage` analyse la racine des répertoires de travail injectée par le daemon. Aucune des deux n'accepte `--profile` ; `disk-usage` refuse aussi `--all-profiles` et `--workspaces-root`, et sa colonne STATUS reste vide, car la renseigner exigerait le jeton enregistré de l'utilisateur humain. Utilisez `du` et `df` pour tout ce qui sort de ce périmètre.

Cela protège la résolution implicite des profils du CLI Multica tout en préservant les variables `HOME` et XDG habituelles qu'utilisent les outils des autres fournisseurs. Ce n'est pas une frontière du système de fichiers au niveau de l'OS : des processus qui tournent sous le même utilisateur système peuvent toujours ouvrir un chemin connu explicitement. Utilisez un utilisateur dédié, un conteneur, une VM ou une isolation équivalente lorsque cette garantie plus forte est nécessaire.

<Callout type="warning">
Les fichiers de configuration du CLI contiennent des jetons qui permettent d'accéder à Multica en votre nom. Ne les commitez pas dans un dépôt, ne les envoyez pas dans des journaux et ne les partagez avec personne.
</Callout>

### Propositions de décision

Un jeton de tâche propose une action encadrée qu'une personne approuve avec une passkey. La proposition ne modifie rien elle-même.

```bash
multica decision propose issue.run_budget.raise --version 1 --issue MUL-123 \
  --for <user-id> --param window_id=<id> --param new_cap:=40 [--reason "..."]
multica decision propose <action-type> --version 1 --issue MUL-123 --params-file ./params.json
```

`--version` et `--issue` sont obligatoires. `--param k=v` envoie une chaîne et `--param k:=<json>` envoie du JSON brut ; `--params-file` prend un objet JSON et ne se combine pas avec `--param`. La commande affiche le lien de la carte d'approbation. Pour une action de budget d'exécutions, ce lien ouvre l'approbation sur la tâche ; pour toute autre action, il mène à la carte dans le chat, où la personne l'approuve. Une carte à options simple (`multica decision request` sans `--action-file`) ne peut pas appliquer un changement : Approuver n'enregistre que la réponse. Le serveur ne peut pas lire l'intention : il ne refuse pas une telle carte, mais ajoute un conseil quand la décision ou une option ressemble à un changement de workflow, d'agent, d'équipe, d'espace de travail ou de budget (ou nomme un type d'action autorisé). Envoyez ce changement avec `multica decision propose`. Un refus affiche le statut et le code d'erreur du serveur. `multica issue budget raise` et `multica issue budget top-up` utilisent la même route avec un jeton de tâche (ajoutez `--for <user-id>`) ; avec un jeton d'accès personnel, ils ouvrent la demande de dépense comme avant. Les deux commandes acceptent un ou plusieurs ID d'issue : `multica issue budget top-up CHE-1 CHE-2 CHE-3 --for <user-id> --goal "<objectif>"`. Un seul ID garde la proposition unique. Avec un jeton de tâche, plusieurs ID appellent une seule fois la route de lot et affichent un seul lien de carte ; `--goal` nomme le lot (par défaut : l'action et le nombre d'issues) et `--output json` renvoie l'id du lot et un id de proposition par issue. Avec un jeton d'accès personnel, chaque ID ouvre sa propre demande. La route de lot exige une tâche de chat et accepte 25 issues au plus ; le serveur approuve un lot de raises avec une seule clé d'accès mais refuse un lot de top-ups à l'approbation : approuvez les top-ups un par un.

Approbateur automatique du budget de runs : quand une issue épuise son budget de runs, le serveur approuve lui-même la fenêtre suivante si la dernière fenêtre a progressé, ne montre aucune anomalie et si l'enveloppe quotidienne de l'espace de travail a encore de la marge. Le commentaire d'audit sur l'issue nomme la règle (`auto-approver v1`) et l'interrupteur. Une fenêtre approuvée relance aussi le run refusé par le serveur : l'issue n'est jamais mise en `blocked`. Il y a progrès quand un run a changé le statut de l'issue, modifié la tête ou l'état d'une PR liée (un commentaire sur la PR ne compte pas), ou fait un commit ; un commentaire ne compte jamais, quoi qu'il dise, donc un run sans rien de cela est sans effet. Une boucle (le même contrôle en échec, le même workflow CI en échec ou la même erreur de run dans au moins 3 runs ; les commentaires ne sont pas lus), une fenêtre sans effet (au moins 80 % des runs ne livrent rien), un pic de jetons (jetons par run supérieurs à 3 fois la médiane de l'espace), un va-et-vient (au moins 3 rallonges sur une issue en 24 h) ou un agent du pool OpenAI pendant la restriction OpenAI n'est jamais approuvé automatiquement : les propriétaires reçoivent au plus une carte groupée par jour ; les anomalies suivantes du même jour arrivent comme messages dans le chat de cette carte, et le brief liste les issues retenues. Tout autre cas, y compris une issue déjà `blocked` ou un run refusé qui ne vise pas l'agent assigné de l'issue, retombe sur la carte par issue. Paramètre d'espace de travail `run_budget_auto` : `enabled` (par défaut `false` : l'auto-approbation est livrée désactivée) et `daily_envelope` (runs supplémentaires par jour ICT, par défaut `300`) et `expected_checks` (les noms de checks que chaque head poussé doit avoir, tous terminés, pour que sa CI compte comme connue ; vide par défaut, ce qui retient toute fenêtre ayant poussé un head). Un snapshot où seule une partie des checks attendus est terminée ne compte pas comme connu. Un nom ne compte que comme exactement un run terminé de l'API Checks : un statut de commit du même nom, ou un second run de ce nom, retient la fenêtre. Activez-le (ou désactivez-le avec `"enabled":false`) avec `multica config propose workspace.settings --set 'run_budget_auto:={"enabled":true}'` ou une proposition de config `workspace.settings`.

### Les champs couverts exigent une action par passkey

Un jeton de tâche ou un jeton de nœud cloud ne peut pas écrire ces champs par les anciennes routes : `agent.instructions`, `squad.instructions`, `workspace.context`, les étapes de workflow et leurs instructions, et les clés de réglages d'espace de travail de la liste autorisée des actions de décision (`compact_prompt`, `auto_compact`, `idle_started_guard`, `wakeups_paused`, `mermaid_orientation` et les autres clés opérationnelles simples). Le serveur répond 403 avec `code: passkey_action_required` et un `action_type` qui nomme l'action à proposer à la place (`agent.instructions.set`, `squad.instructions.set`, `workspace.context.set`, `workflow.steps.set`, `workspace.settings.patch`). La valeur stockée ne change pas. Un reçu de vote, une liaison de décision, un reçu PASS et l'exception Hermes ne lèvent plus ce refus. Proposez l'action avec `multica decision propose <action-type>` ; une personne l'approuve avec une passkey. Les écritures faites par une personne et `project.description` fonctionnent comme avant.

## Piloter Multica depuis un autre agent de codage

Si l'essentiel de votre travail se passe déjà dans Codex, Claude Code ou Cursor, vous pouvez piloter Multica depuis ces outils au lieu de basculer vers un terminal. Le [skill Multica CLI](https://github.com/multica-ai/multica-cli) apprend à ces agents à utiliser les commandes de cette page en toute sécurité : lire les tâches et les fils de commentaires sans gaspiller de tokens, écrire les commentaires via un fichier, et gérer les effets de bord qu'entraînent les mentions, les changements de statut et les assignations.

Il passe entièrement par votre CLI authentifié et n'accorde aucun accès qui lui soit propre : les permissions proviennent toujours de votre connexion, du profil sélectionné et de l'espace de travail. Il nécessite le CLI v0.4.26 ou ultérieur. Le README du dépôt explique l'installation via la marketplace de plugins de Claude Code, l'installateur de skills de Codex, Cursor et tout autre outil qui charge des instructions Markdown.
