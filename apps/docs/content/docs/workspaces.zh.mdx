工作区是 Multica 的最上层边界。成员、任务、项目、智能体、skill 和执行记录都属于某一个工作区，不同工作区之间互不相通。

## 工作区的组成

| 类别 | 内容 |
|---|---|
| **工作** | 任务、项目、评论、附件、执行记录 |
| **团队** | 成员、角色、邀请 |
| **智能体** | 智能体配置、skill、运行时、自动化 |
| **共享设置** | 上下文、标签、[自定义属性](/issues#自定义属性)、集成 |

**上下文**会提供给工作区中的每个智能体，适合写团队背景、产品约定和长期有效的要求。一次性的运行要求写在对应的任务里。

## 创建工作区

创建时要填三项：

- **名称**：展示给成员，之后可以修改。
- **工作区 URL**：地址中的 slug，例如 `multica.ai/my-team` 里的 `my-team`。只能用小写字母、数字和连字符，不能与已有工作区或保留地址重复，创建后不可修改。
- **任务前缀**：根据工作区 URL 自动填好，创建前可以改。前缀为 `MUL` 时，任务编号显示为 `MUL-1`、`MUL-2`，在工作区内独立递增。只能用大写字母和数字，最多 10 位，之后也可以在设置里修改。

创建者自动成为 `owner`。

## 修改设置

`owner` 和 `admin` 可以修改名称、图标、描述、上下文和任务前缀；`member` 只能查看。

![工作区设置：名称、上下文、slug、任务前缀与危险区](/images/docs/workspace-settings.webp)

<Callout type="warning">
修改任务前缀后，所有任务立即换用新编号（`MUL-5` 变为 `NEW-5`），但 PR、分支名和聊天记录里的旧编号不会更新。
</Callout>

### 自动关闭

工作区设置 `auto_close` 决定子任务进入 `agent_accepted` 或 `merged` 步骤且已无事可做时的行为。该步骤的智能体只会把它关闭，所以服务器可以自己沿该步骤的 `agent_done` 边把它移到 `done`。

| 值 | 效果 |
| --- | --- |
| `off` | 不变。该步骤的智能体运行。 |
| `warn`（默认） | 该步骤的智能体照常运行。每次进入还会记录一条 `auto_close_would_close` 活动记录，写明满足的检查和随后的运行。 |
| `block` | 服务器把任务移到 `done`，记录一条写明所读检查的 `auto_closed` 活动记录，并且不启动运行。 |

关闭需要下面所有检查都通过。任何一项不满足或无法读取，该步骤的智能体照常运行。

- 任务有父任务。根任务永远不会被关闭。
- 最新的评审结论是不含 P0 或 P1 问题的 PASS，并且针对当前候选。有 PR 时，每个关联的 PR 都已在 PASS 所指的 head 上合并。没有 PR 时，候选是任务的文本：PASS 之后没有新附件、描述变更、评论（评审者自己的除外）、CHANGES 结论、过期或被取代标记，也没有回到 `in_progress`。
- 没有未完成的子任务、没有未处理的决策请求，并且任务进入该步骤时没有处于启用状态的唤醒（任务自己的合并监视，即 `pr.merged` 边，除外）。
- 描述中没有 `Blockers: Cheese stop` 行，且父任务的 `delivery_stop` 元数据不是 `stopped`。
- 任务元数据 `post_close_work` 为 `none`。由作者写入：`multica issue metadata set <issue> --key post_close_work --value none --type string`。任何其他值（例如对剩余工作的简短描述）都会保留这次运行。
- 工作流中有从该步骤到 `done` 的 `agent_done` 或 `pr.merged` 边。
- 仅 `merged`：每个关联的 PR 都已在 PASS 所指的 head 上合并到其仓库的默认分支。合并到其他分支（堆叠的一层）的 PR，或其推送未带 base 或默认分支的 PR，会保留这次运行。

PASS 所指 head 的 PR 仍未合并时，如果该步骤有到 `done` 的 `pr.merged` 边以及任务自己的监视，则不会保留运行：服务器不启动运行，并记录一条 `auto_close_pending_merge` 活动记录。之后合并会不经运行直接关闭任务。合并时服务器会重新检查所有条件。若有条件不再成立（新的 head 没有 PASS、出现新的有效唤醒等），则不关闭任务，而是启动该步骤的运行并移除监视。

用 `multica workspace update --auto-close-mode off|warn|block` 设置模式。无法读取的值按 `off` 处理。

### 阻塞进入时跳过运行

工作区设置 `blocked_run_skip` 决定任务进入 `blocked` 时是否启动阻塞步骤的运行。只有任务说明了它在等什么，并且该步骤的负责人已经有一个会继续这项工作的唤醒时，服务器才会跳过这次运行。

| 值 | 效果 |
| --- | --- |
| `off` | 不变。阻塞步骤的智能体在进入时运行。 |
| `warn`（默认） | 运行照常启动。每次本应被跳过的进入还会记录一条 `blocked_entry_would_skip` 活动记录，写明随后的运行。 |
| `block` | 服务器不启动运行，记录一条 `blocked_entry_linked` 活动记录，并保持该唤醒有效。 |

只有下列条件全部成立才会跳过运行。任一条件不成立或无法读取，运行照常启动。

- 任务元数据 `blocked_on` 已设置（`multica issue status <id> blocked --blocked-on <ref>`）。
- 阻塞步骤的负责人在该任务上有一个启用的条件唤醒，等待同一个引用：标志、目标以及状态、阶段或类型都相同。时间唤醒、其他条件或其他智能体的唤醒都不算。
- 该唤醒没有 `last_error`，在 7 天内结束，并使用 `--on-timeout wake`。
- 运行会被准入：任务还有运行预算，智能体未暂停。

如果关联的唤醒之后被停用或删除、出现 `last_error`、未产生运行就结束（已过期或被守卫拒绝），或不再匹配 `blocked_on`，服务器会启动阻塞步骤的运行，并记录一条 `blocked_entry_rearmed` 活动记录。若运行预算已用尽或智能体已暂停，该运行同样会被拒绝，记录中会注明。

### 唤醒实时加入

工作区设置 `wakeup_live_join` 决定当条件唤醒触发时，其智能体已在同一事项上有运行进行中的处理方式。服务器不再启动第二个运行，而是可以把这次触发作为唤醒项投递到正在进行的运行中。

| 值 | 效果 |
| --- | --- |
| `off` | 没有任何变化。触发会启动自己的运行。 |
| `warn`（默认） | 触发照常启动运行。每次本可加入的触发还会记录一条 `would_join_live` 活动记录，指明正在进行的运行。 |
| `block` | 服务器把触发投递到正在进行的运行，不排入新运行，并把唤醒的 `last_error` 设为 `Delivering into running run <id>; inputs retained`。 |

只有以下条件全部满足，触发才会加入。任何一项不满足或无法读取时，触发照常启动运行。

- 触发的每一条回执都是条件回执（`condition.met`）。定时、评论、表情回应和手动触发从不加入。
- 唤醒由智能体创建。它不绑定决定，不是系统规则或自定义规则实例，也未暂停。
- 目标智能体在该事项上恰有一个运行中的运行且没有等待中的运行，并且该运行与唤醒代表同一用户。
- 运行中的运行接受唤醒项，且触发的回执都不在任何唤醒项中。
- 没有跳过规则（例如暂停智能体的跳过）已消耗这次触发。
- 唤醒项入队时，该运行仍在运行。

回执在唤醒项结算前保持待处理，`once` 唤醒也会保持启用直到那时。运行以 `completed` 结束时，触发结算为 `joined_live`。若运行被取消或失败，或唤醒项被拒绝或从未被领取，唤醒会启动一个自己的运行并记录一条 `wakeup_join_fallback` 活动记录。同一运行中的类型化 PR 项通过自己的项结算，从不消耗条件回执。

使用 `multica workspace update --wakeup-live-join-mode off|warn|block` 设置模式。无法读取的值按 `off` 处理。

### 运行次数上限

两个工作区设置决定任务用完运行次数上限后的行为。两者的值都是 `{"mode": "off" | "warn" | "block"}`，默认值为 `block`，即当前行为。

| 设置 | 控制的上限 |
| --- | --- |
| `run_budget` | 任务所属工作流的单任务运行预算（`max_runs_per_issue`）。 |
| `run_guard` | 每周运行守卫：任务在 7 天内启动的运行次数。 |

| 值 | 效果 |
| --- | --- |
| `block` | 下一次派生运行被拒绝，负责人收到一张卡片。 |
| `warn` | 运行照常计数，超出部分显示在简报和 `multica issue budget get`（`state: warn`）中。不拒绝运行，不阻塞任务，也不打开卡片。 |
| `off` | 不阻塞、不警告、不开卡片。 |

循环断路器（`MULTICA_LOOP_BREAKER_MAX_RUNS`）不受影响。用 `multica workspace update --run-budget-mode` 或 `--run-guard-mode` 设置模式；代理在 `workspace.settings` 卡片上提议 `run_budget` 或 `run_guard`。

### 请求守卫

工作区设置 `ask_guard_mode` 决定当智能体的操作未创建决策请求就要求人去处理时的行为。

| 取值 | 效果 |
| --- | --- |
| `off`（默认） | 守卫不做任何事。 |
| `warn` | 守卫记录事件和指标，操作继续执行。 |
| `block` | 守卫先记录事件，再以 `422` 拒绝该操作。只有 `block` 事件会成为恢复工作。 |

### 合并队列设置

三项工作区设置用于配置合并队列。只有所有者可以写入，所有写入路径（`multica workspace update` 标志、设置保存和 `config propose` 操作）都使用同一个校验器。

| 设置 | 值 |
| --- | --- |
| `merge_queue_dequeue_routing` | `off`（默认）或 `warn`。在强制执行功能上线前，`block` 会被以 `routing-not-available` 拒绝。 |
| `merge_queue_actor_bindings` | `{"agents": [...], "people": [...]}`。同时出现在两个列表中的 GitHub 登录名会被拒绝。 |
| `merge_queue_watch_issue` | 接收合并队列事件的任务，可为空。 |

### 自动驾驶分配守卫

工作区设置 `autopilot_assign_gate` 决定当一个点名某个自动驾驶（autopilot）的 issue（其 id 紧挨着 “autopilot” 一词）被分配给智能体或小队，而运行所代表的人无法写入该自动驾驶（不是创建者、工作区管理员或被授权的协作者）时的行为。

| 值 | 效果 |
| --- | --- |
| `block`（默认） | 创建或更新被拒绝，返回 `403` 和代码 `autopilot_assign_no_write`。 |
| `warn` | 服务器记录一条警告。分配照常进行。 |
| `off` | 守卫不执行任何操作。 |

每个事件保留创建时的模式，因此从 `warn` 切换到 `block` 不会让之前的事件变成恢复工作。如果事件无法写入，操作会以 `503` 和 `Retry-After` 头失败，且不会写入任何内容。

工作区设置 `reversible_ask_guard`（默认 `off`，可选 `warn`、`block`）针对智能体发出的、类别为 `reversible` 的普通决策请求：智能体请求人批准本可自行决定并执行的工作。`warn` 只记录日志，`block` 以 `422` 拒绝。操作、提案和批量请求不受影响。改回 `off` 即可还原，不涉及数据变更。同一设置也适用于智能体在 `blocked` 或 `need_decision` 状态的议题上，对成员评论的普通回复，这类回复无需决策请求即可向该成员提问：`warn` 只记录日志，`block` 以 `422` 拒绝。顶层评论、对智能体的回复、提及智能体或小队的评论、带 `--notify-only` 的评论和决策请求不受影响。

工作区设置 `owner_script_guard`（`off`、`warn`、`block`；未设置时为 `warn`）适用于智能体的决策请求、操作请求和 `multica decision ask` 卡片：所有者不读 shell，所以卡片要求人运行命令就是请求本身的缺陷。八条规则（R1 至 R8，规则集版本 1）读取卡片文字及其步骤：shell 代码围栏、围栏或行内代码中的命令、`human_steps` 命令、脚本附件，以及紧邻命令或紧跟在已被标记的消息之后的运行提示词（如 “run”“paste”）。`warn` 照常送达并记录命中。`block` 以 `422` 拒绝，指出命中的规则和字段，并建议改用 `multica config propose`、`multica decision propose <type>` 或申请机器人权限。`off` 不做检查。每次检查写入一条事件，即一行 `owner_script_guard` 活动记录：卡片送达时与卡片在同一事务中，被拒绝时单独提交。事件包含 ID、结果、`delivered`、`rule_hits`、命令的带密钥哈希（`cmd_hmacs`）和 `retry_of`，不含消息文本。议题时间线不显示这些行。改回 `warn` 或 `off` 即可还原，不涉及数据变更。

工作区设置 `waiting_audience_guard`（默认 `off`，可选 `warn`、`block`）针对智能体在 `in_review`、`blocked` 或 `need_decision` 状态的事项上发表的评论。这类评论必须指明受众：成员提及、`notify_only`、决策评论、`ask`（下一个行动的成员）或 `no_ask`。提及智能体或小队，或回复智能体的评论，也算有受众。只读取这些类型化字段和链接，不读取评论文本。`warn` 记录一次命中并正常发布评论；`block` 记录命中并以 `422` 拒绝评论。聊天通道的运行只会警告。改回 `off` 即可还原，不涉及数据变更。

工作区设置 `waiting_on_guard`（默认 `off`，可选 `warn`、`block`）针对智能体把事项移到 `in_review`、`blocked` 或 `need_decision` 的操作。移动时必须用 `waiting_on`（`member:<id>` 或 `none`）说明下一个行动的人。如果该任务已在此事项上发布过决策请求，或带成员提及的评论，则无需 `waiting_on`。只读取类型化字段和结构化链接，不读取之前评论的文本。`warn` 记录一次命中并正常移动事项；`block` 记录命中并以 `422` 拒绝移动。聊天通道的运行只会警告。改回 `off` 即可还原，不涉及数据变更。

当产生 `block` 事件的运行结束后，服务器会向请求所指名的那一个人发送自动恢复通知：在一个事务中写入一条私信、一条议题评论和一个收件箱条目。通知引用已存储的请求并链接到议题，没有选项、建议或批准，因此永远不是决策请求。只有在存储的来源包含请求文本、恰好指名一位成员、且该成员仍在工作区时才会发送；否则该事件等待修复。在通知的评论线程中回复会将其标记为 `answered`。已离开工作区的成员无法再阅读或回复该通知。

无法作为通知发送的事件会改交给产生它的那次运行所属的智能体：每个恢复根只有一次修复运行，并经过常规的运行关卡（项目停止、运行预算、角色和审批关卡）启动。第一个 `block` 事件是根，修复运行产生的事件继承该根，因此修复永远不会再启动第二次修复。运行消息包含准确的 `multica decision request ... --recovers <event-id>` 命令，不含原文。运行被拒绝、智能体不可用、修复运行结束时没有匹配的请求，或修复运行又产生了新的请求，都会使该根失败。智能体是其负责人：议题上会有一条点名该智能体、不提及任何成员的系统评论，`multica decision brief` 会连同请求摘录一起列出该失败。聊天通道中的运行只产生 `warn` 事件，因此不会被修复。

守卫也覆盖智能体注册人可触发的唤醒。用 `--decision` 绑定、标记 `--purpose observe`，或限定为仅智能体；见[唤醒](/cli#wakeups)。

工作区设置 `long_thread_member_ask`（默认 `off`，可选 `warn`、`move`）针对智能体在长讨论串中提及成员的评论。`long_thread_member_ask_min`（3 到 100 的整数，默认 10）是该设置开始适用的讨论串大小（含根评论）。`move` 会把评论作为链接回原讨论串的新提问讨论串打开；`warn` 则原地发布并附带提示。该设置只决定评论的去向，从不拒绝评论。使用默认值时没有任何变化。每次命中会写入一条模式为 `move` 或 `warn` 的守卫事件，恢复和修复流程不会读取它。服务器会校验这两个值，不合法的值会被 `400` 拒绝。

工作区设置 `ask_loop_back`（默认 `off`，可选 `on`）会把成员在提问讨论串中的回答带回它所源自的讨论串。成员在提问讨论串中发表评论时，服务器会在源讨论串中添加一行：`<成员> answered in thread <提问讨论串 id>:`，后接前 280 个字符的引用，被截断时以 `…` 结尾。成员回答的决策卡片的提问位于提问讨论串时，这一行是 `<成员> decided: <选项> (thread <提问讨论串 id>).`。这一行不提及任何人，不会启动运行，也不改变源讨论串的解决状态。每条评论只写一行，编辑不会再写。源讨论串已被删除时不写任何内容。回传失败不会让成员的评论失败。使用默认值时没有任何变化。服务器会校验该值，不合法的值会被 `400` 拒绝。

### 工具守卫

**设置 → Guard** 列出工作区的工具守卫插件，以及每个插件在过去 7 天里做了什么。每个插件显示被修正、被拒绝或出错的调用数量、按天统计的命中图表，以及最近的判定。数字与 `multica guard stats`、`multica guard log` 来自同一批记录。日期按你的查看时区计算。

工作区所有者可在此编辑工作区级规则：**用通行密钥编辑** 可更改其动作和消息，所有者用通行密钥对这次确切的更改签名。签名指明编辑所基于的策略版本。若期间已有其他更改，则不会保存，页面会显示两个版本，并提供 **重新应用**（用新的通行密钥把你的更改放到新版本上）、**重新加载当前版本** 和 **放弃**。成员看到的是只读页面。属于组织、仓库或路径层的规则用 CLI 编辑：由智能体用 `multica guard plugin set` 创建变更，再由人在决策卡片上用通行密钥批准。没有已保存的策略时，页面显示内置默认值。

### 决策界面

工作区设置 `decision_screen`(默认 `off`,可设为 `on`)会隐藏承载智能体决策请求的聊天通道。设为 `on` 时,议题智能体向成员发出的请求会进入一个隐藏的后备通道,即使该成员与此智能体有可见私信也一样;该私信中不会发布任何内容。该通道不会出现在成员的聊天列表、未读数、角标或“Needs you”列表中,成员也无法向其中发送消息(`409`)。请求本身仍会打开同样的决策卡片。对这类智能体,服务器会忽略 `session_id` 和 `new_dm`,并在响应中附加一条提示。从私信中发起请求的智能体仍在该私信中请求。要还原,请将其设回 `off`:不会再创建新通道,已有通道仍保持隐藏。

### 委托的受管写入

工作区设置 `delegated_governed_writes` 决定哪些智能体可以写入受管字段，以及每次写入是否仍需要人来决定。它位于工作区设置的 **委托的受管写入** 下。

- **谁可以编辑：** `owner` 和 `admin`。`member` 以只读方式查看同一张表，会看到锁定提示，没有编辑按钮。
- **允许的智能体：** 可以写入的智能体。已归档的智能体不能添加。
- **允许的字段：** 可从 `workflow.steps`、`workflow.instructions`、`workspace.context`、`squad.instructions`、`agent.instructions`、`project.description`、`workflow.budget`、`issue.workflow` 中选择。未勾选的字段对所有智能体保持只读。
- **需要人工决定：** 默认开启。开启时，被允许的智能体会发起决策请求，而不是直接写入。关闭后，被允许的智能体直接写入，因此保存前会先要求你确认。

保存失败时，未保存的编辑会保留，你输入的内容不会丢失。

## 切换和离开

一个账号可以加入多个工作区。切换工作区只换了你正在看的范围，数据不会移动。

离开工作区后，需要重新接受邀请才能回来。离开会同时停用你拥有的运行时、归档绑定在其上的智能体，并取消它们未结束的运行。

最后一名 `owner` 不能离开，需要先把另一位成员提升为 `owner`。

## 删除工作区

只有 `owner` 可以删除工作区。删除会永久移除其中的全部工作、成员、智能体配置和执行记录，无法恢复。只是暂时不参与的话，离开就够了。
