GitHub を接続すると、Multica はタスク番号を使って pull request を自動的に紐づけます。タスクの詳細画面から、PR の状態、変更規模、CI の結果、マージ競合を直接確認できます。

GitHub 連携が読み取るのは、インストール時に許可されたリポジトリだけです。コード、コメント、status check を書き込むことはありません。

セルフホスト版 Multica では、セルフホストの Forgejo、Gitea、GitLab インスタンスも同時に接続できます。PR の自動紐づけ、マージ時のステータス変更、CI 表示を同じように利用できます。**設定 → コード**から設定してください。詳しくは[セルフホスト Git ホスティング](/vcs-integration)を参照してください。Multica Cloud にはこの項目はありません。

## GitHub を接続する

ワークスペースの owner または admin が接続できます。

<Steps>
<Step>
**設定 → コード** を開きます。
</Step>
<Step>
**GitHub** の行で **GitHub を接続**をクリックします。
</Step>
<Step>
GitHub でアカウントまたは organization を選び、すべてのリポジトリか指定したリポジトリを許可します。
</Step>
<Step>
インストールが完了したら Multica に戻ります。
</Step>
</Steps>

接続状態は同じページに表示されます。通常のメンバーは状態を確認できますが、接続、切断、スイッチの変更はできません。

<Callout type="info">
**GitHub 接続**は、Multica がどのリポジトリから PR イベントを受け取るかを決めます。**コードリポジトリ**設定は、エージェントが作業を実行するときに選べるリポジトリを決めます。用途が異なるため、それぞれ設定する必要があります。
</Callout>

## 機能スイッチ

**設定 → コード** の **プルリクエストとタスク** には次の設定があります。GitHub の行の **⋯** メニューで **GitHub 機能を一時停止** すると、下の 3 項目は機能しなくなりますが、GitHub App の接続は解除されません。

| 設定 | 機能 |
|---|---|
| PR サイドバー | 紐づいた pull request をタスクの詳細画面に表示します。 |
| Co-authored-by | エージェントが作成する commit に `Co-authored-by: multica-agent <github@multica.ai>` を追加します。 |
| PR の自動紐づけ | ブランチ名かタイトルにタスク番号を含む PR、または本文で closing keyword の直後にタスク番号を置いた PR を、そのタスクに紐づけます。 |
| PR マージ後のタスクのステータス | タスクに紐づく PR がすべてマージされたとき、タスクをあるステータス（既定は `Done`）に変更するか、変更しないかを選びます。[PR マージ後のステータス変更](#pr-マージ後のステータス変更)を参照してください。 |
| PR カード → CI とマージ可否 | 紐づいた各 PR について、Multica は App として GitHub API からスナップショットを取得し、CI の状態とマージ可否をカードに表示します。[タスクから PR を確認する](#タスクから-pr-を確認する)を参照してください。 |

## PR をタスクに紐づける

最も簡単な方法は、タスク番号をブランチ名または PR タイトルへ入れることです。タスクが `MUL-123` の場合:

```text
mul-123-fix-login-redirect
```

```text
MUL-123 ログイン後のリダイレクトを修正
```

Multica は大文字と小文字を区別せず、現在のワークスペースのタスク接頭辞だけを照合します。1 つの PR を複数のタスクに紐づけることもできます。

タスク番号を PR 本文だけに書く場合は、GitHub の closing keyword を必ず使ってください。

```text
Closes MUL-123
Fixes MUL-123
Resolves MUL-123
```

本文に `Related to MUL-123` のような通常の参照を書いただけでは、そのタスクへまったく紐づきません。Commit message と PR コメントも紐づけの対象外です。

手動で紐づけることもできます。タスクの **Pull requests** セクションで **+** をクリックし、PR の URL を貼り付けます。PR をタスクから外すには、その行の **⋯** メニューから **タスクから外す** を選びます。以後、Multica がタイトルやブランチから再び紐づけることはありません。

## タスクから PR を確認する

紐づけが完了すると、PR がタスク詳細の **Pull requests** セクションに表示されます。各項目には次の情報が含まれます。

- リポジトリ、番号、タイトル、作成者
- `Open`、`Draft`、`Merged`、`Closed` の状態
- 追加行数、削除行数、変更ファイル数
- CI の状態: すべて成功した check の件数、失敗した check の名前、実行中の check の件数。check が 1 つも設定されていない PR ではこの項目を表示せず、「check なし」を成功として扱いません。
- マージ可能性: GitHub がマージ状態を clean と報告した場合だけマージ可能。ほかに競合、blocked、behind を表示します。

CI の状態とマージ可能性は、Multica が GitHub API から取得したスナップショットで、互いに独立しています。マージ済みまたはクローズ済みの PR では、この 2 項目を表示しません。GitHub が一時的に利用できない場合、カードは前回のスナップショットを残し、古い情報として表示します。

リストの下には、次に何が起きるかを 1 行で表示します。たとえば「#19 がマージされると 完了 に変更」や、マージされずにクローズされた PR です。ワークスペースが「変更しない」に設定されている場合や、タスクがすでに変更先のステータスにある場合は表示されません。

項目をクリックすると GitHub の PR が開きます。**PR サイドバー**を無効にしてもこのセクションが非表示になるだけで、接続は解除されません。

## PR マージ後のステータス変更

PR がマージされても、必ずしもタスクが完了するわけではありません。そのため、マージ後に何をするかはワークスペースが決めます: **設定 → コード → PR マージ後のタスクのステータス**。`Done`（新しいワークスペースの既定値）、ほかの「開始済み」「完了」カテゴリーのステータス（「回帰テスト待ち」のようなカスタムステータスも可）、または **変更しない** を選べます。この設定ができる前からあるワークスペースは、これまでの挙動を保ちます。マージしても必ずタスクが完了していたわけではない場合、初期値は **変更しない** です。

次の条件をすべて満たすと、タスクは選んだステータスに変わります。

1. タスクに紐づく PR がすべて `Merged` である。`Open` や `Draft` の PR が残っているとタスクは待機を続けます。マージされずにクローズされた PR も、タスクから外すまで同様です。
2. タスクが `done` または `cancelled` ではなく、Triage 中でもなく、すでに変更先のステータスでもなく、このタスクだけ変更をオフにしていない（**Pull requests → ⋯ → PR マージ後もステータスを変えない**）。

<PrLinkDemo />

PR の紐づけ方は結果に影響しません。タイトル、ブランチ名、本文の `Closes MUL-123` はどれも紐づけるだけです。PR がタスクの一部しか納品しない場合や、マージ後にリリースや確認が必要な場合は、そのタスクの **Pull requests** メニューからステータスを変えないように設定します。

判定は PR イベントがタスクに関わったときだけ行います。紐づいた PR のマージ、紐づけの追加、紐づけの解除です。タスクを再度開いても元には戻らず、次に紐づいた PR がマージされたときに変更されます。設定を変えても、以前にマージされたタスクには影響しません。

状態の変更は関連する PR を示したシステム操作としてタイムラインに記録され、そのタスクを購読しているメンバーへ通知されます。この設定は[セルフホスト Git ホスティング](/vcs-integration)を含むすべてのコードホストで共通です。

## 複数のワークスペース

同じ GitHub App installation を複数の Multica ワークスペースへ接続できます。GitHub イベントは各ワークスペースにそれぞれ送られ、各ワークスペースのタスク接頭辞に従って照合されます。

たとえば、1 つの PR が `MUL-1` と `ENG-2` の両方を参照している場合、異なる接頭辞を持つ 2 つのワークスペースでそれぞれ紐づけられます。ワークスペース間で相手のタスクが見えることはありません。

同じ番号が接続中の複数のワークスペースでタスクに一致する場合（接頭辞が同じときに起こり得ます）、Multica はどのワークスペースでも自動では紐づけません。関係のないタスクがマージで完了しないようにするためです。正しいワークスペースで手動で紐づけてください。

## 接続を解除する

**設定 → コード** の GitHub の行で **⋯** メニューから**接続解除**を選ぶと、現在の Multica ワークスペースと installation の関係だけが削除されます。GitHub から App がアンインストールされることはありません。既存の PR 記録は保持されますが、新しいイベントはこのワークスペースに届かなくなります。

GitHub 側のリポジトリアクセスを取り消す場合は、個人または organization の GitHub App installations ページで App をアンインストールするか、リポジトリの範囲を変更してください。App をアンインストールすると、その installation に接続していたすべての Multica ワークスペースがイベントを受信しなくなります。

## GitHub Actions の実行を待つ

ウェイクアップは、環境の承認ゲートで止まるデプロイなど、GitHub Actions の実行をポーリングなしで待てます。その実行に PR のリンクは不要です。

```bash
multica issue wakeup create ISSUE --until-gh-run OWNER/REPO:RUN_ID --until-gh-run-state completed --expires-in 3h --on-timeout wake --instruction-file ./instruction.md
```

`--until-gh-run` は次の 3 つの形式のいずれかを受け付けます。

| 形式 | 選択される実行 |
|---|---|
| `owner/repo:RUN_ID` | その ID の実行 |
| `owner/repo:WORKFLOW_FILE@SHA` | そのワークフローファイルの実行のうち、自身の `head_sha` が 40 文字の完全な SHA と一致するもの |
| `https://github.com/owner/repo/actions/runs/RUN_ID` | その ID の実行 |

`--until-gh-run-state` は `completed`（デフォルト）または `waiting` です。`waiting` は、実行内のジョブが環境ゲートで待機を始めるたびに発火します。人にゲートの承認を依頼する前に、facts の `waiting_now` を確認してください。ゲートがすでに閉じている場合は `false` です。`SHA` 形式は実行自身のコミットに一致します。別のコミットをデプロイする実行（例: `cd-deploy.yml`）には実行 ID が必要です。

App は、このワークスペースのリポジトリ所有者にインストールされている必要があります。また、**Workflow run** と **Workflow job** のイベントを購読している必要があり、これらには **Actions: read** 権限が必要です。レコードは 30 日間保持されます。

### 制限: 観測したイベントのみ

ルールは、App が購読した後に Multica が受信した webhook イベントで満たされます。実行の現在の状態を問い合わせるものではありません。

- GitHub は失敗した配信を自動では再配信しません。`completed` イベントが失われると、保存された実行は `in_progress` のままになります。
- App が購読する前に始まった実行やゲートは見えません。
- 復旧するには、App の **Advanced → Recent Deliveries** ページでイベントを手動で再配信します。
- 必ず `--expires-in` と `--on-timeout wake` を一緒に設定してください。期限時のデフォルトは `end` で、実行は開始されません。

### レシピ: マージ後にデプロイを待つ

1. マージコミット `M` の認定実行を待ちます。
   `--until-gh-run cheese-work/multica:cd-qualification.yml@M --until-gh-run-state completed --expires-in 3h --on-timeout wake`
2. 起こされた実行がデプロイ実行の ID を探します: `gh run list -R cheese-work/multica --workflow cd-deploy.yml --json databaseId,displayTitle`。タイトルに `M` を含む実行を選びます。
3. 承認ゲートを待ちます: `--until-gh-run cheese-work/multica:RUN_ID --until-gh-run-state waiting --expires-in 6h --on-timeout wake`
4. 承認後、同じルールと `--until-gh-run-state completed` で完了を待ちます。

## セルフホスト設定

Multica Cloud ではこのセクションの作業は不要です。セルフホスト環境では、自分の GitHub App を先に作成します。

<Steps>
<Step>

### GitHub App を作成する [#1-github-app-を作成する]

GitHub の **Developer settings → GitHub Apps** で App を作成し、次の値を入力します。

| フィールド | 値 |
|---|---|
| Homepage URL | Multica のフロントエンド URL。例: `https://multica.example.com` |
| Callback URL | `https://<api-host>/api/github/setup`。Setup URL と同じエンドポイント |
| Request user authorization (OAuth) during installation | 有効にする |
| Setup URL | `https://<api-host>/api/github/setup`。**Redirect on update** を有効にする |
| Webhook URL | `https://<api-host>/api/webhooks/github` |
| Webhook secret | 長期保管するランダムな文字列 |

Repository permissions:

| 権限 | レベル |
|---|---|
| Metadata | Read-only |
| Pull requests | Read-only |
| Members | Read-only。接続ユーザーが organization の active admin であることを確認するために必要 |
| Checks | Read-only。CI の状態表示に使用 |
| Commit statuses | Read-only。legacy status 形式の CI 集計に使用 |

次のイベントを購読します。

- **Pull request**
- **Check suite**、**Check run**、**Status**。CI とマージ可能性を更新するために使用します。

PR スナップショットは Pull requests、Checks、Commit statuses の REST API から取得します。Contents 権限は不要です。

<Callout type="warning">
必要なのは **Webhook secret** であり、OAuth Client secret ではありません。GitHub と Multica に入力した Webhook secret が異なる場合、GitHub delivery は `401 invalid signature` を返します。
</Callout>

</Step>
<Step>

### 環境変数を設定する [#2-環境変数を設定する]

App の公開 URL から slug を確認します。たとえば `https://github.com/apps/multica-acme` の slug は `multica-acme` です。

```dotenv
GITHUB_APP_SLUG=multica-acme
GITHUB_WEBHOOK_SECRET=<webhook secret entered when creating the App>
GITHUB_APP_CLIENT_ID=<the App's Client ID>
GITHUB_APP_CLIENT_SECRET=<a client secret generated on the App's settings page>
FRONTEND_ORIGIN=https://multica.example.com
```

次の App 資格情報により、Multica は紐づけ前に installation を App として正式に確認できます。また、リポジトリ選択と CI・マージ可能性のスナップショットにも使用します。

```dotenv
GITHUB_APP_ID=<numeric GitHub App ID>
GITHUB_APP_PRIVATE_KEY=<complete PEM private key, including BEGIN/END lines and newlines>
```

秘密鍵は GitHub App の **Private keys → Generate a private key** から生成します。これらの App 資格情報がなくても、既存の installation は署名付き webhook を受信でき、PR のミラー、タスクの自動紐づけ、マージ時のステータス変更は動作します。一方、新しい binding の作成、リポジトリの参照、CI やマージ可能性の更新には資格情報が必要なため、設定するまで PR カードに CI やマージ状態は表示されません。

接続ボタンには GitHub の 6 つの値がすべて必要です。新規接続では、Multica が GitHub のユーザー認可 code を交換し、App として installation を解決したうえで、個人アカウントの ID と login の完全一致、または organization の active admin membership を要求します。ユーザーの installation 一覧に表示されるだけでは organization の権限証明になりません。検証エラーはすべて接続を拒否し、一時的な user token は確認後に失効させます。

既存の App に Members 権限を追加する場合、新しいワークスペースへ接続する前に対象 organization ごとに権限変更を承認してください。

</Step>
<Step>

### 3. 再起動して接続する

この変更にデータベースマイグレーションは不要です。新しい環境変数で API サービスを再起動し、既存 installation の権限更新が要求された場合は承認してから、**設定 → コード** で接続します。同じワークスペースに installation を追加するには **Add account or organization** を使います。

</Step>
</Steps>

## よくある問題

- **接続ボタンを使用できない**: `GITHUB_APP_SLUG`、`GITHUB_WEBHOOK_SECRET`、`GITHUB_APP_CLIENT_ID`、`GITHUB_APP_CLIENT_SECRET`、`GITHUB_APP_ID`、`GITHUB_APP_PRIVATE_KEY` が API プロセスに設定されていることを確認します。
- **インストール直後に接続が失敗する**: **Request user authorization (OAuth) during installation** を有効にし、callback URL と setup URL の両方を `/api/github/setup` に設定して、Members read-only を付与します。接続ユーザーは個人アカウントの所有者、または organization の active admin である必要があります。
- **Webhook が 401 を返す**: GitHub App と API が同じ Webhook secret を使っていることを確認し、GitHub の **Recent Deliveries** から再配信します。
- **PR が紐づかない**: リポジトリが App の許可範囲にあること、PR の自動紐づけが有効であること、番号が現在のワークスペースのものであること、誰かがタスクから外していないかを確認します。
- **本文に番号を書いても紐づかない**: `Closes MUL-123` を使うか、番号をブランチ名または PR タイトルに入れるか、手動で紐づけます。
- **CI の状態がない**: `GITHUB_APP_ID` と `GITHUB_APP_PRIVATE_KEY` が設定済みで、App に Pull requests、Checks、Commit statuses の read-only 権限があり、関連イベントを購読していることを確認します。Contents 権限は不要です。インストール済み App に権限を追加した場合は、各 installation の所有者が GitHub 上で承認するまで有効になりません。
- **PR のマージ後もタスクのステータスが変わらない**: タスクの **Pull requests** リストの下にある説明を確認します。まだマージされていない PR やマージされずにクローズされた PR、またはこのタスクが PR マージでステータスを変えない設定であることが表示されます。説明がない場合は、ワークスペースが **変更しない** に設定されているか、タスクがすでに変更先のステータスです。
