ワークスペースは Multica の最上位の境界です。メンバー、タスク、プロジェクト、エージェント、スキル、実行履歴はすべていずれか 1 つのワークスペースに属し、別のワークスペースからは見えません。

## ワークスペースの構成

| 分類 | 内容 |
|---|---|
| **作業** | タスク、プロジェクト、コメント、添付ファイル、実行履歴 |
| **チーム** | メンバー、ロール、招待 |
| **エージェント** | エージェント設定、スキル、ランタイム、自動化 |
| **共有設定** | コンテキスト、ラベル、[カスタムプロパティ](/issues#カスタムプロパティ)、連携 |

**コンテキスト**はワークスペース内のすべてのエージェントに渡されます。チームの背景、プロダクトの約束事、長期的に有効な要件を書く場所です。一回限りの要件は、対応するタスクに書いてください。

## ワークスペースの作成

作成時に入力するのは 3 つです。

- **名前**: メンバーに表示されます。後から変更できます。
- **ワークスペース URL**: アドレスに使われる slug です。`multica.ai/my-team` の `my-team` にあたります。小文字、数字、ハイフンのみが使え、既存のワークスペースや予約済みアドレスとは重複できず、作成後は変更できません。
- **タスク接頭辞**: ワークスペース URL から自動で入力され、作成前に変更できます。接頭辞が `MUL` の場合、タスク番号は `MUL-1`、`MUL-2` と表示され、ワークスペース内で独立して増えていきます。大文字と数字のみ、最大 10 文字で、あとから設定でも変更できます。

作成者は自動的に `owner` になります。

## 設定の変更

`owner` と `admin` は名前、アイコン、説明、コンテキスト、タスク接頭辞を変更できます。`member` は閲覧のみです。

![ワークスペース設定：名前、コンテキスト、slug、タスク接頭辞と危険区域](/images/docs/workspace-settings.webp)

<Callout type="warning">
タスク接頭辞を変更すると、すべてのタスクがただちに新しい番号に切り替わります（`MUL-5` が `NEW-5` になります）。ただし、PR、ブランチ名、チャット履歴にある古い番号は更新されません。
</Callout>

### 自動クローズ

ワークスペース設定 `auto_close` は、子タスクが `agent_accepted` または `merged` ステップに入り、やることが残っていないときの動作を決めます。ステップのエージェントはクローズするだけなので、サーバーがステップの `agent_done` エッジをたどって自分で `done` に移せます。

| 値 | 効果 |
| --- | --- |
| `off` | 何も変わりません。ステップのエージェントが実行されます。 |
| `warn`（デフォルト） | ステップのエージェントはこれまでどおり実行されます。入るたびに、満たされたチェックと続いた実行を示す `auto_close_would_close` アクティビティ行が 1 件記録されます。 |
| `block` | サーバーがタスクを `done` に移し、読み取ったチェックを示す `auto_closed` アクティビティ行を記録し、実行は開始しません。 |

クローズにはすべてのチェックが必要です。1 つでも満たされない、または読み取れない場合は、ステップのエージェントがこれまでどおり実行されます。

- タスクに親があること。ルートタスクは閉じません。
- 最新のレビュー判定が P0 / P1 の指摘を含まない PASS で、現在の候補に対するものであること。PR がある場合は、リンクされたすべての PR が PASS の示す head でマージ済みであること。PR がない場合、候補はタスクのテキストです。PASS の後に添付ファイル、説明の変更、コメント（レビュアー自身のものを除く）、CHANGES 判定、古い・置き換え済みの印、`in_progress` への戻りがないこと。
- 未完了の子タスク、未解決の決定リクエストがなく、タスクがステップに入った時点で有効だったウェイクアップ（タスク自身のマージ監視、`pr.merged` エッジを除く）がないこと。
- 説明に `Blockers: Cheese stop` の行がなく、親の `delivery_stop` メタデータが `stopped` でないこと。
- タスクのメタデータ `post_close_work` が `none` であること。作成者が書きます: `multica issue metadata set <issue> --key post_close_work --value none --type string`。残る作業の短い説明など、それ以外の値の場合は実行が残ります。
- ワークフローにそのステップから `done` への `agent_done` または `pr.merged` エッジがあること。
- `merged` のみ: リンクされたすべての PR が、PASS の示す head でリポジトリのデフォルトブランチにマージ済みであること。別のブランチ（スタックの層）にマージされた PR や、ベースまたはデフォルトブランチが配信に含まれていなかった PR がある場合は、実行が残ります。

PASS の示す head の PR がまだオープンでも、ステップに `done` への `pr.merged` エッジとタスク自身の監視がある場合は、実行は残りません。サーバーは実行を開始せず、`auto_close_pending_merge` アクティビティ行を 1 件記録します。その後マージでタスクが実行なしで閉じます。 マージ時にサーバーはすべての条件を再確認します。満たさない条件（PASS のない新しい head、新たな有効なウェイクアップなど）があれば、閉じずにステップの実行を開始し、監視を外します。

`warn` と `block` では、拒否された完了は `auto_close_skipped` アクティビティ行を 1 件記録します。行には最初に成立しなかった述語（`first_failure`）と、述語が読んだ入力（モードとその由来（ワークスペースまたはステップ）、課題の `post_close_work`、done エッジ、PASS 行とそれが指す head、リンクされた PR、未完了の子課題と決定、ウェイクアップ数、親の `delivery_stop`、確認時刻）が残ります。`multica issue close-check <issue>` は課題の現在の状態で全述語を表示し、`multica issue close-check <issue> --activity <row>` は保存された入力に同じ述語を実行します。課題がその後変わっても、サーバーがそのとき出した答えが返ります。どちらも読み取り専用です。

モードは `multica workspace update --auto-close-mode off|warn|block` で設定します。読み取れない値は `off` として扱われます。

### ブロック時の実行スキップ

ワークスペース設定 `blocked_run_skip` は、タスクが `blocked` に入ったときにブロックステップの実行を開始するかどうかを決めます。タスクが待っている対象を示していて、ステップの担当者がすでに作業を続けるウェイクアップを持っている場合に限り、サーバーはこの実行をスキップします。

| 値 | 動作 |
| --- | --- |
| `off` | 何も変わりません。ブロックステップのエージェントが入った時点で実行されます。 |
| `warn`（デフォルト） | これまでどおり実行が始まります。スキップされるはずだった入り方ごとに、続いた実行を示す `blocked_entry_would_skip` アクティビティ行が 1 件記録されます。 |
| `block` | サーバーは実行を開始せず、`blocked_entry_linked` アクティビティ行を記録し、ウェイクアップを有効のままにします。 |

次のすべてを満たす場合のみ実行をスキップします。1 つでも満たさない、または読み取れない場合は、これまでどおり実行が始まります。

- タスクのメタデータ `blocked_on` が設定されている（`multica issue status <id> blocked --blocked-on <ref>`）。
- ブロックステップの担当者が、このタスクに同じ参照を待つ有効な条件付きウェイクアップを持っている。フラグ、対象、状態・ステージ・種類がすべて同じであること。時間ウェイクアップ、別の条件、別のエージェントのウェイクアップは対象外です。
- そのウェイクアップに `last_error` がなく、7 日以内に終了し、`--on-timeout wake` を使っている。
- 実行が受け付けられる：タスクに実行予算が残っており、エージェントが一時停止していない。

リンクされたウェイクアップが後で無効化・削除された、`last_error` が付いた、実行なしで終了した（期限切れまたはガードに拒否された）、または `blocked_on` と一致しなくなった場合、サーバーはブロックステップの実行を開始し、`blocked_entry_rearmed` アクティビティ行を記録します。実行予算が尽きている、またはエージェントが一時停止している場合は、その実行も拒否され、行にその旨が記録されます。

### ウェイクアップのライブ参加

ワークスペース設定 `wakeup_live_join` は、条件ウェイクアップが発火したときに、そのエージェントが同じ課題ですでに実行中の場合の動作を決めます。2つ目の実行を開始する代わりに、サーバーは発火をウェイクアップ項目として実行中の実行へ配信できます。

| 値 | 効果 |
| --- | --- |
| `off` | 何も変わりません。発火は独自の実行を開始します。 |
| `warn`（デフォルト） | 発火は従来どおり実行を開始します。参加できたはずの発火ごとに、実行中の実行を示す `would_join_live` アクティビティ行も1件記録されます。 |
| `block` | サーバーは発火を実行中の実行へ配信し、実行をキューに入れず、ウェイクアップの `last_error` を `Delivering into running run <id>; inputs retained` にします。 |

次の条件がすべて満たされた場合にのみ、発火は参加します。1つでも満たされないか読み取れない場合、発火は従来どおり実行を開始します。

- 発火のすべての受領が条件の受領（`condition.met`）です。時刻、コメント、リアクション、手動の発火は参加しません。
- エージェントがそのウェイクアップを作成しています。決定に紐づかず、システムルールでもカスタムルールのインスタンスでも、マージ適格性ルールでもなく、一時停止中でもありません。
- 対象エージェントがその課題で実行中の実行をちょうど1つ持ち、待機中の実行がなく、その実行がウェイクアップと同じユーザーのために動いています。その実行は別のルールの分離された発火を持っていません。
- 実行中の実行がウェイクアップ項目を受け付け、発火の受領のどれもまだ項目に入っていません。
- スキップルール（たとえば一時停止中エージェントのスキップ）がすでに発火を消費していません。
- 項目をキューに入れる時点で、その実行がまだ実行中です。

受領は項目が決着するまで保留のままで、`once` のウェイクアップもそれまで有効のままです。実行が `completed` で終わると、発火は `joined_live` として決着します。実行がキャンセルまたは失敗した場合、または項目が拒否されたか一度も取得されなかった場合、ウェイクアップは独自の実行を1回開始し、`wakeup_join_fallback` アクティビティ行を記録します。同じ実行内の型付き PR 項目は自身の項目で決着し、条件の受領を消費することはありません。

モードは `multica workspace update --wakeup-live-join-mode off|warn|block` で設定します。読み取れない値は `off` として扱われます。

### 実行数の上限

2 つのワークスペース設定が、タスクが実行数の上限を使い切ったときの動作を決めます。どちらも `{"mode": "off" | "warn" | "block"}` で、既定値は現在の動作である `block` です。

| 設定 | 制御する上限 |
| --- | --- |
| `run_budget` | タスクのワークフローによるタスクごとの実行予算（`max_runs_per_issue`）。 |
| `run_guard` | 週次の実行ガード：タスクが 7 日間に開始する実行数。 |

| 値 | 動作 |
| --- | --- |
| `block` | 次の派生実行は拒否され、オーナーにカードが届きます。 |
| `warn` | 実行は数えられ、超過はブリーフと `multica issue budget get`（`state: warn`）に表示されます。実行は拒否されず、タスクもブロックされず、カードも開きません。 |
| `off` | ブロック、警告、カードのいずれもありません。 |

ループブレーカー（`MULTICA_LOOP_BREAKER_MAX_RUNS`）は変わりません。モードは `multica workspace update --run-budget-mode` または `--run-guard-mode` で設定します。エージェントは `workspace.settings` カードで `run_budget` または `run_guard` を提案します。

### 依頼ガード

ワークスペース設定 `ask_guard_mode` は、エージェントの操作が決定リクエストを開かずに人へ作業を求めたときの動作を決めます。

| 値 | 動作 |
| --- | --- |
| `off`（既定） | ガードは何もしません。 |
| `warn` | ガードはイベントとメトリクスを記録します。操作はそのまま進みます。 |
| `block` | ガードは先にイベントを記録し、その後 `422` で操作を拒否します。復旧作業になるのは `block` のイベントだけです。 |

### マージキューの設定

3つのワークスペース設定でマージキューを構成します。書き込めるのはオーナーだけで、すべての書き込み経路（`multica workspace update` のフラグ、設定の保存、`config propose` アクション）が同じバリデーターを通ります。

| 設定 | 値 |
| --- | --- |
| `merge_queue_dequeue_routing` | `off`（デフォルト）または `warn`。強制機能が提供されるまで、`block` は `routing-not-available` で拒否されます。 |
| `merge_queue_actor_bindings` | `{"agents": [...], "people": [...]}`。両方のリストにある GitHub ログインは拒否されます。 |
| `merge_queue_watch_issue` | マージキューのイベントを受け取る課題。空も可。 |

### オートパイロット割り当てガード

ワークスペース設定 `autopilot_assign_gate` は、オートパイロットを名指しする issue（その id が "autopilot" という語の近くにある）をエージェントまたはスクワッドに割り当てたとき、run が代理する人がそのオートパイロットに書き込めない（作成者でも、ワークスペース管理者でも、許可されたコラボレーターでもない）場合の動作を決めます。

| 値 | 動作 |
| --- | --- |
| `block`（既定） | 作成または更新は `403` とコード `autopilot_assign_no_write` で拒否されます。 |
| `warn` | サーバーは警告を記録します。割り当てはそのまま進みます。 |
| `off` | ガードは何もしません。 |

各イベントは作成時のモードを保持するため、`warn` から `block` に切り替えても以前のイベントは復旧作業になりません。イベントを書き込めない場合、操作は `503` と `Retry-After` ヘッダーで失敗し、何も書き込まれません。

ワークスペース設定 `reversible_ask_guard`（既定は `off`、`warn`、`block`）は、クラスが `reversible` のエージェントによる通常の決定リクエストを対象にします。これは、エージェントが自分で判断して実行してよい作業について、人に承認を求めるものです。`warn` はログに記録し、`block` は `422` で拒否します。アクション、提案、バッチのリクエストは対象外です。元に戻すには `off` に設定します。データは変わりません。同じ設定は、`blocked` または `need_decision` のイシューで、メンバーのコメントへのエージェントの通常の返信も対象にします。この返信は決定リクエストなしでその人に問いかけられます。`warn` はログに記録し、`block` は `422` で拒否します。トップレベルのコメント、エージェントへの返信、エージェントやスクワッドへのメンションを含むコメント、`--notify-only` 付きのコメント、決定リクエストは対象外です。

ワークスペース設定 `owner_script_guard`（`off`、`warn`、`block`。未設定のときは `warn`）は、エージェントの決定リクエスト、アクションリクエスト、`multica decision ask` のカードを対象にします。オーナーはシェルを読まないため、人にコマンドの実行を求めるカードは、リクエスト自体の欠陥です。8 つのルール（R1〜R8、ルールセットのバージョン 1）がカードの文面とステップを読みます。シェルのコードフェンス、フェンスやインラインコード内のコマンド、`human_steps` のコマンド、スクリプトの添付ファイル、そしてコマンドの隣や、検出済みメッセージの直後にある「run」「paste」などの実行の合図が対象です。`warn` はカードを届けて検出を記録します。`block` は `422` で拒否し、該当したルールとフィールドを示し、`multica config propose`、`multica decision propose <type>`、またはボットの権限の依頼を案内します。`off` は何も確認しません。確認ごとにイベントを 1 件、つまり `owner_script_guard` のアクティビティ行を書きます。カードが届いたときはカードと同じトランザクションで、拒否したときは単独のコミットで書きます。イベントには ID、結果、`delivered`、`rule_hits`、コマンドの鍵付きハッシュ（`cmd_hmacs`）、`retry_of` が入り、メッセージ本文は入りません。イシューのタイムラインにはこれらの行は表示されません。元に戻すには `warn` または `off` に設定します。データは変わりません。

ワークスペース設定 `waiting_audience_guard`（既定は `off`、`warn`、`block`）は、`in_review`、`blocked`、`need_decision` のイシューに対するエージェントのコメントを対象にします。このコメントには宛先が必要です。メンバーへのメンション、`notify_only`、決定コメント、`ask`（次に動くメンバー）、`no_ask` のいずれかです。エージェントまたはスクワッドへのメンション、エージェントのコメントへの返信も宛先として扱われます。読み取るのはこれらの型付きフィールドとリンクだけで、コメント本文は読みません。`warn` はヒットを記録してコメントを投稿し、`block` はヒットを記録したうえでコメントを `422` で拒否します。チャットレーンの実行は警告のみです。`off` に戻せば元の動作に戻り、データは変更されません。

ワークスペース設定 `waiting_on_guard`（既定は `off`、`warn`、`block`）は、エージェントがイシューを `in_review`、`blocked`、`need_decision` に移すときを対象にします。移動では `waiting_on`（`member:<id>` または `none`）で次に動く人を示す必要があります。そのイシューで決定リクエストやメンバーへのメンション付きコメントをすでに投稿したタスクは、`waiting_on` が不要です。読み取るのは型付きフィールドと構造的なリンクだけで、以前のコメント本文は読みません。`warn` はヒットを記録してイシューを移動し、`block` はヒットを記録して移動を `422` で拒否します。チャットレーンの実行は警告のみです。`off` に戻せば元に戻り、データは変わりません。

`block` イベントを発生させた実行が終了すると、サーバーは依頼が指名するただ一人に自動復旧通知を送ります。DM メッセージ、課題コメント、受信トレイ項目を 1 つのトランザクションで書き込みます。通知は保存済みの依頼を引用し、課題へのリンクを含み、選択肢・推奨・承認を持たないため、決定リクエストにはなりません。送信されるのは、保存された元データに依頼テキストがあり、メンバーがちょうど 1 人指名され、そのメンバーがまだワークスペースにいる場合だけです。それ以外はイベントが修復待ちになります。通知のコメントスレッドで返信すると `answered` になります。ワークスペースを離れたメンバーは、通知を読むことも返信することもできません。

通知として送れないイベントは、代わりにそのイベントを生んだ実行のエージェントへ回ります。復旧ルートごとに修復実行は 1 回で、通常の実行ゲート（プロジェクト停止、実行予算、ロールと承認のゲート）を通して開始されます。最初の `block` イベントがルートで、修復実行が生んだイベントはそのルートを引き継ぐため、修復から 2 回目の修復が始まることはありません。実行メッセージには正確な `multica decision request ... --recovers <event-id>` コマンドが入り、元のテキストは入りません。実行が拒否された場合、エージェントが使えない場合、修復実行が対応するリクエストなしで終わった場合、修復実行が新たな依頼を生んだ場合は、そのルートが失敗になります。エージェントが担当者で、課題には担当エージェントを示しメンバーにはメンションしないシステムコメントが 1 件付き、`multica decision brief` が依頼の抜粋とともにその失敗を一覧します。チャットレーンの実行は `warn` イベントしか生まないため、修復されません。

ガードは、エージェントが人の起動できるウェイクアップを登録する操作も対象にします。`--decision` で結び付ける、`--purpose observe` を付ける、またはエージェントだけに限定してください。[ウェイクアップ](/cli#wakeups)を参照。

ワークスペース設定 `long_thread_member_ask`（既定は `off`、`warn`、`move`）は、長いスレッドでメンバーをメンションするエージェントのコメントを対象にします。`long_thread_member_ask_min`（3〜100 の整数、既定 10）は、この設定が適用されるスレッドの大きさです（ルートを含む）。`move` はコメントを元のスレッドへのリンク付きの新しい質問スレッドとして開き、`warn` はヒント付きでその場に投稿します。この設定はコメントの行き先を変えるだけで、拒否はしません。既定値では何も変わりません。該当するたびに、モードが `move` または `warn` のガードイベントが 1 件書き込まれ、回復・修復の処理はこれを読みません。サーバーは両方の値を検証し、不正な値は `400` で拒否されます。

ワークスペース設定 `ask_loop_back`（既定は `off`、`on`）は、質問スレッドでのメンバーの回答を、そのスレッドを開いた元のスレッドへ戻します。メンバーが質問スレッドにコメントすると、サーバーは元のスレッドに `<メンバー> answered in thread <質問スレッドの id>:` の 1 行と、先頭 280 文字の引用を追加します。切り詰めた場合は `…` を付けます。質問が質問スレッドにある決定カードにメンバーが答えた場合、行は `<メンバー> decided: <選択肢> (thread <質問スレッドの id>).` になります。この行は誰もメンションせず、実行を開始せず、元のスレッドの解決状態も変えません。コメント 1 件につき 1 行で、編集では追加されません。元のスレッドが削除されている場合は何も追加しません。戻しに失敗しても、メンバーのコメントは失敗しません。既定値では何も変わりません。サーバーが値を検証し、不正な値は `400` で拒否されます。

### ツールガード

**設定 → Guard** には、ワークスペースのツールガードのプラグインと、過去 7 日間にそれぞれが行ったことが一覧表示されます。各プラグインについて、修正・拒否・エラーになった呼び出しの数、日ごとのヒット数のグラフ、直近の判定を確認できます。数値は `multica guard stats` と `multica guard log` と同じ行から取得します。日付は表示タイムゾーンに従います。

ワークスペースのオーナーは、ここでワークスペース単位のルールを編集できます。**パスキーで編集** でアクションとメッセージを変更し、オーナーがその変更そのものにパスキーで署名します。署名は、編集の元になったポリシーのバージョンを指します。先に別の変更が入っていた場合は何も保存されず、ページに両方のバージョンと **再適用**（新しいバージョンに新しいパスキーで変更を載せる）、**最新を読み込む**、**破棄** が表示されます。メンバーには読み取り専用で表示されます。組織・リポジトリ・パスの層に属するルールは CLI で編集します。エージェントが `multica guard plugin set` で変更を作成し、担当者が判断カードでパスキーを使って承認します。保存済みのポリシーがない場合は、組み込みのデフォルトが表示されます。

### 判断画面

ワークスペース設定 `decision_screen`(既定は `off`、`on` も可)は、エージェントの判断依頼を保持するチャットレーンを非表示にします。`on` のとき、Issue エージェントからメンバーへの依頼は、そのエージェントとの表示できる DM があっても、非表示のバッキングレーンに入ります。その DM には何も投稿されません。このレーンは、メンバーのチャット一覧、未読数、バッジ、「Needs you」一覧に表示されず、メンバーはそこへメッセージを送れません(`409`)。依頼自体は従来どおり同じ判断カードを開きます。これらのエージェントについて、サーバーは `session_id` と `new_dm` を無視し、レスポンスにヒントを 1 件追加します。DM から依頼するエージェントは、引き続きその DM に依頼します。元に戻すには `off` に戻します。新しいレーンは作られず、既存のレーンは非表示のままです。

### 委任されたガバナンス対象の書き込み

ワークスペース設定 `delegated_governed_writes` は、どのエージェントがガバナンス対象のフィールドに書き込めるか、また各書き込みに人の判断がなお必要かを決めます。ワークスペース設定の **委任されたガバナンス対象の書き込み** にあります。

- **編集できる人:** `owner` と `admin`。`member` は同じ表を読み取り専用で見られ、ロックの注記が表示され、編集ボタンはありません。
- **許可するエージェント:** 書き込みできるエージェント。アーカイブ済みのエージェントは追加できません。
- **許可するフィールド:** `workflow.steps`、`workflow.instructions`、`workspace.context`、`squad.instructions`、`agent.instructions`、`project.description`、`workflow.budget`、`issue.workflow` から選びます。チェックしないフィールドは、すべてのエージェントにとって読み取り専用のままです。
- **人の判断を必須にする:** 既定でオンです。オンの間、許可されたエージェントは書き込まず、判断リクエストを開きます。オフにすると許可されたエージェントが直接書き込むため、保存前に確認が求められます。

保存に失敗しても未保存の編集は保持されるので、入力した内容は失われません。

## 切り替えと退出

1 つのアカウントで複数のワークスペースに参加できます。切り替えで変わるのは表示している範囲だけで、データは移動しません。

ワークスペースを退出した後に戻るには、あらためて招待を受ける必要があります。退出すると同時に、自分が所有するランタイムは無効化され、それに紐づくエージェントはアーカイブされ、未完了の実行はキャンセルされます。

最後の `owner` は退出できません。先に別のメンバーを `owner` に昇格してください。

## ワークスペースの削除

ワークスペースを削除できるのは `owner` だけです。`owner` 本人が操作する必要があります。API はタスクトークンやクラウドノードの PAT による削除を拒否します。削除すると、その中の作業、メンバー、エージェント設定、実行履歴のすべてが完全に削除され、復元できません。しばらく参加しないだけなら、退出で十分です。
