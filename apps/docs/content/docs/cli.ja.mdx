Multica CLI は、ローカルのランタイムを接続する役割と、ターミナルからワークスペース、タスク、エージェント、オートパイロットを管理する役割の両方を担います。このページではよく使う操作の流れを紹介します。現在のバージョンがサポートするフラグは、常に各コマンド自身の `--help` が正です。

## インストール

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
```

Homebrew がインストールされていれば、次のコマンドでもインストールできます:

```bash
brew install multica-ai/tap/multica
```

</Tab>
<Tab value="Windows">

PowerShell で実行します:

```powershell
irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex
```

</Tab>
</Tabs>

インストールを確認します:

```bash
multica version
```

## 初回接続

接続先のサービスを選びます:

<Tabs items={["Multica Cloud", "セルフホストインスタンス"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="セルフホストインスタンス">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup` はサーバーアドレスを保存し、ブラウザを開いてサインインを完了し、デーモンを起動します。完了したら確認します:

```bash
multica auth status
multica daemon status
```

他の設定を上書きせずにサインインだけやり直したい場合は、`multica login` を実行します。ブラウザのない環境では、先に Web の設定で個人アクセストークンを作成しておき、次のコマンドで入力します:

```bash
multica login --token
```

このコマンドはターミナル上でトークンの貼り付けを促すため、完全な値が shell history に残りません。

## ワークスペースを選ぶ

ワークスペースを一覧し、デフォルトを切り替えます:

```bash
multica workspace list
multica workspace switch <slug>
```

以降のコマンドはこのワークスペースを使います。単発のコマンドでは `--workspace-id` で一時的に上書きでき、`MULTICA_WORKSPACE_ID` を設定することもできます。

メンバーを招待する:

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## よく使うタスク操作

```bash
# 表示と検索
multica issue list
multica issue get MUL-123
multica issue search "ログイン失敗"

# 作成と更新
multica issue create --title "ログイン失敗を修正"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# コメントと実行履歴
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "まず回帰テストを確認してください"
multica issue comment update <comment-id> --expected-revision 2 --content "回帰テストとリリースノートを確認してください"
multica issue runs MUL-123
```

長い説明やコメントは stdin から読み込むと、改行や引用符の扱いに悩まずに済みます:

```bash
multica issue create --title "アップグレードメモ" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

1 回の実行のメッセージを表示、実行を停止、または再試行する:

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123 --fresh
```

後続の実行をキューに入れる代わりに、進行中の実行にコメントを追加する（追加メッセージを受け付ける実行のみ。コメントで起動できるエージェントに限る）:

```bash
multica issue comment add MUL-123 --content-file note.md --steer <task-id>
multica issue comment add MUL-123 --content-file note.md --steer-active
```

エージェントのタスクから、メンバーへのメンション（`[@名前](mention://member/<id>)`）を含むコメントを送るには、決定リクエスト、`--decision-intent`・`--decision-record`・`--decision-veto` のコメント、または `--notify-only` のいずれかが必要です。返答が要らない通知には `--notify-only` を使います。待機を開始せず、決定リクエストとしても数えません。決定系のフラグとは併用できません。判定は文面ではなくメンションのリンクで行い、コード内のリンクも対象です。ワークスペース設定 `ask_guard_mode`（`off`、`warn`、`block`）で、拒否されるコメントを記録だけにするか 422 を返すかを決めます。チャットのタスクとタスクなしの呼び出しは記録のみです。メンバーへのメンションを追加する編集にも同じルールが適用されます。

```bash
multica issue comment add MUL-123 --content-file fyi.md --notify-only
```

`multica decision request` の `--recovers <event-id>` は、そのリクエストが ask ガードのイベント（拒否された操作や復旧通知に示されたもの）への回答であることを示します。サーバーは、イベントがこの課題にあり、リクエストが問い合わせる本人に対して発生したものである場合に限り、リクエストと同じトランザクションでそのイベントを解消します。ある人へのリクエストが別の人のイベントを解消することはなく、`--recovers` のないリクエストは何も解消しません。別の課題や別の人のイベントは `400` で拒否されます。1 つのリクエストが復旧できるイベントは 1 件だけです。同じリクエストの再試行が 2 件目のイベントを指定すると `400` で拒否されます。

同じプロジェクト・同じ親タスクの下に、タイトルが同じ（大文字小文字と余分な空白は区別しない）未完了のタスクがすでにあると、`issue create` は作成を拒否してそのタスクを示します。それでも作る場合は `--allow-duplicate` を付けます。あるタスクを別のタスクの重複にするには `multica issue status MUL-124 cancelled --duplicate-of MUL-123` を使います。

### タスクをルーティングする

`issue route` は、タスクのステータスを変更し、その理由を 1 回の呼び出しで記録します。ルーティングステップが、タスクの次の行き先を決めるときに使います。`--status`、`--reason`（1〜500 文字）、`--confidence`（0〜1）は必須です。

```bash
multica issue route MUL-123 --status in_review --reason "テスト合格、レビューが必要" --confidence 0.8
multica issue route MUL-123 --status in_progress --owner "Backend Agent" --reason "バックエンドの修正が必要" --confidence 0.6
multica issue route MUL-123 --status in_review --owner-id <agent-id> --no-start --reason "レビュー担当が後で対応する" --confidence 0.9
```

`--owner` を指定しない場合は、`issue status` と同じく、プロジェクトのワークフローが担当者を決めます。明示的な `--owner`（メンバー、エージェント、スクワッド。`--owner-id` は名前の代わりに UUID を取ります）は、ワークフローの担当者を置き換えます。現在のステータスを保ったまま担当者だけを変えるルートは許可されます。ステータスも担当者も同じルートは HTTP 409 で拒否され、何も書き込まれません。`--no-start` は `issue update` と同じく、エージェントの実行を開始しません。`--expected-revision` を指定すると、その間にタスクが変更されていた場合にルートを拒否します。

### タイムライン

`issue get` はタスクの現在の状態を返します。`issue timeline` はステータス、優先度、担当者、タイトル、日付の変更と実行結果を時系列に並べ、コメントも混ぜて表示します。「いつ in_review に移ったか」「今のステータスにどれだけ留まっているか」を調べるときに使います。

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only` はコメントを除き、すべてのアクティビティ記録を残します。`--action` は指定したアクションだけを返し、繰り返し指定でき、`--activity-only` を含意します。サーバーが読み込む履歴には上限があり、切り詰められた場合は stderr に警告が出ます。その結果から滞在時間を推定しないでください。

```bash
multica issue description history MUL-123
multica issue description diff MUL-123 --from 30 --to 35
```

`issue description history` は、課題の説明の記録済みリビジョンを古い順に、リビジョン番号・時刻（ICT）・実行者とともに一覧します。`issue description diff` は、そのうち 2 つの間の unified diff を出力します。リビジョン番号は課題自身のリビジョンカウンターです。存在するのは履歴機能の導入後に記録されたリビジョンだけで、各課題の最初のエントリは、その時点の説明を基準として保存したものです。説明を変更しなかったリビジョンは、それ以前の最新のテキストとして解決されます。存在しないリビジョンは 404 を返します。どちらも `--output json` が使えます。

### 長いコメントスレッドを読む

コメントの多いタスクを 1 件ずつ読むと、エージェントは多くのトークンを使います。まずスレッドをざっと見て、必要なものだけを開きます。

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only` はトップレベルのコメントだけを返し、それぞれに返信数と最終アクティビティ時刻が付きます。
- `--summary` は各コメントを短いプレビューに切り詰めます。
- `--compact` は JSON 出力にだけ効き、情報のないフィールド（繰り返される `issue_id`、空の配列など）を省きます。
- `--recent N` は最近動きのあった N 件のスレッドを、すべての返信付きで返します。返信が多いと出力は長くなります。
- 解決済みのスレッドは既定で最初のコメントと結論に折りたたまれます。全文が必要なら `--full` を付けます。

一覧も必要なフィールドだけに絞れます：`multica issue list --output json --fields id,identifier,title,status`。絞り込みは CLI 側で行われるので、減るのは出力とコンテキストで、リクエストの量は変わりません。

### ウェイクアップ

ウェイクアップは、イベントが起きたとき、条件が成り立ったとき、または指定の時刻に、エージェントの通常の実行を始めます。詳しいルールは[タスクのウェイクアップ](/issue-wakeups)を参照してください。

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "返信が来たら、その内容で見積書を更新する"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "仕入れ先から返信が来ているか確認する"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

ターミナルからメンバーとして作成するときは `--agent-id` が必要です。エージェントが自分の実行の中で作成した場合は、既定でそのエージェント自身を起こします。

人が起動できるルールとは、コメント・課題・リアクション・添付の変更に対するイベントルールで、アクターのフィルターがメンバーを除外しないものです。ワークスペース設定 `ask_guard_mode` が `warn` または `block` のとき、エージェントは次のいずれかがない限り、そのようなルールを自分で登録できません。

- `--decision <request-id>` はルールをこの課題の決定リクエストに結び付けます。リクエストは質問済みまたは回答済みで、`--filter-actor-id` を指定した場合はそのメンバーのものである必要があります。1 つのリクエストに結び付けられる有効なウェイクアップは 1 つです。
- `--purpose observe` は人を待たないルールを示します。メンバーが原因の実行ごとに監査イベントが記録されます。
- `--filter-actor-id` なしの `--filter-actor-type agent` は、すべてのエージェントに一致し、メンバーには一致しません。

`block` モードでは、修正コマンドを含むメッセージ付きの 422 で拒否されます。`warn` モードではルールは作成され、イベントだけが記録されます。

### ウェイクアップルール

ワークスペースとプロジェクトのウェイクアップルール（[Issue ウェイクアップ](/issue-wakeups)を参照）には専用のコマンドがあり、`create` と `get` に加えて次を使えます。

```bash
multica wakeup-definition list [--project <project>] [--output json|table]
multica wakeup-definition preview [--project <project>] [--rule <rule>] [--output json|table] --config-file rule.json
multica wakeup-definition update <rule> [--project <project>] --revision <n> --config-file rule.json
multica wakeup-definition delete <rule> [--project <project>] --revision <n>
```

`--revision` は `list` が表示するリビジョンです。`update` に `--revision 0` を指定するとオーバーライドを作成します。`preview` は何も保存せず、解決後のルールを出力します。条件ルールでは `already_satisfied` が、すぐに一致する Issue の数を示し、`issues` がその Issue を列挙します（`--output table` で一覧表示）。プレビューはスコープの先頭 200 件の Issue を調べ、そのうち未完了でバックログでないものを評価します。スコープにそれ以上ある場合は `truncated` が `true` になり、ほかにも一致する Issue がある可能性があります。イベントルールには条件がないため、プレビューに `already_satisfied` はなく、既存の Issue には一致しません。ルールの編集と削除ができるのはオーナーまたは管理者だけです。プレビューは人のメンバーなら誰でも実行できます。エージェントなどのマシン認証情報は `403` を受け取り、エージェントが作成したルールは人が有効にするまで無効のままです。

### DM で進捗をフォローする

DM は、エージェントがあなたのために作成した issue をフォローします。メンバーは自分が作成した DM でのみ `--chat` を付けてフォローを管理できます。エージェントは `--chat` なしで `multica issue follow <issue>` を実行します。DM は自分のタスクから決まり、DM のないタスクは拒否されます。子 issue は親の有効なフォローを引き継ぎます。

```bash
multica issue follow MUL-123 --chat <chat-session-id>
multica issue mute-follow MUL-123 --chat <chat-session-id>
multica issue unmute-follow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id> --scope root
multica issue follows --chat <chat-session-id>
```

`unfollow` はその issue のフォローを終了します。`--scope root` を付けると、子 issue がそこから継承したフォローも終了します。個別に手動でフォローした子 issue はフォローされたままです。フォローを外した子 issue は、後から子 issue が作成されても再びフォローされません。

## エージェントとスキル

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

インポートで同名のスキルに当たった場合、デフォルトでは既存の内容を変更せずに停止します。意図に応じて選択してください:

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite` はスキルの作成者だけが使え、元の ID とエージェントの紐付けを維持します。

環境変数や MCP 設定にはトークンが含まれることがよくあります。コマンドラインに値を直接書くとシェルの履歴や `ps` の出力に残るので、`-file` または `-stdin` の形で渡してください。

```bash
multica agent create --name "運用アシスタント" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- `--custom-env` 系のフラグは `agent create` にしかありません。後から変えるときは `agent env set` を使います。これは全体を置き換え、値を `****` にしたキーは元の値を保ちます。
- `agent update --mcp-config null` で MCP 設定を消去します。
- `--custom-args` は JSON 配列で、起動引数の最後に置かれます。モデルは `--model` で選んでください。カスタム引数の中の `--model` を受け付けないツールもあります。
- エージェントを呼び出せる人は `--permission-mode` で決めます。`private` は所有者だけ、`public_to` は `--public-to-workspace` または `--public-to-member <user-id>` と組み合わせます。`--visibility private|workspace` は古い書き方で、`--permission-mode` に対応付けられます。両方を指定した場合は `--permission-mode` が優先されます。

## デーモンとランタイム

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

```bash
multica daemon autostart enable
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "社内 Claude ラッパー" \
  --command-name ccms --runtime-type claude
```

`daemon autostart` は現在のプロファイルをログイン時に起動するよう登録します。プラットフォームごとの違いは[ログイン時の自動起動](/daemon-runtimes#autostart)を参照してください。`runtime usage` は既定で 90 日分を集計し、`--days` は最大 365 です。`runtime update` はそのコンピューターのデーモンに CLI を指定のバージョンへ更新させ、`--wait` を付けると更新が終わるまで待ちます。`runtime profile create` は互換ツールを `--runtime-type` で指定します（古い `--protocol-family` も使えます）。固定引数は今のところ Web アプリでしか設定できません。

アクティブなエージェントがまだ紐付いているランタイムの削除は、デフォルトで拒否されます。`multica runtime delete <id> --cascade` は、それらのエージェントをランタイムから解除して設定と履歴を保持し、アクティブな実行をキャンセルします。

`multica runtime breaker list` は各プロバイダーのサーキットブレーカーを表示し、`multica runtime breaker reset <provider>` は強制的に閉じます（オーナーまたは管理者のみ）。[プロバイダーのサーキットブレーカー](/daemon-runtimes#provider-breaker)を参照してください。

仕組みとカスタムプロファイルについては[デーモンとランタイム](/daemon-runtimes)を参照してください。

## プロジェクト、ワークスペース、オートパイロット

```bash
multica project create --title "夏のキャンペーン" --lead "李雷" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "運用チーム" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "週次の売上レポート" --agent "運用アシスタント" \
  --mode create_issue --issue-title-template "売上レポート {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Asia/Tokyo
```

- `--lead` にはメンバーまたはエージェントの名前を指定します。`--default-branch-hint` はリポジトリの既定ブランチをエージェントに伝えるだけで、ブランチは切り替えません。
- ワークスペースの `--context` は、ワークスペース内のすべてのエージェントに渡されます。`--slug` は作成後に変更できません。`--issue-prefix` は大文字に変換され、変更すると既存のすべてのタスクが振り直され、外部から参照している古い番号は使えなくなります。
- `multica workspace update --routing-agent <agent-id> [--routing-fallback-agent <agent-id>]` は、ルーティングだけを行うワークフローのステップ（既定は `todo`、`blocked`、`merged`、`need_decision`。`--routing-statuses` で変更し、`--routing-overrides todo=<agent-id>` で特定のステータスを別のエージェントに振り分け）を担当するエージェントを指定します。このエージェントがアーカイブされた場合、またはその実行がプロバイダーのエラーで失敗した場合、フォールバックのエージェントが引き継ぎます。上書きのキーを `<workflow-id>:<status>` にすると、その上書きは 1 つのワークフローに限定されます。`none` でその項目をオフにします。変更できるのは人間のオーナーまたは管理者のみで、変更はすべてアクティビティログに記録されます。設定は `background_agents` の `routing` ジョブとして保存されます。これらのフラグは `multica workspace background-agents set routing` の別名で、従来の `/routing-agent` API ルートも 1 リリースの間は別名として残ります。
- `--issue-title-template` で置き換えられるのは `{{date}}`（UTC、`YYYY-MM-DD`）だけで、ほかの `{{...}}` は拒否されます。スケジュールトリガーの `--timezone` は既定で UTC です。
- `--mode script --script <name> [--arg <value>]...` は、モデルセッションなしでエージェントのタスクトークンの下、許可リストにあるスクリプトを 1 つ実行します。`--script` と `--arg` には `--mode script` が必要で、`--mode script` には `--script` が必要です。`--description` は実行されません。デーモンに許可リストがない場合、すべてのスクリプトタスクは安全側で失敗します。`--output json` はスクリプト名と引数を `script_config` として表示します。`autopilot update --mode <他のモード>` はスクリプトを消去します。 タスク終了時、サーバーはタスクトークンの削除をベストエフォートで行います。削除に失敗した場合、トークンは有効期限まで有効なままで、それより早く失効させる仕組みはありません。実行結果の `script` にスクリプト名、引数リストの SHA-256、終了コード、所要時間が記録され、削除に失敗した場合は `token_revoke_failed` が設定されます。

### 設定変更の提案

`multica config propose` は、ワークスペース設定の変更用アクションファイルを作ります。現在の値を読み、サーバーが再計算するのと同じ方式で `before_sha256` と `after_sha256` を計算し、`multica decision request --action-file` が受け取るファイルを書き出します。何も送信せず、シークレットも書きません。承認は引き続き人がパスキーで行います。

対象フィールド: `agent.instructions <agent-id>`、`squad.instructions <squad-id>`、`workspace.context`、`workflow.steps <workflow-id>`、`workflow.step.instructions <workflow-id> --status-key <key>`, `workflow.budget <workflow-id>`、`workspace.settings --set key=value|key:=<json>`。テキストは `--file`（UTF-8、NUL バイトなし）で渡します。`workflow.steps` にはワークフロー GET が返す steps 配列を渡します。この出力を編集してください。サーバーが steps を別の形に正規化すると、リクエストは拒否されます（`after_digest_mismatch`）。`workflow.step.instructions` ではサーバーが after ダイジェストを計算するため、ファイルに `after_sha256` は入らず、表示されるダイジェストは比較用です。`--out <path>` でファイルを書き、`--dry-run` で何も書かずに 2 つのダイジェストとアクションを表示します。`--expires-in <秒>` で有効期限を指定します。

`workflow.budget <workflow-id>` は `--file` の代わりに `--max-runs <n>`（1〜1000。0 で上限を解除）と `--include-child-prs=<true|false>` を取ります。少なくとも 1 つを指定してください。省略した欄は保存済みの値のままです。エージェントはこの 2 つの欄をワークフローに直接書き込めません（`budget_requires_decision`）。変更を提案して決定を依頼すると、CLI が読んだダイジェストとワークフローが一致する場合に限り、承認時にサーバーが適用します。

タスクトークンを持つエージェントは 1 回の呼び出しでカードを開きます。`multica workflow update <workflow-id> --max-runs-per-issue 40 --issue <issue> --for <user-id>` は現在のワークフローを読み取り、指定した予算フラグだけで `workflow.budget.set` を提案し、カードの URL を表示します。オーナーが承認するまで何も書き込まれません。同じ呼び出しを繰り返すと同じカードが返ります。予算の呼び出しには `--name`、`--description`、`--steps-file`、`--start-status`、`--map`、`--dry-run` を付けられません。コマンドはリクエスト前に拒否するので、2 つのコマンドに分けて実行してください。`--print-hash` は予算変更の `before_sha256` と `after_sha256` を表示します。`multica config propose workflow.budget` では同じフラグを `--max-runs` と呼びます。ワークフローの予算が広がる場合、`multica issue update <issue> --workflow <workflow-id>` と `multica issue create --workflow <workflow-id>` も同じ `--print-hash` と `--decision-id`（欄 `issue.workflow`）を取ります。両コマンドは同じ規則に従い、オーナーの対話セッションでは決定は不要です。

それ以外のフィールドは、何も読む前に `denylisted` で拒否されます: `project.description`、パスキーと決定ゲート、メンバーとロール、オーナー移譲、認証・連携のシークレット、ワークスペース削除、アクションレジストリ、`delegated_governed_writes`。サーバーの許可テーブルにない設定キーも同様に拒否され、許可キーと拒否キーが混在するパッチは全体が拒否されます。サーバーはリクエスト時と承認時にもう一度確認します。

```bash
multica config propose workspace.context --file ./context.md --out ./action.json
multica config propose agent.instructions <agent-id> --file ./instructions.md --dry-run
multica config propose workflow.step.instructions <workflow-id> --status-key review --file ./step.md --out ./action.json
multica config propose workflow.budget <workflow-id> --max-runs 40 --include-child-prs=false --out ./action.json
multica config propose workspace.settings --set compact_prompt="..." --set wakeups_paused:=false --out ./action.json
multica decision request --issue MUL-123 --for <user-id> --class reversible --ask-file ./ask.md --action-file ./action.json
```

### シャドウレポート

ワークスペースのメンバーは誰でも System 1 のシャドウレポートを読めます:

```bash
multica decision shadow-report [--since <RFC 3339>] [--until <RFC 3339>] --output json
```

`decision` ブロックと `routing` ブロックは全期間を対象にします。`route` ブロックは `[since, until)` の期間を対象にします。`--since` と `--until` は RFC 3339 の時刻を取り、`--until` の既定値は現在、`--since` の既定値は `--until` の 24 時間前です。不正な時刻や `--until` より後の `--since` は、サーバーが 400 で拒否します。

`route` ブロックは 1 つのイベント集合を数えます。ルーティングステップを離れたと記録されたエージェントのステータス変更 (`eligible_exits`) と、同じイベント ID を持つ route ラベル (`matched_labels`) です。`label_coverage` は `matched_labels / eligible_exits` で、1 を超えません。`via_route_share` は、最初のラベルがステータスのフォールバックではなく `issue route` から来た、一致イベントの割合です。`duplicate_labels` は、より古いラベルとイベントを共有するラベルの数です (目標は 0)。`labels_total`、`owner_only_labels` (ステータスを変えない route のためイベントなし)、`non_routing_labels` (ルーティングエージェントのないステップからの route) はカバレッジに含まれません。`overridden` は 1 時間以内に人が取り消したエージェントのラベル数で、`override_rate` は `overridden / labels_total` です。ブロックにはクラスごとの `decided`、`predicted`、`agreed`、`coverage`、`precision` も含まれます。

## ID と出力形式

タスクには `MUL-123` のようなキーまたは完全な UUID を使います。UUID の短いプレフィックスは受け付けません。

その他のリソースの `list` コマンドは通常、コピーできる短い ID を表示し、`--full-id` で完全な UUID を出力できます。短い ID が一意に定まらない場合、CLI は文字の追加か完全な UUID への切り替えを求めます。実行の短い ID は、所属するタスクを `--issue` で指定する必要もあります。

多くのコマンドが構造化出力をサポートします:

```bash
multica issue list --output json
multica agent list --output json
```

スクリプトでは、ターミナル向けの表を解析せず JSON 出力を使ってください。各コマンドがサポートする出力形式とページネーションのフラグは `multica <command> --help` が正です。

## プロファイルと設定

デフォルトの設定は `~/.multica/config.json` に保存されます。`--profile <name>` を使うと、サーバーアドレス、トークン、デフォルトワークスペース、デーモン状態を別のセットとして分離できます:

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

名前付きプロファイルは `~/.multica/profiles/<name>/config.json` に保存されます。現在の値を確認する:

```bash
multica config show
multica config show --profile staging
```

<Callout type="warning">
CLI の設定ファイルには、あなたとして Multica にアクセスできるトークンが含まれます。リポジトリにコミットしたり、ログにアップロードしたり、他人と共有したりしないでください。
</Callout>

### 判断の提案

タスクトークンは、人がパスキーで承認する管理対象アクションを提案できます。提案自体は何も変更しません。

```bash
multica decision propose issue.run_budget.raise --version 1 --issue MUL-123 \
  --for <user-id> --param window_id=<id> --param new_cap:=40 [--reason "..."]
multica decision propose <action-type> --version 1 --issue MUL-123 --params-file ./params.json
```

`--version` と `--issue` は必須です。`--param k=v` は文字列、`--param k:=<json>` は生の JSON を送ります。`--params-file` は JSON オブジェクト 1 つを受け取り、`--param` とは併用できません。コマンドは承認カードのリンクを表示します。実行予算のアクションでは、このリンクは課題上の承認を開きます。それ以外のアクションでは、チャット内のカードへのリンクになり、そこで承認します。通常の選択肢カード（`--action-file` なしの `multica decision request`）では変更を適用できません。承認しても回答が記録されるだけです。サーバーは意図を読み取れないため、そのようなカードを拒否せず、決定や選択肢がワークフロー・エージェント・スクワッド・ワークスペース・予算の変更に見える場合（または許可リストのアクション種別を含む場合）に助言ヒントを付けます。その変更は `multica decision propose` で送ってください。拒否された場合はサーバーのステータスとエラーコードを表示します。`multica issue budget raise` と `multica issue budget top-up` は、タスクトークンでは同じ経路を使います（`--for <user-id>` を追加）。個人アクセストークンでは従来どおり支出リクエストを開きます。どちらのコマンドも 1 つ以上の issue ID を受け取ります：`multica issue budget top-up CHE-1 CHE-2 CHE-3 --for <user-id> --goal "<目的>"`。ID が 1 つなら従来の単一提案のままです。タスクトークンで複数の ID を渡すと、バッチ経路を 1 回だけ呼び、カードのリンクを 1 つ表示します。`--goal` でバッチに名前を付けられ（既定：操作と issue 数）、`--output json` はバッチ ID と issue ごとの提案 ID を返します。個人アクセストークンでは ID ごとに個別のリクエストを開きます。バッチ経路にはチャットタスクが必要で、issue は 25 件までです。サーバーは raise のバッチを 1 つのパスキーで承認しますが、top-up のバッチは承認時に拒否するため、top-up は 1 件ずつ承認してください。

実行予算の次の一手: issue の 80 % 通知には、数値とそのまま実行できるコマンドが付きます。例: `Run budget: 20 of 25 runs used on CHE-1234 (workflow Default, cap 25). Ask for more: multica issue budget raise CHE-1234 --runs 40`。予算が拒否した実行は、エラーコード `run_budget_exhausted` と `runs_used`、`runs_limit`、`workflow_id`、`window_id`、`open_card`、`next_command` を返します。`multica issue budget get <issue> --output json` も `open_card` と `next_command` を返します。issue の現在のウィンドウに引き上げまたは追加ウィンドウのカードが開いている間、`next_command` はそのカードを待つよう伝え、`multica issue budget raise` を再度実行しても新しいカードは開かず同じカードを返します。タスクトークンでは、issue タスクの `--for` は既定でワークスペースのオーナーになり、ヘルプには `raise` だけが表示されます。`top-up` はメンバーが引き続き使えます。サーバー、メンバー、エージェントがカードを開くたびに、アクターの種別、アクター、アクション種別を記録する `run_budget_ask` アクティビティ行が 1 件追加されます。

適用済みのアクションは、取り消し可能な間、本人が取り消せます。`multica decision revoke <request-id> --why "<理由>"` を実行します。アクションが取り消し可能なのは、適用済みで、その種類に正確な逆操作があり、まだ取り消されていない場合だけです。このリリースで逆操作を持つのは `agent.pause`（逆操作は `agent.resume`）のみで、承認によってエージェントが一時停止され、その後に誰も一時停止状態を変更していない場合に限ります。それ以外のアクション種別は取り消せないままです。取り消せるのは依頼の宛先の本人だけで、承認と同じロール規則が適用されます。passkey が必要なアクションはアプリで取り消します。サーバーは取り消した人、日時、理由を記録し、逆操作を実行して、依頼したエージェントを結果 `revoked` で起こします。却下、期限切れ、未適用、議論のみ、または取り消し済みの判断は取り消せません。`multica decision get <request-id>` は `revocable` を表示し、取り消し後は `revoke` レコード（`at`、`by`、`reason`）も表示します。

`issue.project.set` は Issue を別のプロジェクトへ移動します: `multica decision propose issue.project.set --version 1 --issue MUL-123 --param project_id=<project-id>`。カードには移動前後のプロジェクト、ワークフロー、実行上限、使用済み実行数が表示され、移動が実行予算を広げるかどうかも示されます。予算を広げる移動は `spend` カード、それ以外は `reversible` です。承認できるのはワークスペースのオーナーのみです。依頼後に Issue が元のプロジェクトを離れた場合、または移動先ワークフローの予算が増えた場合、カードは拒否されます。

Run 予算の自動承認: issue が run 予算を使い切ると、直前のウィンドウに進捗があり、異常がなく、ワークスペースの 1 日の枠に空きがあれば、サーバーが次のウィンドウを自動で承認します。issue の監査コメントにルール名（`auto-approver v1`）と停止スイッチが書かれます。承認されたウィンドウでは、サーバーが拒否した run も再開され、issue が `blocked` になることはありません。進捗とは、run が issue のステータスを動かした、リンクされた PR のヘッドや状態を変えた（PR へのコメントは含みません）、またはコミットした場合です。コメントは内容にかかわらず進捗になりません。これらがない run は空振りです。ループ（同じ失敗チェック、失敗した CI ワークフロー、または run のエラーが 3 run 以上で繰り返される場合。コメントは読みません）、空振りウィンドウ（80% 以上の run が何も成果を出さない）、トークンの急増（1 run あたりのトークンがワークスペース中央値の 3 倍超）、繰り返しの追加（1 issue で 24 時間に 3 回以上の追加）、OpenAI 制限中の OpenAI プールのエージェントは自動承認されません。オーナーには 1 日最大 1 枚のまとめカードが届きます。同じ日の後続の異常はそのカードのチャットにメッセージとして届き、ブリーフに保留された issue が一覧されます。それ以外のケース（すでに `blocked` の issue や、拒否された run が issue のエージェント担当者向けではない場合を含む）は issue ごとのカードに戻ります。ワークスペース設定 `run_budget_auto`: `enabled`（既定 `false`: 自動承認は無効で出荷されます）と `daily_envelope`（ICT の 1 日あたりの追加 run 数、既定 `300`）と `expected_checks`（push した head が CI を既知とみなされるために、完了して揃っている必要があるチェック名。既定は空で、head を push したウィンドウはすべて保留されます）。期待するチェックの一部しか完了していないスナップショットは既知とみなされません。名前は、完了した Checks API の run がちょうど 1 件の場合にのみ数えられます。同名のコミットステータスや、同名の 2 件目の run があると、そのウィンドウは保留されます。`multica config propose workspace.settings --set 'run_budget_auto:={"enabled":true}'` または `workspace.settings` の設定提案で有効にできます（`"enabled":false` で再び無効）。

### 対象フィールドにはパスキー操作が必要

タスクトークンとクラウドノードトークンは、旧来のルートから次のフィールドに書き込めません: `agent.instructions`、`squad.instructions`、`workspace.context`、ワークフローのステップとステップ指示、決定アクションの許可テーブルにあるワークスペース設定キー(`compact_prompt`、`auto_compact`、`idle_started_guard`、`wakeups_paused`、`mermaid_orientation` など単純な運用キー)。サーバーは 403 と `code: passkey_action_required` を返し、代わりに提案するアクションを `action_type` で示します(`agent.instructions.set`、`squad.instructions.set`、`workspace.context.set`、`workflow.steps.set`、`workspace.settings.patch`)。保存済みの値は変わりません。投票レシート、決定バインディング、PASS レシート、Hermes の例外では、この拒否は解除されません。`multica decision propose <action-type>` でアクションを提案すると、人がパスキーで承認します。人による書き込みと `project.description` は従来どおりです。

## 別のコーディングエージェントから Multica を操作する

作業の多くを Codex、Claude Code、Cursor の中で進めているなら、ターミナルに切り替えずそこから Multica を操作できます。[Multica CLI skill](https://github.com/multica-ai/multica-cli) は、このページのコマンドを安全に扱う方法をそれらのエージェントに教えます。タスクとコメントスレッドをトークンを浪費せずに読み、コメントはファイル経由で書き、メンション・ステータス変更・アサインが伴う副作用を正しく扱います。

認証済みの CLI を通してのみ動作し、それ自体は何の権限も与えません。権限は引き続きログイン、選択中のプロファイル、ワークスペースに由来します。CLI は v0.4.26 以降が必要です。Claude Code のプラグインマーケットプレイス、Codex の skill インストーラー、Cursor、その他 Markdown の指示を読み込むツールへのインストール方法は、リポジトリの README を参照してください。
