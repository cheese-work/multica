Multica の日常的な利用で主に扱う認証情報は 2 種類です: ブラウザのサインインセッションと個人アクセストークンです。ブラウザセッションは Web と Desktop で使われ、個人アクセストークンは CLI、デーモン、スクリプト、API で使われます。

## ブラウザのサインインセッション

メールの確認コードまたは Google でサインインすると、Multica は `multica_auth` という名前の HttpOnly cookie に JWT を保存します。ブラウザが自動的に送信し、JavaScript から直接読み取ることはできません。

セッションはデフォルトで 30 日間有効ですが、これはサインインからのカウントダウンではありません。使い続けているセッションは失効前に再発行されるため、定期的にサインインし直す必要はありません。再発行されるのは有効期間の半分を過ぎてからなので、使われなくなったセッションは最後の利用から 30 日を待たずに失効することがあります。セルフホストの管理者は、`AUTH_TOKEN_TTL` で有効期間を調整できます。[サインインとサインアップ](/auth-setup#セッション有効期間)を参照してください。サインアウトすると、現在のブラウザの認証 cookie と CSRF cookie が削除されます。

ブラウザの cookie をスクリプトや CLI にコピーするのは適切ではありません。ターミナルから Multica にアクセスするには個人アクセストークンを使います。

## 個人アクセストークン

個人アクセストークン（PAT）は `mul_` で始まり、あなたのアカウントを表します。あなたがアクセスできるすべてのワークスペースと API にアクセスできるため、パスワードと同じように保管してください。

**設定 → API Token** でトークンを作成するときは、名前を入力し、有効期限を 30 日、90 日、1 年、無期限から選びます。デフォルトでは 90 日が選択されています。完全なトークンは一度だけ表示されます。ウィンドウを閉じた後、Multica が保持するのは次の情報だけです:

- トークンのハッシュ値
- 識別用の先頭数文字
- 名前、作成日時、有効期限、最終使用日時

完全な値は復元できません。紛失した場合は、古いトークンを失効させて新しく作成してください。

<Callout type="warning">
PAT をリポジトリ、タスク、コメント、スクリーンショット、ログに残さないでください。また、履歴に保存される shell コマンドに直接渡さないでください。
</Callout>

## CLI と PAT

`multica login` を実行すると、CLI はブラウザ経由でサインインを完了し、有効期間 90 日の PAT を作成して、現在のプロファイルの設定ファイルに保存します:

```text
~/.multica/config.json
~/.multica/profiles/<name>/config.json
```

デーモンは同じ PAT で Multica に接続します。有効期限付きの `mul_` PAT は、残りが 7 日を切ると自動的に更新され、その時点から 90 日後まで延長されます。更新に失敗してもトークン自体は変わりません。トークンがすでに期限切れまたは失効している場合は、`multica login` をもう一度実行してください。

ブラウザのない環境では、先に Web で PAT を作成しておき、CLI に安全に入力を促させます:

```bash
multica login --token
```

## API リクエストで PAT を使う

PAT を `Authorization` ヘッダーに入れます:

```bash
export MULTICA_TOKEN='mul_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx'

curl https://api.multica.ai/api/me \
  -H "Authorization: Bearer $MULTICA_TOKEN"
```

ワークスペースレベルの API を呼び出すときは、エンドポイントの要求に応じてワークスペースも指定します:

```bash
curl https://api.multica.ai/api/issues \
  -H "Authorization: Bearer $MULTICA_TOKEN" \
  -H "X-Workspace-ID: $MULTICA_WORKSPACE_ID"
```

スクリプト内のトークンは secret manager か保護された環境変数から取得し、ハードコードしないでください。セルフホストインスタンスでは、ドメインを自分の公開 API アドレスに置き換えます。

## CI 向けスコープ付きトークン

PAT は `scopes` リスト付きで作成できます。スコープ付き PAT は、そのスコープのルートだけを開き、他は開きません。サーバーは呼び出しのたびにトークン行からスコープを読むため、失効または再スコープされたトークンは即座に止まります。PAT のユーザーはワークスペースのオーナーである必要があります。

| スコープ | 開くもの |
| --- | --- |
| `decisions:feed` | `GET /api/decisions/feed` とその確認応答 |
| `decisions:ci_request` | `POST /api/decisions/ci` |
| `decisions:read` | `GET /api/decisions/{id}/state` |

`decisions:ci_request` により、実行中のエージェントタスクを持たない CI ジョブが、決定カードを 1 枚作成できます。カードのクラスは常に `deploy` で、指定した issue と指定したメンバー（`for`）宛てです。本文には、構造化された `ask`、`candidate_sha`（16 進数 7〜64 桁）、`candidate_at`（RFC 3339 のコミット時刻）を含めます。`action` と対象カードは含められません。

```bash
curl -X POST https://api.multica.ai/api/decisions/ci \
  -H "Authorization: Bearer $MULTICA_CI_TOKEN" \
  -H "X-Workspace-ID: $MULTICA_WORKSPACE_ID" \
  -H "Content-Type: application/json" \
  -d '{
    "issue_id": "<issue-id>",
    "for": "<member-user-id>",
    "ask": { ... },
    "candidate_sha": "<commit-sha>",
    "candidate_at": "2026-11-10T07:32:29Z"
  }'
```

- ある SHA への最初の呼び出しは、新しいカードとともに `201` を返します。
- 同じ SHA をもう一度呼ぶと、重複せず既存のカードとともに `200` を返します。
- より新しい SHA（`candidate_at` 基準）は、その issue の古い未決カードを取り下げます。
- 新しい SHA の後に古い SHA を送ると `409` を返し、何も作成しません。
- それ以外の認証情報、スコープのない PAT、ユーザーがワークスペースのオーナーでない PAT は `403` を返します。

`decisions:read` により、CI ジョブは `doop.deploy_lift`（バージョン 1、params は `marker_value` と `repo`）のようなアクション決定がどうなったかを読み取れます。このアクションに答えられるのは、ワークスペースオーナーのパスキー承認だけです。このルートは読み取り専用で、決定（リクエスト）ID をキーにします。

```bash
curl https://api.multica.ai/api/decisions/<decision-id>/state \
  -H "Authorization: Bearer $MULTICA_READ_TOKEN" \
  -H "X-Workspace-ID: $MULTICA_WORKSPACE_ID"
```

`200` のレスポンスには `decision_id`、`action_id`、`action_type`、`action_version`、`state`、`approver_id`、`answered_at`、`withdrawn_at`、`revoked_at`、`expires_at`、`params` が含まれます。`state` は次のいずれかです。

- `pending`: オーナーの回答待ち。
- `approved`: オーナーがパスキーで承認しました。`approver_id` と `answered_at` が設定されます。
- `rejected`: オーナーが却下しました。
- `withdrawn`: 使用前にリクエストが取り下げられました。未使用の承認を取り消す方法です。
- `revoked`: 承認が与えられた後に取り消されました。`revoked_at` が設定されます。
- `expired`: 回答前に期限が切れました。
- `cancelled` と `failed`: 承認が効力を持たないままアクションが終了しました。

存在しない決定は `404` を返します。他の認証情報、このスコープを持たない PAT、ユーザーがワークスペースのオーナーではない PAT は `403` を返します。

## サインアウトと失効

`multica auth logout` は、現在の CLI プロファイルに保存された PAT を削除するだけです。Web のサインアウトも、現在のブラウザの cookie を削除するだけです。どちらもサーバー上の個人アクセストークンを失効させません。

トークンが漏洩した可能性がある場合は、**設定 → API Token** ですぐに失効させてください。失効した PAT は二度と使えなくなり、それを保存していた他のマシンやスクリプトもアクセスを失います。

## エージェント実行用の一時トークン

デーモンが実行を受領すると、サーバーはその実行のために `mat_` で始まる一時トークンを作成します。トークンは現在のユーザー、ワークスペース、エージェント、実行に紐付き、最長 24 時間有効で、実行の終了時にクリーンアップされます。

デーモンは、ユーザーの PAT をエージェントに渡す代わりに、この一時トークンを AI コーディングツールに注入します。そのため、エージェントが送るリクエストはエージェントの操作として記録され、このトークンでユーザーや owner だけに許可された機密操作を呼び出すこともできません。

この種のトークンはサーバーが自動的に作成するため、ユーザーが保存・管理する必要はありません。

## その他のマシン認証情報

サーバーは、内部またはマネージドなシナリオで使われる 2 種類の認証情報も認識します:

| プレフィックス | 用途 | 管理元 |
| --- | --- | --- |
| `mcn_` | Multica Cloud Node の接続 | Multica Cloud Fleet |
| `mdt_` | ワークスペーススコープのデーモン認証プロトコル | サーバー内部のフロー |

通常の Cloud、セルフホスト、Desktop のインストールでは、これらを手動で作成する必要はありません。ユーザー側の CLI とデーモンは常に `mul_` PAT を使います。他のプレフィックスのトークンを自分で組み立てないでください。
