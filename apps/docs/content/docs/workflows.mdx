A workflow sets the steps a project's issues go through, who handles each step, and what they should do.

For example, a delivery workflow could look like this:

| Step | Who handles it | What they do |
|---|---|---|
| Development | An engineering agent | Implement the change and prepare it for review. |
| Review | A review agent | Check the result, then pass it to QA or send it back for changes. |
| QA | A team member | Try the result and decide whether it is ready to finish. |

Moving an issue into Review hands it to the review agent. The description, discussion, and earlier results stay on the same issue, so the next person or agent can pick up where the last one left off.

The **Delivery** template has this shape. Projects that do not choose a workflow use **Default**: every status is available and nothing is handed off automatically, just as before.

## Create a workflow

In the web or desktop app, a workspace `owner` or `admin` can create workflows:

<Steps>
<Step>

Open **Settings → Workflows** and choose **New workflow**. Start blank or use the **Delivery**, **Content**, or **Community** template.

</Step>
<Step>

Name the workflow and choose its status columns. Drag the middle columns into the order your team uses.

</Step>
<Step>

Select a column and choose what happens when an issue enters it: **No handoff**, **Hand to an agent**, or **Hand to a member**. You can also choose the **Project lead** from the member picker.

</Step>
<Step>

For an agent step, write what it should do. Then set **When done, move to** (the next column if you leave it unset) and **If rejected, send back to** (used when this step finds the work it received unacceptable and it needs rework). Use **Blocked**, not send-back, when the step cannot continue for an outside reason.

</Step>
<Step>

Preview the agent's brief, then save.

</Step>
</Steps>

If you added a new status, save the workflow before setting up that status's handoff.

**No handoff** keeps the current assignee. Handing to a member assigns the work without starting an agent. Handing to an agent asks it to start this step; it still needs to be available to you, and its computer needs to be online to run.

A step with `keep_other_assignee: true` skips the handoff when the issue's current assignee was chosen on purpose: it is neither this step's handler nor the handler of the step the issue is leaving. That assignee keeps the issue, and an agent assignee starts a run for this step. The flag is off by default and is set through the API or CLI. It is temporary: per-issue workflows (CHE-5024) will replace it.

A step with `chain_same_owner: true` starts no new run when an agent moves the issue into it and that same agent is the step's handler, provided the step the agent's run started in has the same kind of handler (agent, project lead, and so on). The agent keeps working in its run, and the status response carries the step's instructions as `step_brief`; `multica issue status` prints it. A different agent, a changed handler kind, or a person moving the issue starts a run as before. A batch update never chains. The flag is off by default and is set through the API or CLI.

A step can carry its own `auto_close: {"mode": "off|warn|block", "top_level": true|false}`. The workspace setting `auto_close` set to `off` is the kill switch and always wins. Otherwise the step's mode replaces the workspace mode for issues entering that step, and a step with no `auto_close` follows the workspace. With `top_level: true`, a root issue can close too: the parent check is skipped, and a child still waits for a parent that is not stopped. On a step in `block` mode, a `pr.merged` edge to `done` whose merge has arrived but whose close checks fail does not move the issue to `done`. It takes the edge's `on_timeout` status at once, one time, and does not wait for the deadline. The field is off by default; set it through the API or CLI.

## Use it in a project

Open a project and choose its **Workflow**. Workspace owners, admins, and the project's lead, when that lead is a member, can change this choice.

The confirmation shows which issues keep their status. If the new workflow does not have a status some issues are using, choose where those issues should go. Switching workflows does not hand off issues or start agents.

The project's board now follows the workflow's columns. Each issue's status picker offers the steps in that workflow and shows who takes over. Projects that have not chosen a workflow use **Default**; you can switch back to it later.

## Pick a workflow from the title type

A workspace owner or admin can set `workflow_by_type` in the workspace settings, for example `{"design": "<workflow id>", "plan": "<workflow id>"}`. A new issue whose title starts with a mapped type, such as `design(x): …`, follows that workflow instead of its project's. `--workflow` (CLI) or an explicit workflow choice always wins. A type with no entry, or an entry whose workflow no longer exists, keeps the project's workflow. `multica issue create` prints the chosen workflow. The create dialog shows the chosen workflow's statuses and handoff once the title has a mapped type. The mapping is workspace policy: it applies to every creator, agents included, without the run-budget check an explicit `--workflow` gets from non-interactive callers. If two keys differ only by case, the first in alphabetical order wins. Editing a title later does not change the workflow; the update response carries a one-line `workflow_hint` (printed by `multica issue update`) with the command that moves it.

A workspace owner or admin can set `quick_first` in the workspace settings to try the Quick workflow on part of new issues: `{"workflow_id": "<Quick workflow id>", "types": ["feat", "fix"], "starts_at": "<RFC 3339>", "ends_at": "<RFC 3339>"}`. From `starts_at` (included) to `ends_at` (excluded), a new root issue whose title type is in `types` and that already follows a full workflow (its project's, or one `workflow_by_type` names) is drawn by its number: an even number starts in the Quick workflow on `todo`, an odd number keeps the workflow it had. A child follows its parent's Quick workflow. An issue is left out when the caller chose the workflow with `--workflow`, when its status is not `todo` or `backlog`, when it is assigned to a member or squad, or when its project has an A/B split in its window. An agent named as the assignee is kept as the issue's author. The setting is off until set; unset, creation is unchanged.

Every bind into the Quick workflow writes a `quick_entry` row in the issue's activity: the draw writes one for both arms (`source` `arm`, `arm` `Q` or `D`), and an issue-level override into Quick writes one with `source` `override`. Quick is the workflow named `Quick`, or the one `quick_first` names. `full_workflow_id` is set by the server to the workflow the issue followed just before: for the draw, the route an odd number keeps; for an override, the issue's previous override, else the `workflow_by_type` entry for its title type, else its project's workflow. It is left out when the issue had none. A caller cannot name it.

`multica issue workflow escalate <id> --reason "..."` moves an issue that follows Quick to the full workflow named by its newest `quick_entry` row; the caller cannot name the target, and unknown request fields are refused. An issue with no `quick_entry` row, or one whose row names no workflow, is refused with `no_full_workflow`; an issue that does not follow Quick is refused with `not_quick`. From `todo` or `investigating` the issue needs an `Estimate:` line in its description or a comment, unless the reason is `rollback`; otherwise the call is refused with `estimate_required`. One transaction writes a `workflow_escalated` row (the reason and the target) and an `intake_call` row with `call` `escalated` and the estimate, then records the switch. With no live task the issue enters the full workflow's step at once, with one run for that step's handler; with a live task the switch is pending and applies after the last task ends. A finished issue follows the full workflow and is handed to no one; a reopened Quick issue escalates to its prior workflow with one run for the step it sits on. The reverse move is guarded: an agent that moves an issue into Quick (`issue update --workflow`) opens an owner approval card and changes nothing until it is approved, while a member switches at once. An agent with a task token that moves an issue into a project that follows Quick (`issue update --project`, with `project_id` as the only field; any other field in the call is refused with `quick_move_alone`), or switches a project to Quick (from a run on an issue), opens an owner approval card and changes nothing until it is approved; a member does it at once. The cards are `issue.project.quick_set` and `project.workflow.quick_set`: each seals the binding the owner sees, the server recomputes it under locks on approval, and any difference ends the card as `stale_base`. Any other agent credential is still refused with `budget_rebinding_requires_interactive`.

## Route work by capability

The workspace setting `capability_routing` maps an issue type to an author agent and an ordered list of reviewer agents, for example `{"feat": {"author": "<agent id>", "reviewers": ["<agent id>"]}}`. Keys are lowercase types, ids must be agents of the workspace, `reviewers` is not empty, and the author is not a reviewer. It is unset by default; with it unset, behavior does not change. Only the **Author** and **Reviewer** handlers read it. It changes only through a `workspace.settings` card (`multica config propose workspace.settings --set 'capability_routing:=<json>'`); a generic settings save keeps the stored value. Read it with `multica workspace capability-routing`; it prints `{}` when unset.

**Author** is a handler for a step such as In progress. An issue entering the step goes to its author: the person or agent who last took the issue into this step, else the `author` that `capability_routing` names for the issue's type (the Conventional Commit prefix of its title, such as `feat`). A change to the table keeps the author an issue already has; a person who reassigns the issue becomes its author for the next entry. With neither, the step hands off to nobody and the workflow lint warns (WF015) when the workspace routes no author. Set it with `multica workflow handoff set <workflow> <status-key> --handler author`.

A `reviewer` step hands the issue to the first reachable reviewer listed for the issue's type (the Conventional-Commit prefix of the title) whose lab is known, differs from every author's lab, and who is not an author. An override, a sticky assignee, or an assignee named in the same write is held to the same rule. When none qualifies, or the issue's type has no routing entry, the move is refused with `409 review_independence`, naming the labs, and the issue is left unchanged.

The workspace setting `review_independence` sets what the reviewer rule compares and who has which value: `{"attribute": "lab", "rule": "reviewer_value_not_in_author_values", "agent_values": {"<provider>/<model>": "<value>", "<provider>/*": "<value>"}, "commit_identities": {"<exact email>": "<value>", "<domain>": "<value>"}}`. An agent's value is looked up by its runtime `provider/model`, then `provider/*`; an unlisted agent has no value and is refused. A commit identity (author, committer or `Co-authored-by`) maps by its exact email, then its exact domain (no suffix match). With the setting present and a linked PR whose commits all name a mapped identity, the authors' values are the values on those commits, so an agent that only moved statuses or commented is not an author; with no linked PR, an unreadable commit list or a commit with no mapped identity, every agent that ran at a work step counts. The merge gate judges the PASS by the same values. A refusal names the attribute and the commit or run behind each author value. With the setting unset, the built-in lab rule applies as before. It changes only through a `workspace.settings` card (`multica config propose workspace.settings --set 'review_independence:=<json>'`); a generic settings save keeps the stored value.

A `same_as` step hands the issue to the agent that last handled another step of the workflow on this issue, so one agent can carry an issue through several steps. Set it with a handler of `{"type": "same_as", "step": "<status-key>"}`. The agent is the issue's assignee while it sits in that step, else the one it had when it last left that step. An agent that is archived or gone counts as not found. When none is found, the step uses the agent in the handler's optional `id`, else the handler of the named step. The `step` must be another step of the same workflow, and a step cannot lead back to itself through other `same_as` steps; a save that breaks either rule is refused. `multica workflow get` shows the handler as `same_as: <status-key>`. On the `agent_review` step the agent it finds must also pass the reviewer independence rule (an author, or an agent of an author's lab, is refused with `review_independence`).

An entry named `default` in `capability_routing` routes an issue whose title has no type, or a type the table does not list (`task`, `ops`, `spec`); a listed type keeps its own entry. The **Author** and **Reviewer** handlers read it, and the reviewer still passes the reachability and lab independence rules; with no `default` entry and no listed type, the refusal names a blocker. An issue already in flight keeps the agent that worked it as its author when it has no stored author. A `same_as` step that names `agent_review` hands the issue to the agent that signed the PASS for the exact head of the linked pull request, not to the last agent on record. When no standing PASS names that head, the move lands in Blocked and records `review_signer_missing`, not another reviewer. A `same_as` step whose named step is a **Reviewer** step takes that step's routed reviewer, and a refusal is reported. The signer is the only route: a sticky assignee does not replace it, and a `handoff_assignee` other than the signer is refused. A PASS from a run that did not review that exact head is not recorded, and no older PASS stands in for it: the move lands in Blocked. An issue that had already left `agent_review` when the rule started keeps its route until it closes, however it moves afterwards; one that goes back through `agent_review` joins the rule.

## Move work to the next step

Change an issue's status or drag its card to another column. If that step has a handoff, check who will receive it and, for an agent, the instructions it will receive.

<WorkflowDemo />

When you create an issue in a project and its status has a handoff, the issue goes straight to that step's handler, even if you picked an assignee; an agent starts right away. The create dialog shows who it will be handed to. To create it without starting anything yet, put it in Backlog.

When the previous assignee is an agent with a run underway or waiting to start, the confirmation adds an option to stop or cancel it, selected by default. Leave it selected unless you want both agents working at once; the comments and work it already saved are kept.

**When done, move to** and **If rejected, send back to** tell the agent where to move the issue next. A run finishing does not move the issue by itself: the member or agent handling the step updates its status. When an agent moves the issue into the next step, that step's handoff runs just as it would for a member.

You can see the handoff and its instructions in the issue's timeline. Open the workflow menu on the project board to view the full flow.

## When a PR merges [#pr-merged]

A merge changes a status through one workspace setting: **Settings → Code → After PRs merge, move the issue to**. See [GitHub integration](/github-integration). The rule is set and shown only there. The workflow board and editor don't draw it, and it is never saved in the workflow. With **Don't change**, a merge moves no issue. If the workflow doesn't list the status the setting names, the issue doesn't move.

When that step has a handler, the merge hands the issue to it and starts its run, like any other move.

### The `pr.merged` transition is deprecated

An older workflow can store a transition guarded by `pr.merged`. While the setting is not **Don't change**, a stored `pr.merged` transition no longer moves issues itself: it runs the same check as the setting. The editor's guard list still offers `pr.merged`, but while a merge status is chosen a save that adds one is refused with a message that points to Settings → Code. With **Don't change**, stored transitions work as before. They will be removed in a later release.

## Adjust a workflow

A workflow can be shared by several projects. Changes saved in **Settings → Workflows** apply to every project using it. To give one project a different process, duplicate the workflow and select the copy in that project.

Admins can also set a handoff from the project board: hover a column header and click **Hand to…**, or click the handler already shown. If other projects share the workflow, you are asked **Where should this change apply?** Choosing only the current project makes a copy of the workflow for it and leaves the other projects unchanged.

Removing a column may ask you to choose a new status for issues already in it. Other issues stay where they are, and this move does not start agents. The status library below the workflows is where you rename or recolor statuses; those changes are shared wherever the status is used.

Set **Max runs per issue** in the workflow editor to limit how many runs one issue may start before the workflow blocks it (1 to 1000; leave it empty for the default of 15). Changing it needs a signed-in web or desktop session; a save that leaves the field alone works from any client. The **Include child PRs** switch next to it controls whether PR guards also read the PRs of sub-issues (on by default) and follows the same rule. An agent or token cannot change either field directly: it gets `budget_requires_decision` and proposes the change with `multica config propose workflow.budget`, and an owner approves it with a passkey. The same limit applies when an agent or token creates an issue on, or re-binds an issue to, a workflow with a wider budget (`budget_rebinding_requires_interactive`). It takes the same decision: `multica issue create` and `multica issue update` accept `--workflow <id> --decision-id <id>`. The decision must be of class `spend` and its owner must not be in passkey recovery. While the workspace passkey gate is `block`, the owner must also have answered it with a passkey; otherwise the write is refused and names the missing condition. From an agent run, `multica issue update <id> --workflow <workflow-id>` with a wider budget needs no decision: it opens an approval card for the workspace owners, prints its action id and URL, and leaves the issue unchanged until an owner approves it with a passkey. The approval fails with `stale_base` if the issue's workflow, its project's workflow or its budget changed after the card opened.

On an issue with a run budget, the sidebar shows a meter with the runs used, the runs left, a warning at 80 % and a **Run budget used up** state. **Raise** and **Top up** ask a workspace owner to approve more runs. If you are an owner, you approve with your passkey right there; otherwise the owner gets the request. In the list and on the board, an issue the budget stopped shows a **Budget used** chip next to its status. After an owner approves, the decided card and the approval panel show the new limit and what happened to the stopped issue (run queued, run started, status restored, or why it did not resume), and they update without a reload.

To delete a workflow, first switch the projects using it to another workflow. Issues keep their current status.

If **Settings** does not include **Workflows**, the feature is not available in this workspace yet, and statuses are still managed in **Settings → Issue Statuses**.

## Hold new requests in a project [#intake-hold]

A workspace can keep new top-level requests in **Backlog** for a time window, so people read and release them before agents start work. The rule is the workspace setting `intake_hold`: a list with one entry per project. Each entry has `project_id`, `mode`, `starts_at`, `ends_at`, `exempt_types`, `exempt_labels`, `exempt_escalation_classes`, `exempt_autopilot_ids`, `exempt_issue_ids` and `source`. An agent changes it with the workspace settings patch, which an owner approves with a passkey. A project with no entry is not affected. `source` is required, and every ID is a lowercase UUID with hyphens; a value that breaks either rule is refused when you save it.

The modes are `off` (nothing is held), `warn` and `block`. An issue is held while all of these are true: the entry's window is open (`starts_at` up to, not including, `ends_at`); the issue was created at or after `starts_at`; it has no parent; it is in Backlog, or was parked from Backlog by a decision request; no person has released it; and no exemption applies. In mode `block`, a status move that an agent or token makes on a held issue is refused with HTTP 409 and the code `intake_hold`, whether the issue is in Backlog or parked from it; the body carries `ends_at`, `fix` and `release_paths`. A move to `cancelled` is not refused. A create by an agent or token in the project that names a status other than `backlog` or `cancelled` is refused the same way; a create with no status lands in Backlog, and the new issue gets the metadata key `intake_hold` set to the entry `source`. A person's own move or create is never refused. In mode `warn`, nothing is refused and the server writes one `intake_hold_warn` log line.

`GET /api/issues/{id}` returns an `intake_hold` field with `source`, `held`, `owned`, `reason`, `ends_at` and `exempt_after`. `owned` stays true after `ends_at`, so you can tell an issue the hold covered from one it never covered. The field is absent for an issue with a parent and for a project with no entry. The list endpoints do not return it. `reason` is one of `held`, `ended`, `not_started`, `mode_off`, `created_before_start`, `left_backlog`, `released_by_member`, `exempt_type`, `exempt_label`, `exempt_escalation_class`, `exempt_autopilot` or `exempt_issue_id`. An issue whose title has no type, such as `plain words`, is held. Priority exempts nothing.

When an agent needs a person's decision on spend, deploy, publish, an irreversible action or product direction, it asks with a decision request. If the entry lists that class in `exempt_escalation_classes`, the person's answer lifts the hold for that one issue, 10 minutes after the answer. Until then `held` stays true and `exempt_after` shows the time the exemption starts. A withdrawn answer exempts nothing, and a `reversible` request never does. While the issue is still held, the request keeps its full flow, but delivering its answer or any other decision event (withdrawn, expired, asked again, retracted) starts no run. The delivery settles as `skipped_ineligible` and is not retried. In mode `warn` the delivery runs as usual. The same holds for a wait episode in a human-in-charge step (it closes and settles as `skipped_ineligible`, with no resume run), a person's discussion message on an open action card (the comment is stored and the wake is `skipped_ineligible`) and a person's revoke of an executed action (the revoke is stored and no run starts). The run that created the held issue can open that request on it too, while that run is still running; an agent that did not create the issue cannot, and a `reversible` request from the creating run is refused. The creating run must first post a comment on the issue, because the request quotes a comment on that issue.

A person releases an issue in one of two ways. Either they move it out of Backlog in the web app, the desktop app or the CLI signed in as themselves, or they move it out of a status the issue was parked in from Backlog, and the server records the release. A token that belongs to an agent or a cloud runtime never releases an issue. The server stores the release on the person's own status row, in the key `intake_release` of its details, set to the entry `source`. It writes the key only for a person's move that changes the status to something other than `backlog`, and only while the issue is covered by an open entry. The park, the unpark, system moves and moves made by an agent or a cloud runtime never carry it. A move out of the parked state releases the issue because of that key, so the release stays even when the move was made before the park and stored after it.

In mode `block`, a held issue also starts no run that is derived from it: an agent's mention or reply, an assignment to an agent or a squad, a wakeup that an agent created, an autopilot run, a rerun or an automatic retry. Each is refused with the dispatch reason `intake_hold`, which shows in `trigger_outcomes` or in the wakeup's `last_error`. A member's mention and a wakeup that a member created still start a run. An issue that a person released, or whose escalation answer is effective, is not held, so its runs start. A guard alert run on a held issue (decision wait guard, idle started guard, ask repair) is refused the same way and the guard records the refusal.

## Gate a step on intake or QA proof [#intake-qa-gates]

A step can carry entry gates: conditions a status move into the step must meet. Two gates read what an agent wrote on the issue. Add them to the step's `entry` list as `{"guard": "intake_simple", "mode": "warn", "param": "1"}`. The mode is `off`, `warn` or `block`; a gate that is not listed is off, and with every gate off an issue moves as before. In `warn` the move goes through and the issue gets one warning; in `block` the move is refused with the failed fact and a fix, and a person can pass it with a reason unless the gate sets `member_override` to `false`.

- `intake_simple` holds when the issue's description or comments carry the lines `Estimate:`, `Repos:`, `Schema change:`, `Security change:` and `Human decision:`, and the answers read as simple. The newest line of each kind counts. It fails when a line is missing or cannot be read, when the estimate (for example `1h` or `45m`) is over the gate's `param` (hours, above 0 and at most 24), when `Repos:` names more than one repository, when a yes/no line says `yes`, or while the issue has an open decision request. `param` is required.
- `qa_proof` holds when the agent making the move wrote a comment since the issue entered the current step with a `QA:` line that holds a link (`https://…`) or is followed by a fenced block, and the agent making the move set the issue's `post_close_work` metadata itself (its newest write; a value another actor or an earlier run left does not count). It takes no `param`. A comment by anyone else does not count.

Both gates fail closed: a value they cannot read counts as a failure. Neither is accepted as a transition guard. Each time `intake_simple` is checked, the issue's activity gets an `intake_call` row with `call` (`simple` or `rejected`), the raw `estimate` and the `step`.

`pr.none_open` is a third entry gate that reads PRs, not what an agent wrote. It holds when no open or draft PR is linked to the issue, or to its children when the workflow includes child PRs. Merged and closed PRs do not hold it back, and an issue with no PR passes. Put it on the step an agent closes into (for example `agent_accepted`) and give the step before it an `agent_done` edge to that step, so an agent can close an `in_review` issue that has nothing left to merge. An agent can never use the shortcut while a PR is open: the refusal lists each open PR (for example `acme/widget#12 (draft)`) with the fix, which is to merge or close it. Like the other entry gates it is not accepted as a transition guard, and `multica workflow lint` accepts it in `entry`.

## Check a workflow [#checks]

Open a saved workflow and select **Checks** to see what the server's lint found in it. The button shows the count of errors, warnings and notes. Each step card that has a finding carries the same marks, so you can see which step to open. The sheet lists the findings grouped by step. Filter them with the tabs **All**, **Errors**, **Warnings** and **Notes**. Each finding shows its message, a **Fix:** hint and its rule ID. **Go to step** selects that step in the editor. **Re-run** checks the saved workflow again. A waived finding stays in the list, muted, with its reason, and is not counted.

Checks judge the saved workflow, not your unsaved edits. The server judges the edits when you save. If the save has errors that are not waived, the server refuses it and the editor opens **Save refused: unresolved errors**. Fix the errors and save again, or type a reason and select **Save anyway**. The reason is sent as `lint_override`, up to 500 characters, and a save without one is refused. The editor keeps the text you typed until the save goes through. If the checks fail to run, saving stays allowed.
