A workspace is Multica's top-level boundary. Members, issues, projects, agents, skills, and run history all belong to one workspace and are fully isolated from every other.

## What a workspace contains

| Category | Contents |
|---|---|
| **Work** | Issues, projects, comments, attachments, run history |
| **Team** | Members, roles, invitations |
| **Agents** | Agent configuration, skills, runtimes, automations |
| **Shared settings** | Context, labels, [custom properties](/issues#custom-properties), integrations |

**Context** is provided to every agent in the workspace — the place for team background, product conventions, and long-lived requirements. One-off run requirements belong in the corresponding issue.

## Create a workspace

Creating a workspace asks for three things:

- **Name**: shown to members; can be changed later.
- **Workspace URL**: the slug in the address — the `my-team` in `multica.ai/my-team`. Lowercase letters, digits, and hyphens only; it cannot collide with an existing workspace or a reserved address, and it cannot be changed after creation.
- **Issue prefix**: pre-filled from the workspace URL and editable before you create — with the prefix `MUL`, issue numbers appear as `MUL-1`, `MUL-2`, counting up independently within the workspace. Uppercase letters and digits, up to 10 characters; it can be changed later in settings.

The creator automatically becomes an `owner`.

## Change settings

`owner` and `admin` can change the name, icon, description, context, and issue prefix; `member` can only view them.

![Workspace settings: name, context, slug, issue prefix, and the danger zone](/images/docs/workspace-settings.webp)

<Callout type="warning">
After the issue prefix changes, every issue immediately switches to the new number (`MUL-5` becomes `NEW-5`), but the old numbers in PRs, branch names, and chat history do not update.
</Callout>

### Auto-close

The workspace setting `auto_close` controls what happens when a child issue enters the `agent_accepted` or `merged` step and nothing is left to do. The step's agent would only close it, so the server can take the step's `agent_done` edge to `done` itself.

| Value | Effect |
| --- | --- |
| `off` | Nothing changes. The step's agent runs. |
| `warn` (default) | The step's agent runs as today. Each entry also records one `auto_close_would_close` activity row that names the checks that held and the run that followed. |
| `block` | The server moves the issue to `done`, records an `auto_closed` activity row that names the checks it read, and starts no run. |

A close needs every check below. If one fails or cannot be read, the step's agent runs as today.

- The issue has a parent. Root issues are never closed.
- The newest review verdict is a PASS with no P0 or P1 finding, and it is for the current candidate. With a PR, every linked PR is merged at the head the PASS names. Without a PR, the candidate is the issue's text: no attachment, description change, or comment (other than the reviewer's) came after the PASS, and neither did a CHANGES verdict, stale or superseded mark, or return to `in_progress`.
- No open child issue, no open decision request, and no wakeup that was live when the issue entered the step.
- The description has no `Blockers: Cheese stop` line, and the parent's `delivery_stop` metadata is not `stopped`.
- The issue metadata `post_close_work` is `none`. The author writes it: `multica issue metadata set <issue> --key post_close_work --value none --type string`. Any other value, such as a short description of the work that remains, keeps the run.
- The workflow has an `agent_done` edge from the step to `done`.
- On `merged` only: every linked PR is merged into its repository's default branch, at the head the PASS names. A PR merged into another branch (a stacked layer), or one whose delivery did not state its base or default branch, keeps the run.

Set the mode with `multica workspace update --auto-close-mode off|warn|block`. An unreadable value counts as `off`.

### Ask guard

The workspace setting `ask_guard_mode` controls what happens when an agent operation asks a person to act without opening a decision request.

| Value | Effect |
| --- | --- |
| `off` (default) | The guard does nothing. |
| `warn` | The guard records an event and a metric. The operation goes ahead. |
| `block` | The guard records the event first, then refuses the operation with `422`. Only `block` events become recovery work. |

### Autopilot assignment guard

The workspace setting `autopilot_assign_gate` controls what happens when an issue that names an autopilot (its id next to the word "autopilot") is assigned to an agent or squad and the person the run acts for cannot write that autopilot: not its creator, a workspace admin or a granted collaborator.

| Value | Effect |
| --- | --- |
| `block` (default) | The create or update is refused with `403` and code `autopilot_assign_no_write`. |
| `warn` | The server logs a warning. The assignment goes ahead. |
| `off` | The guard does nothing. |

Each event keeps the mode it was created under, so switching from `warn` to `block` does not turn earlier events into recovery work. If the event cannot be written, the operation fails with `503` and a `Retry-After` header, and nothing is written.

The workspace setting `reversible_ask_guard` (`off` by default, `warn`, `block`) covers a plain decision request from an agent whose class is `reversible`: the agent asks a person to approve work that agents may already decide and do themselves. `warn` logs it. `block` refuses it with `422`. Action, proposal and batch requests are unaffected. Set it back to `off` to revert; no data changes. The same setting covers a plain reply from an agent under a member's comment on an issue in `blocked` or `need_decision`, where the reply can ask that person without any decision request: `warn` logs it and `block` refuses it with `422`. Top-level comments, replies under an agent, comments that mention an agent or squad, comments with `--notify-only` and decision requests are unaffected.

The workspace setting `owner_script_guard` (`off`, `warn`, `block`; `warn` when unset) covers an agent's decision request, action request and `multica decision ask` card: the owner reads no shell, so a card that tells the person to run a command is a defect of the ask. Eight rules (R1 to R8, rule set version 1) read the card text and its steps: a shell code fence, a command in a fence or in inline code, a `human_steps` command, a script attachment, and a run cue such as "run" or "paste" next to a command or right after a flagged message. `warn` delivers the card and records the hit. `block` refuses it with `422`, names the rules and fields that hit, and points to `multica config propose`, `multica decision propose <type>` or a bot permission instead. `off` checks nothing. Each check writes one event, an `owner_script_guard` activity row, in the same transaction as the card, or on its own when the card is refused. The event holds ids, the outcome, `delivered`, `rule_hits`, keyed hashes of the commands (`cmd_hmacs`) and `retry_of`; it holds no message text. The issue timeline does not list these rows. Set it back to `warn` or `off` to revert; no data changes.

When the run that raised a `block` event has ended, the server sends the one person the ask names an automatic recovery notice: a DM message, an issue comment and an inbox item, written in one transaction. The notice quotes the stored ask, links the issue, and has no options, recommendation or approval, so it is never a decision request. It is sent only if the stored source has the ask text, names exactly one member, and that member is still in the workspace; otherwise the event waits for repair. Replying in the notice's comment thread marks it `answered`. A member who left the workspace can no longer read or answer it.

An event that cannot be sent as a notice goes to the agent whose run produced it instead: one repair run per recovery root, started through the normal run gates (project stops, run budget, role and approval gates). The first `block` event is the root, and an event raised by a repair run inherits it, so a repair never starts a second repair. The run message holds the exact `multica decision request ... --recovers <event-id>` command and no source text. A refused run, an unavailable agent, a repair run that ends without a matching request, or a new ask raised by the repair run fails the root. The agent is its owner: one system comment on the issue names the agent and mentions no member, and `multica decision brief` lists the failure with an excerpt of the ask. Runs in a chat lane only raise `warn` events, so they are never repaired.

The guard also covers an agent registering a wakeup that a person can trigger. Bind it with `--decision`, mark it `--purpose observe`, or limit it to agents; see [Wakeups](/cli#wakeups).

### Held-setting ask guard

The workspace setting `held_setting_ask_mode` (`off` by default, `warn` or `block`) controls what happens when a decision or action request asks a person for a workspace setting the workspace settings already hold. The request names the keys in the typed field `settings_needed`; the server never reads the prose. A key counts as held when its stored value is not null, not an empty string, list or object. Key names compare without case.

| Value | Effect |
| --- | --- |
| `off` (default) | The guard does nothing. |
| `warn` | The request is created and the response carries one hint per held key. |
| `block` | The request is refused with `400` and no request row. The message names the key and never the stored value. |

To revert, set `held_setting_ask_mode` to `off`. No data changes.

### Delegated governed writes

The workspace setting `delegated_governed_writes` decides which agents may write governed fields, and whether each write still needs a person's decision. Find it in workspace settings under **Delegated governed writes**.

- **Who can edit:** `owner` and `admin`. A `member` sees the same table read-only, with a lock note and no Edit button.
- **Allowed agents:** the agents that may write. An archived agent cannot be added.
- **Allowed fields:** any of `workflow.steps`, `workflow.instructions`, `workspace.context`, `squad.instructions`, `agent.instructions`, `project.description`, `workflow.budget`, `issue.workflow`. Fields you do not tick stay read-only for every agent.
- **Requires human decision:** on by default. An allowed agent then opens a decision request instead of writing. Turning it off lets allowed agents write directly, so Save asks you to confirm first.

Unsaved edits are kept if a save fails, so nothing you typed is lost.

## Switch and leave

One account can join multiple workspaces. Switching only changes what you are currently viewing; it moves no data.

After leaving a workspace, you need a new invitation to return. Leaving also deactivates the runtimes you own, archives the agents bound to them, and cancels their unfinished runs.

The last `owner` cannot leave; promote another member to `owner` first.

## Delete a workspace

Only an `owner` can delete a workspace. Deletion permanently removes all of its work, members, agent configuration, and run history, and cannot be undone. If you are only stepping away for a while, leave instead of deleting.
