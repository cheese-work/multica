A workspace is Multica's top-level boundary. Members, issues, projects, agents, skills, and run history all belong to one workspace and are fully isolated from every other.

## What a workspace contains

| Category | Contents |
|---|---|
| **Work** | Issues, projects, comments, attachments, run history |
| **Team** | Members, roles, invitations |
| **Agents** | Agent configuration, skills, runtimes, automations |
| **Shared settings** | Context, labels, [custom properties](/issues#custom-properties), integrations |

**Context** is provided to every agent in the workspace — the place for team background, product conventions, and long-lived requirements. One-off run requirements belong in the corresponding issue.

## Create a workspace

Creating a workspace asks for three things:

- **Name**: shown to members; can be changed later.
- **Workspace URL**: the slug in the address — the `my-team` in `multica.ai/my-team`. Lowercase letters, digits, and hyphens only; it cannot collide with an existing workspace or a reserved address, and it cannot be changed after creation.
- **Issue prefix**: pre-filled from the workspace URL and editable before you create — with the prefix `MUL`, issue numbers appear as `MUL-1`, `MUL-2`, counting up independently within the workspace. Uppercase letters and digits, up to 10 characters; it can be changed later in settings.

The creator automatically becomes an `owner`.

## Change settings

`owner` and `admin` can change the name, icon, description, context, and issue prefix; `member` can only view them.

![Workspace settings: name, context, slug, issue prefix, and the danger zone](/images/docs/workspace-settings.webp)

<Callout type="warning">
After the issue prefix changes, every issue immediately switches to the new number (`MUL-5` becomes `NEW-5`), but the old numbers in PRs, branch names, and chat history do not update.
</Callout>

### Ask guard

The workspace setting `ask_guard_mode` controls what happens when an agent operation asks a person to act without opening a decision request.

| Value | Effect |
| --- | --- |
| `off` (default) | The guard does nothing. |
| `warn` | The guard records an event and a metric. The operation goes ahead. |
| `block` | The guard records the event first, then refuses the operation with `422`. Only `block` events become recovery work. |

Each event keeps the mode it was created under, so switching from `warn` to `block` does not turn earlier events into recovery work. If the event cannot be written, the operation fails with `503` and a `Retry-After` header, and nothing is written.

When the run that raised a `block` event has ended, the server sends the one person the ask names an automatic recovery notice: a DM message, an issue comment and an inbox item, written in one transaction. The notice quotes the stored ask, links the issue, and has no options, recommendation or approval, so it is never a decision request. It is sent only if the stored source has the ask text, names exactly one member, and that member is still in the workspace; otherwise the event waits for repair. Replying in the notice's comment thread marks it `answered`. A member who left the workspace can no longer read or answer it.

The guard also covers an agent registering a wakeup that a person can trigger. Bind it with `--decision`, mark it `--purpose observe`, or limit it to agents; see [Wakeups](/cli#wakeups).

### Delegated governed writes

The workspace setting `delegated_governed_writes` decides which agents may write governed fields, and whether each write still needs a person's decision. Find it in workspace settings under **Delegated governed writes**.

- **Who can edit:** `owner` and `admin`. A `member` sees the same table read-only, with a lock note and no Edit button.
- **Allowed agents:** the agents that may write. An archived agent cannot be added.
- **Allowed fields:** any of `workflow.steps`, `workflow.instructions`, `workspace.context`, `squad.instructions`, `agent.instructions`, `project.description`, `workflow.budget`, `issue.workflow`. Fields you do not tick stay read-only for every agent.
- **Requires human decision:** on by default. An allowed agent then opens a decision request instead of writing. Turning it off lets allowed agents write directly, so Save asks you to confirm first.

Unsaved edits are kept if a save fails, so nothing you typed is lost.

## Switch and leave

One account can join multiple workspaces. Switching only changes what you are currently viewing; it moves no data.

After leaving a workspace, you need a new invitation to return. Leaving also deactivates the runtimes you own, archives the agents bound to them, and cancels their unfinished runs.

The last `owner` cannot leave; promote another member to `owner` first.

## Delete a workspace

Only an `owner` can delete a workspace. Deletion permanently removes all of its work, members, agent configuration, and run history, and cannot be undone. If you are only stepping away for a while, leave instead of deleting.
