워크스페이스는 Multica의 최상위 경계입니다. 멤버, 태스크, 프로젝트, 에이전트, 스킬, 실행 기록은 모두 하나의 워크스페이스에 속하며, 다른 워크스페이스와는 서로 공유되지 않습니다.

## 워크스페이스의 구성

| 범주 | 내용 |
|---|---|
| **작업** | 태스크, 프로젝트, 댓글, 첨부 파일, 실행 기록 |
| **팀** | 멤버, 역할, 초대 |
| **에이전트** | 에이전트 설정, 스킬, 런타임, 자동화 |
| **공유 설정** | 컨텍스트, 라벨, [사용자 지정 속성](/issues#사용자-지정-속성), 연동 |

**컨텍스트**는 워크스페이스의 모든 에이전트에게 제공됩니다. 팀 배경, 제품 규칙, 장기적으로 적용되는 요구 사항을 작성하기에 적합합니다. 일회성 요구 사항은 해당 태스크에 작성하세요.

## 워크스페이스 만들기

만들 때 세 항목을 입력합니다.

- **이름**: 멤버에게 표시되며 나중에 변경할 수 있습니다.
- **워크스페이스 URL**: 주소에 들어가는 slug입니다. 예를 들어 `multica.ai/my-team`의 `my-team`입니다. 소문자, 숫자, 하이픈만 사용할 수 있고 기존 워크스페이스 또는 예약된 주소와 중복될 수 없으며 만든 뒤에는 변경할 수 없습니다.
- **태스크 접두사**: 워크스페이스 URL에서 자동으로 채워지며 만들기 전에 바꿀 수 있습니다. 접두사가 `MUL`이면 태스크 번호는 `MUL-1`, `MUL-2`처럼 표시되며 워크스페이스 안에서 독립적으로 증가합니다. 대문자와 숫자만, 최대 10자이며 나중에 설정에서도 바꿀 수 있습니다.

만든 사람은 자동으로 `owner`가 됩니다.

## 설정 변경

`owner`와 `admin`은 이름, 아이콘, 설명, 컨텍스트, 태스크 접두사를 변경할 수 있습니다. `member`는 보기만 할 수 있습니다.

<Callout type="warning">
태스크 접두사를 변경하면 모든 태스크가 즉시 새 번호를 사용합니다(`MUL-5`가 `NEW-5`로 변경). 하지만 PR, 브랜치 이름, 채팅 기록의 이전 번호는 업데이트되지 않습니다.
</Callout>

### 자동 닫기

워크스페이스 설정 `auto_close`는 하위 태스크가 `agent_accepted` 또는 `merged` 단계에 들어왔고 남은 일이 없을 때의 동작을 정합니다. 단계의 에이전트는 태스크를 닫기만 할 것이므로, 서버가 단계의 `agent_done` 엣지를 따라 직접 `done`으로 옮길 수 있습니다.

| 값 | 효과 |
| --- | --- |
| `off` | 아무것도 바뀌지 않습니다. 단계의 에이전트가 실행됩니다. |
| `warn` (기본값) | 단계의 에이전트가 기존처럼 실행됩니다. 진입할 때마다 충족된 검사와 이어진 실행을 적은 `auto_close_would_close` 활동 행이 하나 기록됩니다. |
| `block` | 서버가 태스크를 `done`으로 옮기고, 읽은 검사를 적은 `auto_closed` 활동 행을 기록하며, 실행은 시작하지 않습니다. |

닫으려면 아래 검사를 모두 통과해야 합니다. 하나라도 실패하거나 읽을 수 없으면 단계의 에이전트가 기존처럼 실행됩니다.

- 태스크에 상위 태스크가 있습니다. 루트 태스크는 닫지 않습니다.
- 가장 최근 리뷰 판정이 P0·P1 지적이 없는 PASS이고, 현재 후보에 대한 것입니다. PR이 있으면 연결된 모든 PR이 PASS가 가리키는 head로 병합되어 있어야 합니다. PR이 없으면 후보는 태스크의 텍스트입니다. PASS 이후 첨부 파일, 설명 변경, 댓글(리뷰어 본인의 댓글 제외), CHANGES 판정, 오래됨·대체됨 표시, `in_progress`로의 복귀가 없어야 합니다.
- 열린 하위 태스크가 없고, 열린 결정 요청이 없으며, 태스크가 단계에 들어올 때 활성이던 웨이크업(태스크 자체의 병합 감시, 즉 `pr.merged` 엣지는 제외)이 없습니다.
- 설명에 `Blockers: Cheese stop` 줄이 없고, 상위 태스크의 `delivery_stop` 메타데이터가 `stopped`가 아닙니다.
- 태스크 메타데이터 `post_close_work`가 `none`입니다. 작성자가 기록합니다: `multica issue metadata set <issue> --key post_close_work --value none --type string`. 남은 작업을 짧게 적은 값 등 다른 값이면 실행이 유지됩니다.
- 워크플로에 해당 단계에서 `done`으로 가는 `agent_done` 또는 `pr.merged` 엣지가 있습니다.
- `merged`에서만: 연결된 모든 PR이 PASS가 가리키는 head로 저장소의 기본 브랜치에 병합되어 있습니다. 다른 브랜치(스택의 한 층)에 병합된 PR이나 전달에 base 또는 기본 브랜치가 없던 PR이 있으면 실행이 유지됩니다.

PASS가 가리키는 head의 PR이 아직 열려 있어도, 단계에 `done`으로 가는 `pr.merged` 엣지와 태스크 자체의 감시가 있으면 실행은 유지되지 않습니다. 서버는 실행을 시작하지 않고 `auto_close_pending_merge` 활동 행을 하나 기록합니다. 이후 병합이 실행 없이 태스크를 닫습니다. 병합 시 서버는 모든 조건을 다시 확인합니다. 조건이 하나라도 충족되지 않으면(PASS 없는 새 head, 새 활성 웨이크업 등) 닫지 않고 단계의 실행을 시작하며 감시를 제거합니다.

모드는 `multica workspace update --auto-close-mode off|warn|block`으로 설정합니다. 읽을 수 없는 값은 `off`로 취급합니다.

### 차단 진입 실행 건너뛰기

워크스페이스 설정 `blocked_run_skip`은 태스크가 `blocked`에 들어올 때 차단 단계의 실행을 시작할지 정합니다. 태스크가 무엇을 기다리는지 밝혔고 단계 담당자에게 작업을 이어갈 웨이크업이 이미 있을 때만 서버가 이 실행을 건너뜁니다.

| 값 | 동작 |
| --- | --- |
| `off` | 아무것도 바뀌지 않습니다. 차단 단계의 에이전트가 진입 시 실행됩니다. |
| `warn` (기본값) | 기존처럼 실행이 시작됩니다. 건너뛰었을 진입마다 이어진 실행을 적은 `blocked_entry_would_skip` 활동 행이 하나 기록됩니다. |
| `block` | 서버가 실행을 시작하지 않고 `blocked_entry_linked` 활동 행을 기록하며 웨이크업을 활성 상태로 둡니다. |

아래를 모두 만족할 때만 실행을 건너뜁니다. 하나라도 실패하거나 읽을 수 없으면 기존처럼 실행이 시작됩니다.

- 태스크 메타데이터 `blocked_on`이 설정되어 있습니다(`multica issue status <id> blocked --blocked-on <ref>`).
- 차단 단계의 담당자가 이 태스크에 같은 참조를 기다리는 활성 조건 웨이크업을 가지고 있습니다. 플래그, 대상, 상태·단계·종류가 모두 같아야 합니다. 시간 웨이크업, 다른 조건, 다른 에이전트의 웨이크업은 해당하지 않습니다.
- 그 웨이크업에 `last_error`가 없고, 7일 안에 끝나며, `--on-timeout wake`를 사용합니다.
- 실행이 승인됩니다: 태스크에 실행 예산이 남아 있고 에이전트가 일시 중지되지 않았습니다.

연결된 웨이크업이 나중에 비활성화·삭제되거나, `last_error`가 생기거나, 실행 없이 끝나거나(만료 또는 가드가 거부), `blocked_on`과 더 이상 일치하지 않으면 서버가 차단 단계의 실행을 시작하고 `blocked_entry_rearmed` 활동 행을 기록합니다. 실행 예산이 소진되었거나 에이전트가 일시 중지된 경우 그 실행도 거부되며 행에 그 사실이 기록됩니다.

### 실행 한도

두 워크스페이스 설정이 태스크가 실행 한도를 모두 사용했을 때의 동작을 정합니다. 각각 `{"mode": "off" | "warn" | "block"}`이며 기본값은 현재 동작인 `block`입니다.

| 설정 | 제어하는 한도 |
| --- | --- |
| `run_budget` | 태스크 워크플로의 태스크별 실행 예산(`max_runs_per_issue`). |
| `run_guard` | 주간 실행 가드: 태스크가 7일 동안 시작하는 실행 수. |

| 값 | 효과 |
| --- | --- |
| `block` | 다음 파생 실행이 거부되고 소유자에게 카드가 갑니다. |
| `warn` | 실행은 계속 집계되고 초과분은 브리프와 `multica issue budget get`(`state: warn`)에 표시됩니다. 실행이 거부되지 않고, 태스크가 차단되지 않으며, 카드도 열리지 않습니다. |
| `off` | 차단, 경고, 카드가 모두 없습니다. |

루프 차단기(`MULTICA_LOOP_BREAKER_MAX_RUNS`)는 바뀌지 않습니다. 모드는 `multica workspace update --run-budget-mode` 또는 `--run-guard-mode`로 설정하며, 에이전트는 `workspace.settings` 카드에서 `run_budget` 또는 `run_guard`를 제안합니다.

### 요청 가드

워크스페이스 설정 `ask_guard_mode`는 에이전트 작업이 결정 요청을 열지 않고 사람에게 작업을 요구할 때의 동작을 정합니다.

| 값 | 동작 |
| --- | --- |
| `off` (기본값) | 가드는 아무 일도 하지 않습니다. |
| `warn` | 가드가 이벤트와 메트릭을 기록합니다. 작업은 그대로 진행됩니다. |
| `block` | 가드가 먼저 이벤트를 기록한 뒤 `422`로 작업을 거부합니다. 복구 작업이 되는 것은 `block` 이벤트뿐입니다. |

### 머지 큐 설정

워크스페이스 설정 3개가 머지 큐를 구성합니다. 소유자만 쓸 수 있으며, 모든 쓰기 경로(`multica workspace update` 플래그, 설정 저장, `config propose` 액션)가 같은 검증기를 거칩니다.

| 설정 | 값 |
| --- | --- |
| `merge_queue_dequeue_routing` | `off`(기본값) 또는 `warn`. 강제 기능이 제공되기 전까지 `block`은 `routing-not-available`로 거부됩니다. |
| `merge_queue_actor_bindings` | `{"agents": [...], "people": [...]}`. 두 목록에 모두 있는 GitHub 로그인은 거부됩니다. |
| `merge_queue_watch_issue` | 머지 큐 이벤트를 받는 이슈. 비워 둘 수 있습니다. |

### 오토파일럿 할당 가드

워크스페이스 설정 `autopilot_assign_gate`는 오토파일럿을 지목하는 이슈(해당 id가 "autopilot" 단어 근처에 있음)를 에이전트나 스쿼드에 할당했는데, 실행이 대행하는 사람이 그 오토파일럿에 쓸 수 없는 경우(생성자, 워크스페이스 관리자, 허용된 협업자가 아님)의 동작을 정합니다.

| 값 | 동작 |
| --- | --- |
| `block`(기본값) | 생성 또는 업데이트가 `403`과 코드 `autopilot_assign_no_write`로 거부됩니다. |
| `warn` | 서버가 경고를 기록합니다. 할당은 그대로 진행됩니다. |
| `off` | 가드는 아무 동작도 하지 않습니다. |

각 이벤트는 생성 당시의 모드를 유지하므로 `warn`에서 `block`으로 바꿔도 이전 이벤트가 복구 작업이 되지 않습니다. 이벤트를 기록할 수 없으면 작업은 `503`과 `Retry-After` 헤더로 실패하며 아무것도 기록되지 않습니다.

워크스페이스 설정 `reversible_ask_guard`(기본값 `off`, `warn`, `block`)는 클래스가 `reversible`인 에이전트의 일반 결정 요청을 다룹니다. 에이전트가 스스로 결정하고 실행해도 되는 작업에 대해 사람에게 승인을 요청하는 경우입니다. `warn`은 로그에 남기고 `block`은 `422`로 거부합니다. 액션, 제안, 배치 요청은 영향을 받지 않습니다. 되돌리려면 `off`로 설정하세요. 데이터는 바뀌지 않습니다. 같은 설정은 `blocked` 또는 `need_decision` 상태 이슈에서 멤버의 댓글에 에이전트가 단 일반 답글도 다룹니다. 이 답글은 결정 요청 없이 그 사람에게 물을 수 있습니다. `warn`은 로그에 남기고 `block`은 `422`로 거부합니다. 최상위 댓글, 에이전트에 대한 답글, 에이전트나 스쿼드를 멘션한 댓글, `--notify-only` 댓글, 결정 요청은 영향을 받지 않습니다.

워크스페이스 설정 `owner_script_guard`(`off`, `warn`, `block`, 설정하지 않으면 `warn`)는 에이전트의 결정 요청, 액션 요청, `multica decision ask` 카드를 다룹니다. 소유자는 셸을 읽지 않으므로, 사람에게 명령을 실행하라고 하는 카드는 요청 자체의 결함입니다. 규칙 8개(R1~R8, 규칙 세트 버전 1)가 카드 텍스트와 단계를 읽습니다. 셸 코드 펜스, 펜스나 인라인 코드 안의 명령, `human_steps`의 명령, 스크립트 첨부 파일, 명령 옆이나 표시된 메시지 직후에 나오는 "run", "paste" 같은 실행 표현이 대상입니다. `warn`은 카드를 전달하고 적중을 기록합니다. `block`은 `422`로 거부하고, 적중한 규칙과 필드를 알려 주며 `multica config propose`, `multica decision propose <type>` 또는 봇 권한 요청을 안내합니다. `off`는 검사하지 않습니다. 검사마다 이벤트 하나, 즉 `owner_script_guard` 활동 행이 기록됩니다. 카드가 전달되면 카드와 같은 트랜잭션에, 거부되면 별도 커밋에 기록됩니다. 이벤트에는 ID, 결과, `delivered`, `rule_hits`, 명령의 키 해시(`cmd_hmacs`), `retry_of`가 들어가며 메시지 텍스트는 없습니다. 이슈 타임라인에는 이 행이 표시되지 않습니다. 되돌리려면 `warn` 또는 `off`로 설정하세요. 데이터는 바뀌지 않습니다.

워크스페이스 설정 `waiting_audience_guard`(기본값 `off`, `warn`, `block`)는 `in_review`, `blocked`, `need_decision` 상태 이슈에 대한 에이전트의 댓글을 다룹니다. 이 댓글에는 대상이 있어야 합니다. 멤버 멘션, `notify_only`, 결정 댓글, `ask`(다음에 행동할 멤버), `no_ask` 중 하나입니다. 에이전트나 스쿼드 멘션, 에이전트 댓글에 대한 답글도 대상으로 인정됩니다. 이러한 타입 필드와 링크만 읽으며 댓글 본문은 읽지 않습니다. `warn`은 히트를 기록하고 댓글을 게시하며, `block`은 히트를 기록한 뒤 댓글을 `422`로 거부합니다. 채팅 레인 실행은 경고만 합니다. `off`로 되돌리면 원래대로 복구되며 데이터는 변경되지 않습니다.

워크스페이스 설정 `waiting_on_guard`(기본값 `off`, `warn`, `block`)는 에이전트가 이슈를 `in_review`, `blocked`, `need_decision`으로 옮길 때를 다룹니다. 이동에는 `waiting_on`(`member:<id>` 또는 `none`)으로 다음에 행동할 사람을 밝혀야 합니다. 해당 이슈에 결정 요청이나 멤버 멘션이 있는 댓글을 이미 게시한 작업은 `waiting_on`이 필요 없습니다. 타입 필드와 구조적 링크만 읽으며 이전 댓글의 본문은 읽지 않습니다. `warn`은 히트를 기록하고 이슈를 옮기며, `block`은 히트를 기록한 뒤 이동을 `422`로 거부합니다. 채팅 레인 실행은 경고만 합니다. `off`로 되돌리면 원복되며 데이터는 바뀌지 않습니다.

`block` 이벤트를 만든 실행이 끝나면 서버는 요청이 지목한 한 사람에게 자동 복구 알림을 보냅니다. DM 메시지, 이슈 댓글, 받은 편지함 항목을 하나의 트랜잭션으로 기록합니다. 알림은 저장된 요청을 인용하고 이슈 링크를 담으며 선택지, 권장안, 승인이 없으므로 결정 요청이 아닙니다. 저장된 원본에 요청 텍스트가 있고, 멤버가 정확히 한 명 지목되며, 그 멤버가 아직 워크스페이스에 있을 때만 전송됩니다. 그렇지 않으면 이벤트는 복구(repair)를 기다립니다. 알림의 댓글 스레드에 답하면 `answered`가 됩니다. 워크스페이스를 떠난 멤버는 알림을 읽거나 답할 수 없습니다.

알림으로 보낼 수 없는 이벤트는 대신 그 이벤트를 만든 실행의 에이전트로 갑니다. 복구 루트마다 수리 실행은 하나이며, 일반 실행 게이트(프로젝트 중지, 실행 예산, 역할 및 승인 게이트)를 거쳐 시작됩니다. 첫 `block` 이벤트가 루트이고, 수리 실행이 만든 이벤트는 그 루트를 물려받으므로 수리가 두 번째 수리를 시작하는 일은 없습니다. 실행 메시지에는 정확한 `multica decision request ... --recovers <event-id>` 명령이 들어가고 원문은 들어가지 않습니다. 실행이 거부되거나, 에이전트를 쓸 수 없거나, 수리 실행이 일치하는 요청 없이 끝나거나, 수리 실행이 새 요청을 만들면 루트가 실패합니다. 에이전트가 소유자이며, 이슈에는 에이전트 이름을 밝히고 멤버를 멘션하지 않는 시스템 댓글이 하나 달리고, `multica decision brief`가 요청 발췌와 함께 실패를 나열합니다. 채팅 레인의 실행은 `warn` 이벤트만 만들기 때문에 수리되지 않습니다.

가드는 에이전트가 사람이 트리거할 수 있는 웨이크업을 등록하는 작업도 다룹니다. `--decision`으로 묶거나, `--purpose observe`로 표시하거나, 에이전트로만 제한하세요. [웨이크업](/cli#wakeups)을 참고하세요.

워크스페이스 설정 `long_thread_member_ask`(기본값 `off`, `warn`, `move`)는 긴 스레드에서 멤버를 멘션하는 에이전트 댓글을 다룹니다. `long_thread_member_ask_min`(3~100 사이의 정수, 기본값 10)은 이 설정이 적용되는 스레드 크기입니다(루트 포함). `move`는 댓글을 원래 스레드로 연결되는 새 질문 스레드로 열고, `warn`은 힌트와 함께 그 자리에 게시합니다. 이 설정은 댓글의 위치만 정하며 거부하지 않습니다. 기본값에서는 아무것도 바뀌지 않습니다. 해당할 때마다 모드가 `move` 또는 `warn`인 가드 이벤트가 하나 기록되며, 복구·수리 처리는 이를 읽지 않습니다. 서버가 두 값을 검증하며, 잘못된 값은 `400`으로 거부됩니다.

워크스페이스 설정 `decision_reask_thread`(기본값 `off`, `warn`, `block`)는 같은 에이전트가 같은 이슈에서 같은 멤버에게 30일 안에 보내는 두 번째 결정 카드를 다룹니다. `--reask-of <request id>`(카드가 그 카드의 스레드로 들어가고 열려 있는 이전 카드는 철회됨)나 `--new-topic`(카드가 자체 스레드를 시작함)이 없으면 `block`은 409와 두 플래그를 설명하는 문구로 카드를 거부하고 ask 가드 로그에 `refused` 행을 하나 기록합니다. `warn`은 카드를 만들고 같은 문구를 힌트로 반환하며 `warn` 행을 하나 기록합니다. 거부는 처리되지 않은 질문이 아니므로 복구 알림도 수리 실행도 뒤따르지 않습니다.

### 도구 가드

**설정 → Guard**에는 워크스페이스의 도구 가드 플러그인과 각 플러그인이 최근 7일 동안 한 일이 나열됩니다. 플러그인마다 수정·거부·오류가 난 호출 수, 일별 적중 차트, 최근 판정을 볼 수 있습니다. 수치는 `multica guard stats`, `multica guard log`와 같은 행에서 가져옵니다. 날짜는 보기 시간대를 따릅니다.

워크스페이스 소유자는 여기서 워크스페이스 수준 규칙을 편집할 수 있습니다. **패스키로 편집**으로 동작과 메시지를 바꾸면, 소유자가 그 변경 자체에 패스키로 서명합니다. 서명은 편집을 시작한 정책 버전을 가리킵니다. 그 사이 다른 변경이 들어왔다면 아무것도 저장되지 않고, 페이지가 두 버전과 **다시 적용**(새 버전 위에 새 패스키로 변경 적용), **현재 버전 불러오기**, **버리기**를 보여 줍니다. 멤버에게는 읽기 전용으로 표시됩니다. 조직·저장소·경로 계층에 속한 규칙은 CLI로 편집합니다. 에이전트가 `multica guard plugin set`으로 변경을 만들고, 담당자가 결정 카드에서 패스키로 승인합니다. 저장된 정책이 없으면 기본 제공 기본값이 표시됩니다.

### 결정 화면

워크스페이스 설정 `decision_screen`(기본값 `off`, `on` 가능)은 에이전트의 결정 요청을 담는 채팅 레인을 숨깁니다. `on`이면 이슈 에이전트가 멤버에게 보내는 요청은 그 에이전트와 볼 수 있는 DM이 있어도 숨겨진 백킹 레인으로 들어갑니다. 그 DM에는 아무것도 게시되지 않습니다. 이 레인은 멤버의 채팅 목록, 읽지 않음 수, 배지, "Needs you" 목록에 나타나지 않으며 멤버는 이 레인에 메시지를 보낼 수 없습니다(`409`). 요청 자체는 이전과 같은 결정 카드를 엽니다. 이 에이전트의 경우 서버는 `session_id`와 `new_dm`을 무시하고 응답에 힌트를 하나 추가합니다. DM에서 요청하는 에이전트는 계속 그 DM에서 요청합니다. 되돌리려면 `off`로 설정하세요. 새 레인은 만들어지지 않고 기존 레인은 계속 숨겨집니다.

### 위임된 거버넌스 대상 쓰기

워크스페이스 설정 `delegated_governed_writes`는 어떤 에이전트가 거버넌스 대상 필드에 쓸 수 있는지, 그리고 각 쓰기에 사람의 결정이 여전히 필요한지를 정합니다. 워크스페이스 설정의 **위임된 거버넌스 대상 쓰기**에 있습니다.

- **편집 가능한 사람:** `owner`와 `admin`. `member`는 같은 표를 읽기 전용으로 보며, 잠금 안내가 표시되고 편집 버튼은 없습니다.
- **허용된 에이전트:** 쓸 수 있는 에이전트. 보관된 에이전트는 추가할 수 없습니다.
- **허용된 필드:** `workflow.steps`, `workflow.instructions`, `workspace.context`, `squad.instructions`, `agent.instructions`, `project.description`, `workflow.budget`, `issue.workflow` 중에서 고릅니다. 선택하지 않은 필드는 모든 에이전트에게 읽기 전용으로 남습니다.
- **사람의 결정 필요:** 기본값은 켜짐입니다. 켜져 있으면 허용된 에이전트는 쓰는 대신 결정 요청을 엽니다. 끄면 허용된 에이전트가 직접 쓰므로, 저장하기 전에 확인을 요구합니다.

저장에 실패해도 저장되지 않은 편집은 유지되므로 입력한 내용이 사라지지 않습니다.

## 전환 및 나가기

하나의 계정으로 여러 워크스페이스에 참여할 수 있습니다. 워크스페이스를 전환하면 지금 보고 있는 범위만 바뀌고 데이터는 옮겨지지 않습니다.

워크스페이스를 나가면 다시 참여하려면 초대를 새로 수락해야 합니다. 나갈 때는 본인이 소유한 런타임도 비활성화되고, 해당 런타임에 연결된 에이전트는 보관 처리되며, 완료되지 않은 실행은 취소됩니다.

마지막 `owner`는 워크스페이스를 나갈 수 없습니다. 먼저 다른 멤버를 `owner`로 승격해야 합니다.

## 워크스페이스 삭제

워크스페이스는 `owner`만 삭제할 수 있습니다. 삭제하면 그 안의 모든 작업, 멤버, 에이전트 설정, 실행 기록이 영구적으로 제거되며 복구할 수 없습니다. 잠시 참여하지 않을 뿐이라면 나가기만 해도 충분합니다.
