The Multica CLI both connects local runtimes and manages workspaces, issues, agents, and automations from the terminal. This page covers the common paths; the flags your installed version supports are always defined by each command's own `--help`.

## First connection

Pick the service you are connecting to:

<Tabs items={["Multica Cloud", "Self-hosted instance"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="Self-hosted instance">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup` saves the server address, opens a browser to complete sign-in, and starts the daemon. When it finishes, check:

```bash
multica auth status
multica daemon status
```

If you only need to sign in again without overwriting other configuration, run `multica login`. On a machine without a browser, create a personal access token in the web settings first, then enter it with:

```bash
multica login --token
```

The command prompts you to paste the token in the terminal, keeping the full value out of shell history.

## Choosing a workspace

List workspaces and switch the default:

```bash
multica workspace list
multica workspace switch <slug>
```

Subsequent commands use this workspace. A single command can override it with `--workspace-id`, or you can set `MULTICA_WORKSPACE_ID`.

Invite members:

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## Common issue operations

```bash
# View and search
multica issue list
multica issue get MUL-123
multica issue search "login failure"

# Create and update
multica issue create --title "Fix login failure"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# Comments and runs
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "Check the regression tests first"
multica issue comment update <comment-id> --expected-revision 2 --content "Check the regression tests and release notes"
multica issue runs MUL-123
```

Read long descriptions or comments from stdin to avoid dealing with newlines and quoting:

```bash
multica issue create --title "Upgrade notes" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

Inspect, stop, or retry a single run:

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123 --fresh
```

Add a comment to a run that is still working, instead of queueing a follow-up run (only runs that accept additional messages; you can steer an agent exactly when your comment could start it):

```bash
multica issue comment add MUL-123 --content-file note.md --steer <task-id>
multica issue comment add MUL-123 --content-file note.md --steer-active
```

A comment from an agent task that mentions a member (`[@Name](mention://member/<id>)`) is accepted only as a decision request, a `--decision-intent`, `--decision-record` or `--decision-veto` comment, or a comment with `--notify-only`. Use `--notify-only` for an FYI that needs no answer. It never opens a wait and never counts as a decision request. It cannot combine with the decision flags. The check reads the mention link, not the wording, and a link inside code counts. The workspace setting `ask_guard_mode` (`off`, `warn`, `block`) decides whether a refused comment is only logged or returns 422. Chat tasks and calls without a task only log. An edit that adds a member mention follows the same rule.

```bash
multica issue comment add MUL-123 --content-file fyi.md --notify-only
```

## Forking a web DM

From the source DM's running chat task, copy the DM into a new child DM:

```bash
multica chat continue --fork
```

The source stays active and unchanged. The child gets a full copy of the messages the person can see, with their original times, and of their attachments; it holds no summary. It keeps the same agent, creator and project, with a title ending in ` (fork)`, and starts with no provider session and no managed checkout. Decisions, approvals, task tokens and lane summaries stay with the source. The agent's private tool memory is not copied. Agent-builder DMs cannot be forked.

On the child's first turn, and on any turn with no provider session to resume, the agent receives a fork context block: a notice, an index of the copied attachments, and the newest messages of the DM that fit in 64 KiB. When older messages are left out, the block says so; read them with `multica chat history`.

The default fork operation key is the current turn: an auto-retry of the same turn returns the same child. To create another fork in that turn, use a different explicit key; reuse that key when retrying:

```bash
multica chat continue --fork --idempotency-key explore-alternative
```

A task fork does not send a message. `--summary-file` is not accepted with `--fork`.

The session-human API is `POST /api/chat/sessions/{sessionId}/fork` with a required `idempotency_key` and an optional `message` in the JSON body. With a message, the server sends it as the person's first message in the child and starts the agent's first turn in the same transaction; without one, the child is idle. A retry with the same key returns the same child (HTTP 200) and sends nothing twice. The task-scoped API is `POST /api/chat/fork`. Session responses expose `forked_from_session_id`, `fork_last_message_id` and `fork_message_count` on children. Only web DMs with at least one message can be forked. Without `--fork`, `chat continue` still archives the source and requires `--summary-file`; `/compact` is unchanged.

### `/fork` in the web app

Type `/fork [message]` as the first word of a web DM message. The web app forks the DM directly, with no agent turn: the new DM is a full copy of the visible messages and attachments, and the source stays active with a "Forked into" link. You land in the new DM. With a message, the agent answers it at once; without one, the new DM is idle until you send a first message. The agent in the new DM starts a fresh session and gets the transcript in a context block capped at 64 KiB (newest messages first); it reads earlier ones with `multica chat history`. The agent's private tool memory is not copied. Agent-builder DMs cannot be forked, and there is no fork prompt setting.
If an open issue with the same title (case-insensitive, extra spaces ignored) already exists under the same project and parent, `issue create` refuses and points to that issue. To create another one anyway, add `--allow-duplicate`. To mark an issue as a duplicate of another, run `multica issue status MUL-124 cancelled --duplicate-of MUL-123`.

For sequential PR delivery, use `issue create --title "..." --pr-auto-complete off` or `issue update <id> --pr-auto-complete off` to keep that issue's status when PRs merge. Use `--pr-auto-complete on` to restore the workspace rule; this takes effect at the next PR event. `issue pull-requests <id>` shows the issue override, workspace setting, target status, and decision state, even with no linked PRs. Supported servers save the creation override atomically; older servers receive a follow-up PUT. If that fails, the CLI reports the created issue ID and an update command to retry, so do not repeat the create.

### Timeline

`issue get` shows an issue as it is now. `issue timeline` lists, in order, the changes to status, priority, assignee, title, and dates and the run outcomes, interleaved with comments, which answers questions like "when did it move to in_review" or "how long has it been stuck in this status":

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only` drops comments and keeps every activity record; `--action` returns only the given actions, is repeatable, and implies `--activity-only`. The server caps how far back it reads; when the result is truncated, a warning goes to stderr, and durations should not be inferred from it.

```bash
multica issue description history MUL-123
multica issue description diff MUL-123 --from 30 --to 35
```

`issue description history` lists the recorded revisions of an issue's description, oldest first, with revision number, time (ICT) and actor. `issue description diff` prints a unified diff between two of them. A revision number is the issue's own revision counter. Only revisions recorded after the history feature shipped exist; for each issue the first entry is a baseline of the description at that time. A revision that did not change the description resolves to the latest earlier text. An unknown revision returns 404. `--output json` is available on both.

### Reading long comment threads

On an issue with many comments, reading them one by one costs an agent a lot of tokens. Scan the threads first, then open the one you need:

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only` returns only top-level comments, each with its reply count and last activity time.
- `--summary` clips each comment to a short preview.
- `--compact` applies to JSON output and drops fields that carry no information (such as the echoed `issue_id` and empty arrays).
- `--recent N` returns the N most recently active threads with every reply, which can be long.
- Resolved threads are folded to their root and conclusion by default; add `--full` for the complete text.

Lists can be trimmed to the fields you need, too: `multica issue list --output json --fields id,identifier,title,status`. The filtering happens in the CLI, so it shrinks output and context, not the request.

To list issues by their last update time, pass both `--updated-since` and `--updated-until` as RFC3339 timestamps. The server returns issues whose current `updated_at` is at or after `since` and before `until`: `[since, until)`. These flags work with existing filters, sorting, and pagination. Keep the same bounds across pages; concurrent updates can change the result set because pagination does not provide a snapshot.

```bash
multica issue list --updated-since 2026-11-05T10:00:00Z \
  --updated-until 2026-11-05T10:01:00Z \
  --sort created_at --direction asc --limit 100 --offset 0 \
  --output json --fields id,workspace_id,project_id,title
```

### Wakeups

A wakeup starts an ordinary run for an agent when an event happens, a condition becomes true, or a time arrives. The full rules are in [Issue wakeups](/issue-wakeups).

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "When they reply, update the quote from their answer"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "Check whether the supplier has replied"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

Creating one from a terminal as a member requires `--agent-id`; an agent creating one inside its own run wakes itself by default.

A rule a person can trigger is an event rule on a comment, issue, reaction or attachment change whose actor filter does not exclude members. When the workspace `ask_guard_mode` is `warn` or `block`, an agent cannot register such a rule on its own unless it has one of these:

- `--decision <request-id>` binds the rule to a decision request on this issue. The request must be asked or answered, and for the member in `--filter-actor-id` if you set one. One request binds one enabled wakeup at a time.
- `--purpose observe` marks a rule that does not wait for a person. Each fire caused by a member is recorded as an audit event.
- `--filter-actor-type agent` with no `--filter-actor-id` matches any agent and no member.

In `block` mode the refusal is a 422 whose message gives the fix command. In `warn` mode the rule is created and an event is recorded.

### Following progress in a DM

A DM follows the issues its agent creates for you. Members manage follows only in a DM they created, with `--chat`. An agent runs `multica issue follow <issue>` without `--chat`: the DM comes from its own task, and a task with no DM is refused. Child issues inherit their parent's active follow.

```bash
multica issue follow MUL-123 --chat <chat-session-id>
multica issue mute-follow MUL-123 --chat <chat-session-id>
multica issue unmute-follow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id> --scope root
multica issue follows --chat <chat-session-id>
```

`unfollow` ends this issue's follow. With `--scope root` it also ends the follows its child issues inherited from it; a child with its own manual follow stays followed. A child you unfollowed is not followed again when a later child is created.

## Agents and skills

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

When an import hits a skill with the same name, the default is to stop without modifying existing content. Pick by intent:

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite` is only allowed for the skill's creator and preserves the original ID and agent bindings.

Environment variables and MCP configuration often carry tokens. Values typed on the command line stay in shell history and `ps` output, so pass them through the `-file` or `-stdin` forms:

```bash
multica agent create --name "Ops helper" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- The `--custom-env` flags exist only on `agent create`. Change variables later with `agent env set`, which replaces the whole set; keys whose value is `****` keep their existing value.
- `agent update --mcp-config null` clears the MCP configuration.
- `--custom-args` is a JSON array placed at the end of the launch arguments. Choose the model with `--model`; some tools reject `--model` inside custom arguments.
- `--permission-mode` controls who can invoke the agent: `private` for the owner only, or `public_to` with `--public-to-workspace` or `--public-to-member <user-id>`. `--visibility private|workspace` is the older form and maps onto `--permission-mode`; when both are given, `--permission-mode` wins.

### Agent run history

`multica agent tasks <agent-id> --limit 200` returns the newest page of runs.
The default and maximum page size is 200. If more runs exist, stderr prints a
cursor; pass it unchanged as `--before '<cursor>'` to read the next page.
`--output json` keeps the array output and includes usage for that page only.

The corresponding `GET /api/agents/{id}/tasks` endpoint accepts `limit` and
`before`, and keeps its JSON array response. The `X-Agent-Tasks-Next-Cursor`
response header supplies the next cursor; its absence marks the final page.
Cursors preserve `(created_at, id)` order, including timestamp precision.
Invalid limits or cursors return HTTP 400; limits above 200 are capped.
Clients that do not follow the cursor receive only the newest 200 runs.

#### Task claim provenance

`multica agent tasks <agent-id> --output json` and
`multica issue runs <issue-id> --output json` (full execution log, not
`--siblings`) return `claimed_model` on every run, beside `id`, `agent_id`,
`issue_id`, `workspace_id`, `status` and `dispatched_at` (claim time). Both
reads keep their existing workspace-membership and private-agent checks.

```bash
multica issue runs CHE-1962 --output json \
  | jq '.[] | {id, agent_id, issue_id, workspace_id, status, dispatched_at, claimed_model}'
multica agent tasks <agent-id> --output json | jq '.[] | {id, claimed_model}'
```

`claimed_model` is the model the daemon was told to run at claim, as stored on
the task. It is not derived from the agent's current model.

| Value | Meaning |
| --- | --- |
| a string | Exact stored value |
| `null` | Nothing stored: not yet claimed, or the claim could not record it |
| `""` | An empty string was stored |
| key absent | Server predates this field; nothing can be concluded |

It attests the claim only. It does not show which upstream model or provider
served the run; that stays unverified. Task prompts, provider environment and
tokens are not part of this field.


## Daemon and runtimes

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

```bash
multica daemon autostart enable
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "Internal Claude wrapper" \
  --command-name ccms --runtime-type claude
```

`daemon autostart` registers the current profile to start at login; see [Start at login](/daemon-runtimes#autostart) for platform details. `runtime usage` covers 90 days by default, and `--days` goes up to 365. `runtime update` asks the daemon on that computer to update its CLI to the given version; `--wait` keeps polling until the update finishes. `runtime profile create` takes the compatible tool through `--runtime-type` (the older `--protocol-family` still works); fixed arguments can currently be set only in the web app.

Deleting a runtime that still has active agents bound to it is refused by default. `multica runtime delete <id> --cascade` unbinds those agents, preserves their configuration and history, and cancels their active runs.

`multica runtime breaker list` shows each provider's circuit breaker; `multica runtime breaker reset <provider>` force-closes it (owner or admin only). See [Provider circuit breaker](/daemon-runtimes#provider-breaker).

See [Daemon and runtimes](/daemon-runtimes) for how it works and for custom profiles.

## Projects, workspaces, and autopilots

```bash
multica project create --title "Summer campaign" --lead "Lei Li" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "Operations" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "Weekly sales report" --agent "Ops helper" \
  --mode create_issue --issue-title-template "Sales report {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Europe/London
```

- `--lead` takes the name of a member or an agent. `--default-branch-hint` only tells the agent the repository's default branch; it does not switch branches.
- A workspace's `--context` is provided to every agent in the workspace. `--slug` cannot be changed after creation. `--issue-prefix` is uppercased; changing it renumbers every existing issue, and old identifiers in external references stop resolving.
- `multica workspace update --routing-agent <agent-id> [--routing-fallback-agent <agent-id>]` names the agent that takes routing-only workflow steps (`todo`, `blocked`, `merged`, `need_decision` by default; change with `--routing-statuses`, send one status elsewhere with `--routing-overrides todo=<agent-id>`). The fallback takes over when that agent is archived, or when its run fails on a provider error. An override key `<workflow-id>:<status>` limits that override to one workflow. `none` turns a field off. Only a human owner or admin can change it, and each change is recorded in the activity log.
- `--issue-title-template` interpolates only `{{date}}` (UTC, `YYYY-MM-DD`) and rejects any other `{{...}}` token. A schedule trigger's `--timezone` defaults to UTC.
- `--mode script --script <name> [--arg <value>]...` runs one allowlisted script under the agent's task token, with no model session. `--script` and `--arg` need `--mode script`, and `--mode script` needs `--script`. `--description` is never executed. With no daemon allowlist every script task fails closed. `--output json` shows the script name and args as `script_config`. `autopilot update --mode <other>` clears the script. The server deletes the task token when the task ends, on a best-effort basis. If the deletion fails, the token stays valid until it expires; nothing revokes it sooner. The run result records the script name, a SHA-256 of the argument list, the exit code and the duration under `script`, and sets `token_revoke_failed` when a deletion failed.

`multica chat` reads **the external chat session an agent is currently handling**; it is mainly for agents in chat integrations, not a general command for browsing arbitrary workspace conversations.

### Rename a DM

```bash
multica chat rename <session-id> "Release decisions"
```

A running workspace agent task can rename a DM in that workspace, including a DM owned by another person. The rename and its announcement commit together. The announcement shows the old title, the new title, and the authenticated actor. Titles must be nonempty, single-line, and at most 200 characters.

The agent receives only the session ID, new title, previous title, and announcement message ID. Rename does not grant permission to list DM lanes, read messages, access resume pointers, or change project context. Automatic title generation does not overwrite a manual rename, including a rename back to the original title.

### DM attention

```bash
multica chat attention [--stale] --output json
multica chat later <session> [duration | RFC3339 time]
```

`attention` lists the DM chains that need you, one row per chain, oldest `attention_since` first. Chains with nothing open, archived chains and chains whose `later` is still in the future are not listed. `--stale` keeps only `yellow` (4 h or more) and `red` (24 h or more) rows.

`later` snoozes the obligations the server shows for the chain right now. Durations take `2h`, `90m`, `7d`, `1d12h` or plain seconds; with no duration the server uses 2 hours. The server accepts 1 second to 168 hours from now. The CLI sends the value as given and prints the server's range error; it never caps silently. Repeat a call with the same `--request-id` and the due time does not move. Agent tasks cannot use `later`.

### Decision lane metadata

A running assigned issue task can open a three-minute decision window by posting a comment with `--decision-intent` and member mentions. Only that task can list active web DM lanes for the people named in the window:

```bash
multica chat sessions --issue MUL-123 --for <user-id> --output json
```

Omit `--for` only when the window names exactly one person. The person must still be an active workspace member who can invoke the asking agent, and their target must be unconsumed. A listing does not consume the window. Another run of the same agent, a chat task, PATs and JWTs cannot use this command.

The response contains only `id`, `title`, `updated_at` and `issue_mentions`, newest lane first. It never includes messages, unread counts or transcript previews. Archived sessions and channel-origin sessions are excluded. If no lane exists, the server creates a web DM titled `Decisions: <agent name>` for the named person. Expired, closed, deleted-tag and consumed windows are refused.

### Decision requests

A running assigned issue task asks a person in one call:

```bash
multica decision request --issue MUL-123 --for <user-id> --class reversible \
  --ask-file ./ask.md [--footer-file ./footer.md] [--parent <comment-id>]
```

`--for` accepts the person's user ID or their member ID in the issue's workspace, including workspace owners. The server stores the canonical user ID.

A running DM chat task can also ask, but only its own DM member: it must pass `--for <that member>`. Another member is refused with 403. `--session`, `--new-dm` and `--parent` are refused with 400. The card renders in the calling DM, and the request carries the decision ID, the member, the issue, the class and the expiry.

One call writes one issue comment (the ask plus the optional footer, top-level or under `--parent`), one DM message (the ask only) and one inbox ping. The footer reaches the issue comment only, so use it for handoff lines. Footer lines dispatch no agent, because an ask comment does not trigger tasks.

The server picks the DM: the lane of your latest request to that person on this issue, else the newest lane that mentions this issue, else a new `Decisions: <agent name>` DM. `--session <lane-id>` and `--new-dm` override the choice. The same checks as a decision-intent comment apply to the task, issue and person. One call asks one person.

A batch card closes the per-issue cards it covers. Pass `--covers <request-id>` (repeatable, at most 25) with the ids of open `reversible` or `product_direction` cards for the same person in the same workspace. The batch card must also be `reversible` or `product_direction`. When the person answers the batch card, each covered card closes as answered by the batch, its issue gets the quoted answer, and its asking agent wakes once. The DM folds each covered card into one row under the batch card. Only a plain choice card can be covered: a card with an attached action, a governed write ("Approve write"), an artifact, a human action, a gated class is never covered, and the person must answer that card itself. A covered card that gains one of these after the batch card was created stays open when the batch is answered. Each batch option must also be an option of every covered card with the same label and the same `what_happens` meaning, and the batch card lists every covered decision with its options and their meanings so the person sees what the answer closes. If the covered decisions cannot be loaded, the card offers no answer form. A covered card closes only when the person picks a batch option that is one of its own options, label and meaning alike: a free-text batch answer closes none, and a covered card that does not offer the chosen option stays open for its own answer. The server refuses a batch option answer (400, `covers_ack_required`) unless it carries `covers_ack`, a SHA-256 digest of the batch id, the sorted covered ids and the chosen option: an older client that cannot show the covered decisions cannot answer for them, and nothing is closed. While a person is in passkey recovery and the workspace gate blocks, a batch answer is refused if it would close a covered `product_direction` card, exactly as that card's own answer would be. Any withdrawal of the batch answer also withdraws every covered answer and reopens those cards: the person disclaiming it, an agent vetoing it, its source being removed or its answering turn failing, a lifecycle cancel of the batch card, a raise past a delegate, and the batch card being removed with its issue. The call is refused if any id is not an open, eligible card of that person, or if a covered card lacks a batch option or gives it another meaning.

If a decision-intent comment is still open for the task, the older two-step flow applies: pass `--session` or `--new-dm --for`, and the ask replies under the intent comment. `--parent` is refused there.

### Decision proposals

A running task token proposes a governed action for a person to approve with a passkey. The proposal changes nothing itself.

```bash
multica decision propose issue.run_budget.raise --version 1 --issue MUL-123 \
  --for <user-id> --param window_id=<id> --param new_cap:=40 [--reason "..."]
multica decision propose <action-type> --version 1 --issue MUL-123 --params-file ./params.json
```

`--version` and `--issue` are required. `--param k=v` sends a string and `--param k:=<json>` sends raw JSON; `--params-file` takes one JSON object and cannot be combined with `--param`. The command prints the approve-card link. For a run-budget action that link opens the approval on the issue; for any other action it links to the card in the chat, where the person approves it. A plain option card (`multica decision request` without `--action-file`) cannot apply a change: Approve only records the answer. The server cannot read intent, so it does not refuse such a card; when the decision or an option reads like a workflow, agent, squad, workspace or budget change (or names an allowlisted action type) it adds an advisory hint. Send that change with `multica decision propose`. A refusal shows the server's status and error code. `multica issue budget raise` and `multica issue budget top-up` use the same route under a task token (add `--for <user-id>`); with a personal access token they open the spend request as before.

### Config change proposals

`multica config propose` builds the action file for a workspace config change. It reads the live value, computes `before_sha256` and `after_sha256` with the recipes the server recomputes, and writes the file that `multica decision request --action-file` takes. It sends nothing and writes no secret. A person still approves with a passkey.

Fields: `agent.instructions <agent-id>`, `squad.instructions <squad-id>`, `workspace.context`, `workflow.steps <workflow-id>`, `workflow.step.instructions <workflow-id> --status-key <key>`, `workflow.budget <workflow-id>` and `workspace.settings --set key=value|key:=<json>`. Text fields take `--file` (UTF-8, no NUL byte). `workflow.steps` takes the steps array as the workflow GET returns it; edit that output, because the server refuses the request (`after_digest_mismatch`) if it normalizes your steps differently. For `workflow.step.instructions` the server computes the after digest, so the file carries no `after_sha256` and the printed digest is for comparison only. Pass `--out <path>` to write the file or `--dry-run` to print both digests and the action without writing. `--expires-in <seconds>` sets the request expiry.

`workflow.budget <workflow-id>` takes `--max-runs <n>` (1 to 1000; 0 clears the cap) and `--include-child-prs=<true|false>` in place of `--file`; name at least one, and a field left out keeps its stored value. An agent cannot write these two fields on a workflow directly (`budget_requires_decision`): propose the change, request the decision, and the server applies it on approval if the workflow still matches the digest the CLI read.

The agent can also write the approved change itself. Run `multica workflow update <workflow-id> --max-runs 40 --print-hash` (nothing is written) to read `before_sha256` and `after_sha256`, request the decision for `workflow.budget`, then repeat the command with `--decision-id <id>`. A budget write carries no `--steps-file`. `multica issue update <issue> --workflow <workflow-id>` and `multica issue create --workflow <workflow-id>` take the same `--print-hash` and `--decision-id` (field `issue.workflow`) when the workflow has a wider budget; both commands follow one rule, and an owner's interactive session needs no decision.

Any other field is refused with `denylisted` before the CLI reads anything: `project.description`, passkeys and the decision gate, members and roles, owner transfer, auth and integration secrets, workspace deletion, the action registry, and `delegated_governed_writes`. A settings key off the server allow table is refused the same way, and a patch that mixes allowed and refused keys is refused whole. The server checks again at request and at approval.

```bash
multica config propose workspace.context --file ./context.md --out ./action.json
multica config propose agent.instructions <agent-id> --file ./instructions.md --dry-run
multica config propose workflow.step.instructions <workflow-id> --status-key review --file ./step.md --out ./action.json
multica config propose workflow.budget <workflow-id> --max-runs 40 --include-child-prs=false --out ./action.json
multica config propose workspace.settings --set compact_prompt="..." --set wakeups_paused:=false --out ./action.json
multica decision request --issue MUL-123 --for <user-id> --class reversible --ask-file ./ask.md --action-file ./action.json
```

### Shadow report

Any workspace member reads the System 1 shadow report:

```bash
multica decision shadow-report [--since <RFC 3339>] [--until <RFC 3339>] --output json
```

The `decision` and `routing` blocks cover all time. The `route` block covers the window `[since, until)`: `--since` and `--until` take RFC 3339 times, `--until` defaults to now and `--since` to 24 hours before `--until`. The server refuses a bad time or a `--since` after `--until` with 400.

The `route` block counts one population of events: agent status changes marked as leaving a routing step (`eligible_exits`) and the route labels that carry the same event id (`matched_labels`). `label_coverage` is `matched_labels / eligible_exits` and never exceeds 1. `via_route_share` is the part of matched events whose first label came from `issue route`, not from the status fallback. `duplicate_labels` counts labels that share an event with an earlier label (target 0). `labels_total`, `owner_only_labels` (a route that kept the status, so it has no event) and `non_routing_labels` (a route from a step with no routing agent) sit outside coverage. `overridden` counts agent labels a person reversed within 1 hour, and `override_rate` is `overridden / labels_total`. The block also carries the per-class `decided`, `predicted`, `agreed`, `coverage` and `precision`.

## IDs and output formats

Issues use keys like `MUL-123` or full UUIDs; short UUID prefixes are not accepted.

`list` commands for other resources usually print copyable short IDs and support `--full-id` for the full UUID. When a short ID is ambiguous, the CLI asks for more characters or the full UUID. Short task IDs also require `--issue` to identify the owning issue.

Many commands support structured output:

```bash
multica issue list --output json
multica agent list --output json
```

Scripts should use JSON output rather than parsing the terminal-oriented tables. The output formats and pagination flags each command supports are defined by `multica <command> --help`.

## Profiles and configuration

The default configuration lives in `~/.multica/config.json`. Use `--profile <name>` to isolate a separate set of server address, token, default workspace, and daemon state:

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

Named profiles live in `~/.multica/profiles/<name>/config.json`. Inspect the current values:

```bash
multica config show
multica config show --profile staging
```

Do not set `MULTICA_DAEMON_PORT` in the host shell, Compose service, or container entrypoint that starts a daemon. The host daemon normally derives its health port from `--profile`; if that port cannot be bound, it uses an available loopback port and injects the actual port into agent tasks itself. Remove the variable from older startup environments entirely: versions 0.4.22 and 0.4.23 otherwise mistake that shell for a managed task and reject login. Newer versions let guarded human login and `daemon status` recover when the port is the only task signal, but ordinary API and profile-resolving commands intentionally remain fail-closed until the variable is removed.

When the CLI runs inside a daemon-managed agent task, it does not load or modify these human-owned profile files. Multica API commands authenticate with the task-scoped credential injected by the daemon. `config show` and `config set` use private task-local state; human/local commands such as `login`, `logout`, `setup`, `workspace switch`, local runtime profile path changes, `daemon start` / `stop` / `restart`, `daemon logs`, and `daemon probe-runtimes` are unavailable. `auth status` does not print token material in this context.

`daemon status` and `daemon disk-usage` stay available so an agent can inspect the runtime hosting it, scoped to that runtime: `status` probes the health port the daemon injected, and `disk-usage` scans the workspaces root the daemon injected. Neither accepts `--profile`, `disk-usage` also rejects `--all-profiles` and `--workspaces-root`, and its STATUS column is blank because resolving it would require the human's stored token. Use `du` and `df` for anything outside that scope.

This protects implicit Multica CLI profile resolution while preserving the normal `HOME` and XDG variables used by other provider tools. It is not an OS filesystem boundary: processes running as the same system user may still open an explicitly known path. Use a dedicated user, container, VM, or equivalent isolation when that stronger guarantee is required.

CLI configuration files contain tokens that can access Multica as you. Don't commit them to a repository, upload them to logs, or share them with others.
</Callout>

## Command reference

The tables below cover every current top-level command, grouped the way the CLI itself groups them. All commands accept the global flags `--server-url`, `--workspace-id`, `--profile`, and `--debug`. `--output` is registered per command, and the default format varies: `list` commands default to a table, while `get` and `create` commands mostly default to JSON. Full flags are defined by `multica <command> --help`.

### Issue attachments

For `issue create`, `issue update`, and `issue comment add`, each `--attachment` takes one literal file path, including any commas or double quotes in the filename. Repeat the flag for multiple files: `--attachment 'report,final.csv' --attachment notes.txt`. Omitting the flag attaches no files; an explicitly empty path is an error. All local paths are checked before any file is uploaded.

Migration from CSV parsing: replace `--attachment a,b` with `--attachment a --attachment b` to attach two files. The former now selects a single file named `a,b`. Remove extra CSV quotes from the old workaround `--attachment '"report,final.csv"'`; use `--attachment 'report,final.csv'` unless the filename itself contains those double quotes.
