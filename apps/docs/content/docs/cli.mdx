The Multica CLI both connects local runtimes and manages workspaces, issues, agents, and automations from the terminal. This page covers the common paths; the flags your installed version supports are always defined by each command's own `--help`.

## First connection

Pick the service you are connecting to:

<Tabs items={["Multica Cloud", "Self-hosted instance"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="Self-hosted instance">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup` saves the server address, opens a browser to complete sign-in, and starts the daemon. When it finishes, check:

```bash
multica auth status
multica daemon status
```

If you only need to sign in again without overwriting other configuration, run `multica login`. On a machine without a browser, create a personal access token in the web settings first, then enter it with:

```bash
multica login --token
```

The command prompts you to paste the token in the terminal, keeping the full value out of shell history.

## Choosing a workspace

List workspaces and switch the default:

```bash
multica workspace list
multica workspace switch <slug>
```

Subsequent commands use this workspace. A single command can override it with `--workspace-id`, or you can set `MULTICA_WORKSPACE_ID`.

Invite members:

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## Common issue operations

```bash
# View and search
multica issue list
multica issue get MUL-123
multica issue search "login failure"

# Create and update
multica issue create --title "Fix login failure"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# Comments and runs
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "Check the regression tests first"
multica issue comment update <comment-id> --expected-revision 2 --content "Check the regression tests and release notes"
multica issue runs MUL-123
```

Read long descriptions or comments from stdin to avoid dealing with newlines and quoting:

```bash
multica issue create --title "Upgrade notes" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

Inspect, stop, or retry a single run:

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123 --fresh
```

Add a comment to a run that is still working, instead of queueing a follow-up run (only runs that accept additional messages; you can steer an agent exactly when your comment could start it):

```bash
multica issue comment add MUL-123 --content-file note.md --steer <task-id>
multica issue comment add MUL-123 --content-file note.md --steer-active
```

A comment from an agent task that mentions a member (`[@Name](mention://member/<id>)`) is accepted only as a decision request, a `--decision-intent`, `--decision-record` or `--decision-veto` comment, or a comment with `--notify-only`. Use `--notify-only` for an FYI that needs no answer. It never opens a wait and never counts as a decision request. It cannot combine with the decision flags. The check reads the mention link, not the wording, and a link inside code counts. The workspace setting `ask_guard_mode` (`off`, `warn`, `block`) decides whether a refused comment is only logged or returns 422. Chat tasks and calls without a task only log. An edit that adds a member mention follows the same rule.

```bash
multica issue comment add MUL-123 --content-file fyi.md --notify-only
```

A comment from an agent on an issue in `in_review`, `blocked` or `need_decision` must name who acts next: `--ask <member-id>` if a person acts next, or `--no-ask` if no one does. A member mention, `--notify-only` or a decision request also counts. The two flags cannot combine with each other, with `--notify-only` or with the decision flags. The same move needs `--waiting-on member:<member-id>` or `--waiting-on none` on `multica issue status`, accepted only with `in_review`, `blocked` or `need_decision`. The workspace settings `waiting_audience_guard` and `waiting_on_guard` decide whether a missing audience is allowed, counted or refused.

To ask a short question without growing a long thread, open an ask thread: `--from-thread <comment-id>` creates the comment as a new root that links back to the thread of that comment, which must be on the same issue (otherwise `400 thread_issue_mismatch`). The server adds one line to the source thread, `Asked <names> in thread <id>.`; it mentions nobody, starts no run and leaves the source thread's resolution as it is. `--from-thread` cannot combine with `--parent`. An agent task cannot resolve the root of an ask thread (`409 ask_root_not_resolvable`): resolve the source thread with a reply there. A member can resolve it as usual.

```bash
multica issue comment add MUL-123 --content-file ask.md --from-thread <comment-id>
```

An agent comment that mentions a member deep inside a long thread can be moved by the server into a new ask thread, as if the agent had passed `--from-thread`. The workspace setting `long_thread_member_ask` (`off` by default, `warn`, `move`) decides; `long_thread_member_ask_min` (3 to 100, default 10) is the thread size from which it applies, root included. It applies only when none of the mentioned members wrote one of the last 3 comments of the thread. A comment with `--notify-only`, a decision kind, `--supersedes` or `--resolve-thread` is never moved. Under `move` the response carries `placement` (`moved`, `source_root_id`, `reason`) and a hint; under `warn` the comment posts in place with a hint that names `--from-thread`. Editing a comment never moves it.

## Forking a web DM

From the source DM's running chat task, copy the DM into a new child DM:

```bash
multica chat continue --fork
```

The source stays active and unchanged. The child gets a full copy of the messages the person can see, with their original times, and of their attachments; it holds no summary. It keeps the same agent, creator and project, with a title ending in ` (fork)`, and starts with no provider session and no managed checkout. Decisions, approvals, task tokens and lane summaries stay with the source. The agent's private tool memory is not copied. Agent-builder DMs cannot be forked.

On the child's first turn, and on any turn with no provider session to resume, the agent receives a fork context block: a notice, an index of the copied attachments, and the newest messages of the DM that fit in 64 KiB. When older messages are left out, the block says so; read them with `multica chat history`.

The default fork operation key is the current turn: an auto-retry of the same turn returns the same child. To create another fork in that turn, use a different explicit key; reuse that key when retrying:

```bash
multica chat continue --fork --idempotency-key explore-alternative
```

A task fork does not send a message. `--summary-file` is not accepted with `--fork`.

The session-human API is `POST /api/chat/sessions/{sessionId}/fork` with a required `idempotency_key` and an optional `message` in the JSON body. With a message, the server sends it as the person's first message in the child and starts the agent's first turn in the same transaction; without one, the child is idle. A retry with the same key returns the same child (HTTP 200) and sends nothing twice. The task-scoped API is `POST /api/chat/fork`. Session responses expose `forked_from_session_id`, `fork_last_message_id` and `fork_message_count` on children. Only web DMs with at least one message can be forked. Without `--fork`, `chat continue` still archives the source and requires `--summary-file`; `/compact` is unchanged.

### Compacting a web DM

`multica chat compact --summary-file ./summary.md` keeps the DM, its id, history and URL, and starts the next turn from the summary. It never archives the DM. A server without in-place compaction stops the command and leaves the DM unchanged.

The `/compact` task runs with the workspace's compact agent, set by an owner or admin. It falls back to the DM's own agent when none is set:

```bash
multica workspace update <workspace> --compact-agent <agent-id-or-name>
multica workspace update <workspace> --compact-agent null    # reset: the DM's own agent compacts
```

- The name is looked up in the workspace you name, not your default one. A name that matches more than one agent is refused with the matches listed; use the id.
- `--compact-agent` is an alias for `multica workspace background-agents set compact --agent <agent>`. It cannot be combined with any other `workspace update` flag. After the write the CLI reads the setting back; if the server kept something else, it fails with `compact agent was not saved` and the value the server holds.
- The agent summarises the whole DM transcript, so choose one you trust with it. A human owner or admin must make the change; task tokens are refused.
- A compaction task cannot fork or archive the DM, and only the workspace's current compact agent may finish it. Otherwise `multica chat compact` and `multica chat continue` print the server's stable code and message to stderr and exit with code 3 (auth):
  - `compaction_agent_not_current`: this agent is no longer the workspace's compact agent.
  - `compaction_continue_refused`: a compaction task finishes in place with `multica chat compact`; it cannot use `multica chat continue` to fork or archive.

### `/fork` in the web app

Type `/fork [message]` as the first word of a web DM message. The web app forks the DM directly, with no agent turn: the new DM is a full copy of the visible messages and attachments, and the source stays active with a "Forked into" link. You land in the new DM. With a message, the agent answers it at once; without one, the new DM is idle until you send a first message. The agent in the new DM starts a fresh session and gets the transcript in a context block capped at 64 KiB (newest messages first); it reads earlier ones with `multica chat history`. The agent's private tool memory is not copied. Agent-builder DMs cannot be forked, and there is no fork prompt setting.
If an open issue with the same title (case-insensitive, extra spaces ignored) already exists under the same project and parent, `issue create` refuses and points to that issue. To create another one anyway, add `--allow-duplicate`. To mark an issue as a duplicate of another, run `multica issue status MUL-124 cancelled --duplicate-of MUL-123`.

To record what a blocked issue waits for, add `--blocked-on <ref>` to the move: `multica issue status MUL-124 blocked --blocked-on pr:merged`. The flag is accepted only with `blocked`. The ref is stored in the `status_changed` activity and in the issue metadata key `blocked_on`, and is removed when the issue leaves `blocked`. A move to `blocked` without the flag works as before. Each ref form is the target of a wakeup condition flag:

| Ref | Same as |
| --- | --- |
| `issue:<id>[@done\|ended\|in_review\|blocked]` | `--until-issue`, `--until-issue-state` |
| `pr:<checks\|merged\|conflicts\|dequeued>` | `--until-pr` |
| `children[@<stage>]` | `--until-children-done`, `--stage` |
| `gh-run:<owner>/<repo>:<run-id>` | `--until-gh-run` |
| `decision:<request-id>` | a wakeup bound with `--decision` |

The ref is validated against the workspace: an issue or decision request from another workspace is refused, and so is any other form. A person is not a ref form. The `Blockers:` line of the issue description stays the place for the owner and the ending event; show the ref there as `--blocked-on <ref>`.

### Route an issue

`issue route` moves an issue's status and records why, in one call. A routing step uses it to decide where an issue goes next. `--status`, `--reason` (1 to 500 characters) and `--confidence` (0 to 1) are required:

```bash
multica issue route MUL-123 --status in_review --reason "Tests pass, needs review" --confidence 0.8
multica issue route MUL-123 --status in_progress --owner "Backend Agent" --reason "Needs a backend fix" --confidence 0.6
multica issue route MUL-123 --status in_review --owner-id <agent-id> --no-start --reason "Reviewer will pick it up later" --confidence 0.9
```

Without `--owner`, the project workflow picks the handler, as with `issue status`. An explicit `--owner` (a member, agent, or squad; `--owner-id` takes a UUID instead of a name) replaces the workflow's handler. A route that keeps the current status and changes only the owner is allowed. A route with the same status and the same owner is refused with HTTP 409 and writes nothing. `--no-start` starts no agent run, as it does for `issue update`. `--expected-revision` refuses the route if the issue changed in the meantime.

`multica issue workflow escalate <id> --reason "..."` moves an issue that follows Quick to the full workflow it followed before. `--reason` is required, and `rollback` needs no `Estimate:` line from `todo` or `investigating`. The command takes no workflow: the server reads the target from the issue's newest `quick_entry` row. It prints `applied` when the issue entered the full workflow, or `pending` when a live task keeps it on Quick until the last task ends; `--output json` prints `state` and `workflow_id`. See [Workflows](/workflows) for the refusal codes.

### Timeline

`issue get` shows an issue as it is now. `issue timeline` lists, in order, the changes to status, priority, assignee, title, and dates and the run outcomes, interleaved with comments, which answers questions like "when did it move to in_review" or "how long has it been stuck in this status":

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only` drops comments and keeps every activity record; `--action` returns only the given actions, is repeatable, and implies `--activity-only`. The server caps how far back it reads; when the result is truncated, a warning goes to stderr, and durations should not be inferred from it.

```bash
multica issue description history MUL-123
multica issue description diff MUL-123 --from 30 --to 35
```

`issue description history` lists the recorded revisions of an issue's description, oldest first, with revision number, time (ICT) and actor. `issue description diff` prints a unified diff between two of them. A revision number is the issue's own revision counter. Only revisions recorded after the history feature shipped exist; for each issue the first entry is a baseline of the description at that time. A revision that did not change the description resolves to the latest earlier text. An unknown revision returns 404. `--output json` is available on both.

### Reading long comment threads

On an issue with many comments, reading them one by one costs an agent a lot of tokens. Scan the threads first, then open the one you need:

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only` returns only top-level comments, each with its reply count and last activity time.
- `--summary` clips each comment to a short preview.
- `--compact` applies to JSON output and drops fields that carry no information (such as the echoed `issue_id` and empty arrays).
- `--recent N` returns the N most recently active threads with every reply, which can be long.
- Resolved threads are folded to their root and conclusion by default; add `--full` for the complete text.

To read only the threads that involve you (or another member or agent), add a relation flag:

```bash
multica issue comment list MUL-123 --roots-only --summary --with-me --output json --compact
multica issue comment list MUL-123 --roots-only --summary --waiting-on <member> --output json --compact
```

- `--with-me` returns only threads you wrote in, were mentioned in directly, or that hold a decision request addressed to you. `--without-me` returns the rest.
- `--waiting-on <member>` returns only threads that wait on that member: an open decision request targets them, or a direct mention of them has had no reply from them yet. It takes a member id or name.
- `--for <id>` reads the relation as that member or agent instead of you. Alone, it adds `thread_relation` to each root without filtering.
- These flags filter whole threads, so they work with `--roots-only`, `--summary` and `--thread`. Each root then carries `thread_relation`.
- Without a relation flag, `--compact` and `--summary` output does not carry `thread_relation`, so existing reads do not grow.
- If the server cannot compute the relation, the command fails instead of printing an unfiltered list.

Lists can be trimmed to the fields you need, too: `multica issue list --output json --fields id,identifier,title,status`. The filtering happens in the CLI, so it shrinks output and context, not the request.

### Wakeups

A wakeup starts an ordinary run for an agent when an event happens, a condition becomes true, or a time arrives. The full rules are in [Issue wakeups](/issue-wakeups).

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "When they reply, update the quote from their answer"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "Check whether the supplier has replied"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

Creating one from a terminal as a member requires `--agent-id`; an agent creating one inside its own run wakes itself by default.

A rule a person can trigger is an event rule on a comment, issue, reaction or attachment change whose actor filter does not exclude members. When the workspace `ask_guard_mode` is `warn` or `block`, an agent cannot register such a rule on its own unless it has one of these:

- `--decision <request-id>` binds the rule to a decision request on this issue. The request must be asked or answered, and for the member in `--filter-actor-id` if you set one. One request binds one enabled wakeup at a time.
- `--purpose observe` marks a rule that does not wait for a person. Each fire caused by a member is recorded as an audit event.
- `--filter-actor-type agent` with no `--filter-actor-id` matches any agent and no member.

In `block` mode the refusal is a 422 whose message gives the fix command. In `warn` mode the rule is created and an event is recorded.

### Wakeup rules

Workspace and project wakeup rules (see [Issue wakeups](/issue-wakeups)) have their own command, with `create` and `get` beside these:

```bash
multica wakeup-definition list [--project <project>] [--output json|table]
multica wakeup-definition preview [--project <project>] [--rule <rule>] [--output json|table] --config-file rule.json
multica wakeup-definition update <rule> [--project <project>] --revision <n> --config-file rule.json
multica wakeup-definition delete <rule> [--project <project>] --revision <n>
```

`--revision` is the revision `list` shows; `update` with `--revision 0` creates an override. `preview` saves nothing: it prints the resolved rule. For a condition rule, `already_satisfied` counts the issues that would match at once and `issues` names them (`--output table` prints them as a list). The preview looks at the first 200 issues of the scope and evaluates the open, non-backlog ones; when the scope has more, `truncated` is `true` and more issues may match. An event rule has no predicate, so its preview has no `already_satisfied` and matches no existing issue. Only an owner or admin can edit or delete a rule. Any human member can preview; an agent or other machine credential gets `403`, and a rule an agent creates stays disabled until a human enables it.

### Following progress in a DM

A DM follows the issues its agent creates for you. Members manage follows only in a DM they created, with `--chat`. An agent runs `multica issue follow <issue>` without `--chat`: the DM comes from its own task, and a task with no DM is refused. Child issues inherit their parent's active follow.

```bash
multica issue follow MUL-123 --chat <chat-session-id>
multica issue mute-follow MUL-123 --chat <chat-session-id>
multica issue unmute-follow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id> --scope root
multica issue follows --chat <chat-session-id>
```

`unfollow` ends this issue's follow. With `--scope root` it also ends the follows its child issues inherited from it; a child with its own manual follow stays followed. A child you unfollowed is not followed again when a later child is created.

## Agents and skills

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

`multica agent get <agent-id> --output json` also returns `background_use`: the background jobs the agent serves, as a list of `{scope, job}` (`scope` is `workspace` or `personal`). You see every workspace job and only your own personal picks.

When an import hits a skill with the same name, the default is to stop without modifying existing content. Pick by intent:

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite` is only allowed for the skill's creator and preserves the original ID and agent bindings.

Environment variables and MCP configuration often carry tokens. Values typed on the command line stay in shell history and `ps` output, so pass them through the `-file` or `-stdin` forms:

```bash
multica agent create --name "Ops helper" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- The `--custom-env` flags exist only on `agent create`. Change variables later with `agent env set`, which replaces the whole set; keys whose value is `****` keep their existing value. A `****` for a key that is not stored (for example a renamed key) is rejected with 400 and nothing changes.
- `agent update --mcp-config null` clears the MCP configuration.
- `--custom-args` is a JSON array placed at the end of the launch arguments. Choose the model with `--model`; some tools reject `--model` inside custom arguments.
- `--permission-mode` controls who can invoke the agent: `private` for the owner only, or `public_to` with `--public-to-workspace` or `--public-to-member <user-id>`. `--visibility private|workspace` is the older form and maps onto `--permission-mode`; when both are given, `--permission-mode` wins.

### Agent run history

`multica agent tasks <agent-id> --limit 200` returns the newest page of runs.
The default and maximum page size is 200. If more runs exist, stderr prints a
cursor; pass it unchanged as `--before '<cursor>'` to read the next page.
`--output json` keeps the array output and includes usage for that page only.

The corresponding `GET /api/agents/{id}/tasks` endpoint accepts `limit` and
`before`, and keeps its JSON array response. The `X-Agent-Tasks-Next-Cursor`
response header supplies the next cursor; its absence marks the final page.
Cursors preserve `(created_at, id)` order, including timestamp precision.
Invalid limits or cursors return HTTP 400; limits above 200 are capped.
Clients that do not follow the cursor receive only the newest 200 runs.

#### Task claim provenance

`multica agent tasks <agent-id> --output json` and
`multica issue runs <issue-id> --output json` (full execution log, not
`--siblings`) return `claimed_model` on every run, beside `id`, `agent_id`,
`issue_id`, `workspace_id`, `status` and `dispatched_at` (claim time). Both
reads keep their existing workspace-membership and private-agent checks.

```bash
multica issue runs CHE-1962 --output json \
  | jq '.[] | {id, agent_id, issue_id, workspace_id, status, dispatched_at, claimed_model}'
multica agent tasks <agent-id> --output json | jq '.[] | {id, claimed_model}'
```

`claimed_model` is the model the daemon was told to run at claim, as stored on
the task. It is not derived from the agent's current model.

| Value | Meaning |
| --- | --- |
| a string | Exact stored value |
| `null` | Nothing stored: not yet claimed, or the claim could not record it |
| `""` | An empty string was stored |
| key absent | Server predates this field; nothing can be concluded |

It attests the claim only. It does not show which upstream model or provider
served the run; that stays unverified. Task prompts, provider environment and
tokens are not part of this field.

## Daemon and runtimes

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

`daemon restart` preserves an existing Linux systemd user service, including custom units and their launch settings. Before shutdown, it verifies the target daemon PID against the service manager. It uses native shutdown admission (with `--maintenance-token` when a hold exists), then waits for automatic restart or starts the same inactive service. Success requires a changed service PID and matching profile health within 90 seconds. An ownership mismatch or unconfirmed shutdown returns an error without a forced kill or separate child launch. Managed tasks still cannot restart the daemon.

`multica config set reserved_chat_slots <n>` keeps `n` daemon slots for chat (DM) runs: issue runs use at most `max_concurrent_tasks - n` slots, chat runs may use all of them, and the default `0` changes nothing. Group channel conversations count with issue runs; only direct chats use the reserved slots. A value below `0`, or at or above `max_concurrent_tasks`, is refused with an error naming both values. The value is checked against the cap the daemon starts with: `MULTICA_DAEMON_MAX_CONCURRENT_TASKS` if set, else the saved `max_concurrent_tasks`, else 20. A `--max-concurrent-tasks` flag given at start is not known to `config set`; the daemon refuses to start if the reservation does not fit it. `daemon status --output json` reports `reserved_chat_slots` and `reserved_chat_slots_free` (reserved slots not currently used by a chat run).

```bash
multica daemon autostart enable
multica daemon update-schedule set --runtime-id <runtime-id> --cron '0 2 * * *'
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "Internal Claude wrapper" \
  --command-name ccms --runtime-type claude
```

`daemon autostart` registers the current profile to start at login; see [Start at login](/daemon-runtimes#autostart) for platform details. `runtime usage` covers 90 days by default, and `--days` goes up to 365. `runtime update` asks the daemon on that computer to update its CLI to the given version; `--wait` keeps polling until the update finishes. `runtime profile create` takes the compatible tool through `--runtime-type` (the older `--protocol-family` still works); fixed arguments can currently be set only in the web app.

`daemon update-schedule get|set|clear --runtime-id <id>` reads or edits the update schedule of the machine that runtime runs on (see [Scheduled self-update](/daemon-runtimes#update-schedule)). `set` takes `--cron` (five fields, required), `--timezone` (IANA name, default `Asia/Ho_Chi_Minh`), `--window-minutes` (10 to 30, default 30) and `--enabled=false` to save the schedule paused. `get` also prints the next 3 fire times. Only the machine owner and the workspace owner can change it.

Deleting a runtime that still has active agents bound to it is refused by default. `multica runtime delete <id> --cascade` unbinds those agents, preserves their configuration and history, and cancels their active runs.

`multica runtime breaker list` shows each provider's circuit breaker; `multica runtime breaker reset <provider>` force-closes it (owner or admin only). See [Provider circuit breaker](/daemon-runtimes#provider-breaker).

See [Daemon and runtimes](/daemon-runtimes) for how it works and for custom profiles.

## Projects, workspaces, and autopilots

```bash
multica project create --title "Summer campaign" --lead "Lei Li" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "Operations" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "Weekly sales report" --agent "Ops helper" \
  --mode create_issue --issue-title-template "Sales report {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Europe/London
```

`multica project create --priority <urgent|high|medium|low|none>` and `multica project update <project> --priority <value>` set the project priority. It is stored only until the claim path reads it in a later release; `project_rank` does not use it yet.

- `--lead` takes the name of a member or an agent. `--default-branch-hint` only tells the agent the repository's default branch; it does not switch branches.
- A workspace's `--context` is provided to every agent in the workspace. `--slug` cannot be changed after creation. `--issue-prefix` is uppercased; changing it renumbers every existing issue, and old identifiers in external references stop resolving.
- `multica workspace update --routing-agent <agent-id> [--routing-fallback-agent <agent-id>]` names the agent that takes routing-only workflow steps (`todo`, `blocked`, `merged`, `need_decision` by default; change with `--routing-statuses`, send one status elsewhere with `--routing-overrides todo=<agent-id>`). The fallback takes over when that agent is archived, or when its run fails on a provider error. An override key `<workflow-id>:<status>` limits that override to one workflow. `none` turns a field off. Only a human owner or admin can change it, and each change is recorded in the activity log. The setting is stored as the `routing` job of `background_agents`. These flags are an alias for `multica workspace background-agents set routing`, and the old `/routing-agent` API route stays as an alias for one release.
- `multica workspace update --time-wakeup-skip-mode off|warn|block` sets the workspace time-wakeup skip mode (`settings.time_wakeup_skip.mode`). It patches that key alone, changes no other setting, and cannot be combined with other update flags. Only the owner can change it, and each change is recorded in the activity log. `off` turns the check off and runs every deferred time wakeup; `warn` records what `block` would do and still runs the fire; `block` defers an unchanged declared fire and requires agents to pass `--watch <inputs>` or `--watch always` on a time wakeup.
- `multica workspace update --auto-close-mode off|warn|block` sets the auto-close mode (`settings.auto_close.mode`). It patches that key alone, changes no other setting, and cannot be combined with other update flags. Only the owner can change it. See [Workspaces](/docs/workspaces) for the checks a close needs. An issue's author records `multica issue metadata set <issue> --key post_close_work --value none --type string` when nothing is left to do after review.
- `multica workspace update --blocked-run-skip-mode off|warn|block` sets the blocked-run skip mode (`settings.blocked_run_skip.mode`). It patches that key alone, changes no other setting, and cannot be combined with other update flags. Only the owner can change it. See [Workspaces](/docs/workspaces) for when an entry run is skipped.
- `multica workspace update --wakeup-live-join-mode off|warn|block` sets the live wakeup join mode (`settings.wakeup_live_join.mode`). It patches that key alone, changes no other setting, and cannot be combined with other update flags. Only the owner can change it. See [Workspaces](/docs/workspaces) for when a condition firing joins the agent's running run.
- `multica workspace update --run-budget-mode off|warn|block` and `--run-guard-mode off|warn|block` set the per-issue run budget mode (`settings.run_budget.mode`) and the weekly run guard mode (`settings.run_guard.mode`). Each patches its key alone and changes no other setting. The two flags can be given together in one command, for example `--run-guard-mode warn --run-budget-mode warn`; neither can be combined with any other update flag. Only the owner can change them. See [Workspaces](/docs/workspaces) for what each mode does.
- `multica workspace update --ask-guard-mode off|warn|block` sets the ask guard mode (`settings.ask_guard_mode`). It patches that key alone, changes no other setting, and cannot be combined with other update flags. Only the owner can change it. The command prints the saved workspace, and `multica workspace get` shows the mode under `settings`. `off` turns the guard off; `warn` counts misses and lets them through; `block` refuses them.
- `multica workspace update --merge-queue-routing off|warn`, `--merge-queue-bindings '<json>'` and `--merge-queue-watch-issue <issue-id|none>` set the merge queue settings (`settings.merge_queue_dequeue_routing`, `settings.merge_queue_actor_bindings`, `settings.merge_queue_watch_issue`). They can be combined with each other but not with other update flags. Only the owner can change them. `--merge-queue-routing block` is refused with `routing-not-available`, and so is a login in both binding lists.
- `--issue-title-template` interpolates only `{{date}}` (UTC, `YYYY-MM-DD`) and rejects any other `{{...}}` token. A schedule trigger's `--timezone` defaults to UTC.
- `--mode script --script <name> [--arg <value>]...` runs one allowlisted script under the agent's task token, with no model session. `--script` and `--arg` need `--mode script`, and `--mode script` needs `--script`. `--description` is never executed. With no daemon allowlist every script task fails closed. `--output json` shows the script name and args as `script_config`. `autopilot update --mode <other>` clears the script. The server deletes the task token when the task ends, on a best-effort basis. If the deletion fails, the token stays valid until it expires; nothing revokes it sooner. The run result records the script name, a SHA-256 of the argument list, the exit code and the duration under `script`, and sets `token_revoke_failed` when a deletion failed.

## Background agents

Each background job (`dm_title`, `quick_actions`, `compact`, `routing`) runs as a task of a primary agent, then a fallback agent. Show or set the workspace default, or your own chain:

```bash
multica workspace background-agents list
multica workspace background-agents set dm_title --agent haiku --fallback luna
multica me background-agents set dm_title --agent none   # back to the workspace default
```

`multica workspace update --compact-agent <id-or-name|null>` is an alias for `set compact` (see Compacting a web DM). `--agent` and `--fallback` take an agent id or name; `none` clears the field. `multica me` covers `dm_title`, `quick_actions` and `compact`; `routing` is workspace-only. Workspace writes need an owner or admin, and both commands refuse task tokens. See [Background Agents](/background-agents) for the no-agent behaviour and deadlines.

`multica workspace capability-routing [workspace]` prints the `capability_routing` setting (issue type to author and reviewer agents) as JSON, or `{}` when it is unset. It only reads; change the setting with `multica config propose workspace.settings --set 'capability_routing:=<json>'`. See [Workflows](/docs/workflows).

`multica workspace agent-role-scope [workspace]` prints the `agent_role_scope` setting (agent to the work classes another agent may assign it: `plan`, `plan_review`, `decision`, `debate`, `security_cosign`, `code_review`, `execution`) as JSON, or `{}` when it is unset. An agent with no entry is unrestricted. When an agent assigns an issue, or requests a review, from an agent whose scope excludes the work class, the server refuses with a hint naming the `capability_routing` author or reviewers; a person's assignment succeeds and leaves an audit note on the issue. The work class comes from the title's type prefix (`plan`, `decision`, `debate`), a `review(...)` scope (`plan`, `design`, `spec`, `decision` and `debate` are plan reviews, anything else, `security` included, is a code review), a child issue titled `security gate: <parent identifier>` under the issue it gates (the D8 co-sign), or else `execution`; security-typed work, a `security` review and a path in a title never make work a co-sign. It only reads; change it with `multica config propose workspace.settings --set 'agent_role_scope:=<json>'`. `multica agent get <agent>` shows one agent's scope.

`multica workspace queue-order show [workspace]` prints the effective `queue_order` (`priority` or `project_rank`) and `queue_aging_minutes` (5 to 720) as JSON. `multica workspace queue-order set [workspace] --order <mode> --aging-minutes <n>` changes one or both (owner or admin only; every change is audited with actor, old value, new value and time). `priority`, the default, keeps today's queue order. `project_rank` ranks queued runs by project priority, then parent issue priority, then their own priority, and each aging period a run waits lifts it one step; the claim path reads this setting in a later release, so for now the setting is stored and audited only. A refused value names the allowed values. Set `--order priority` to roll back.

## Browser leases

Inside a daemon task, lease the shared remote browser. The command goes through the local daemon, which holds the task's daemon credential; the agent never does. A granted lease prints the gateway URL and a short-lived token on stdout only; nothing is logged. A queued lease prints its queue position and no token.

```bash
multica browser lease --profile <profile-id> [--decision <decision-id>] [--output json]
multica browser renew <lease-id>
multica browser release <lease-id>
multica browser status <lease-id>
```

`status` never prints a token. `renew` prints a fresh one. A login profile needs `--decision`, the id of an answered decision request on the issue.

The server returns the gateway URL from `MULTICA_BROWSER_GATEWAY_URLS`, a JSON object that maps each host to its gateway URL (for example `{"c00":"https://c00.example.ts.net:35443"}`). Without an entry for the lease's host, the CLI prints a warning and no URL.

`multica chat` reads **the external chat session an agent is currently handling**; it is mainly for agents in chat integrations, not a general command for browsing arbitrary workspace conversations.

### Rename a DM

```bash
multica chat rename <session-id> "Release decisions"
```

A running workspace agent task can rename a DM in that workspace, including a DM owned by another person. The rename and its announcement commit together. The announcement shows the old title, the new title, and the authenticated actor. Titles must be nonempty, single-line, and at most 200 characters.

The agent receives only the session ID, new title, previous title, and announcement message ID. Rename does not grant permission to list DM lanes, read messages, access resume pointers, or change project context. Automatic title generation does not overwrite a manual rename, including a rename back to the original title.

### DM attention

```bash
multica chat attention [--stale] --output json
multica chat later <session> [duration | RFC3339 time]
```

`attention` lists the DM chains that need you, one row per chain, oldest `attention_since` first. Chains with nothing open, archived chains and chains whose `later` is still in the future are not listed. `--stale` keeps only `yellow` (4 h or more) and `red` (24 h or more) rows.

`later` snoozes the obligations the server shows for the chain right now. Durations take `2h`, `90m`, `7d`, `1d12h` or plain seconds; with no duration the server uses 2 hours. The server accepts 1 second to 168 hours from now. The CLI sends the value as given and prints the server's range error; it never caps silently. Repeat a call with the same `--request-id` and the due time does not move. Agent tasks cannot use `later`.

### Decision lane metadata

A running assigned issue task can open a three-minute decision window by posting a comment with `--decision-intent` and member mentions. Only that task can list active web DM lanes for the people named in the window:

```bash
multica chat sessions --issue MUL-123 --for <user-id> --output json
```

Omit `--for` only when the window names exactly one person. The person must still be an active workspace member who can invoke the asking agent, and their target must be unconsumed. A listing does not consume the window. Another run of the same agent, a chat task, PATs and JWTs cannot use this command.

The response contains only `id`, `title`, `updated_at` and `issue_mentions`, newest lane first. It never includes messages, unread counts or transcript previews. Archived sessions and channel-origin sessions are excluded. If no lane exists, the server creates a web DM titled `Decisions: <agent name>` for the named person. Expired, closed, deleted-tag and consumed windows are refused.

### Decision requests

A running assigned issue task asks a person in one call:

```bash
multica decision request --issue MUL-123 --for <user-id> --class reversible \
  --ask-file ./ask.md [--footer-file ./footer.md] [--parent <comment-id>]
```

`--for` accepts the person's user ID or their member ID in the issue's workspace, including workspace owners. The server stores the canonical user ID.

A running DM chat task can also ask, but only its own DM member: it must pass `--for <that member>`. Another member is refused with 403. `--session`, `--new-dm` and `--parent` are refused with 400. The card renders in the calling DM, and the request carries the decision ID, the member, the issue, the class and the expiry.

One call writes one issue comment (the ask plus the optional footer, top-level or under `--parent`), one DM message (the ask only) and one inbox ping. The footer reaches the issue comment only, so use it for handoff lines. Footer lines dispatch no agent, because an ask comment does not trigger tasks.

The server picks the DM: the lane of your latest request to that person on this issue, else the newest lane that mentions this issue, else a new `Decisions: <agent name>` DM. `--session <lane-id>` and `--new-dm` override the choice. The same checks as a decision-intent comment apply to the task, issue and person. One call asks one person.

A batch card closes the per-issue cards it covers. Pass `--covers <request-id>` (repeatable, at most 25) with the ids of open `reversible` or `product_direction` cards for the same person in the same workspace. The batch card must also be `reversible` or `product_direction`. When the person answers the batch card, each covered card closes as answered by the batch, its issue gets the quoted answer, and its asking agent wakes once. The DM folds each covered card into one row under the batch card. Only a plain choice card can be covered: a card with an attached action, a governed write ("Approve write"), an artifact, a human action, a gated class is never covered, and the person must answer that card itself. A covered card that gains one of these after the batch card was created stays open when the batch is answered. Each batch option must also be an option of every covered card with the same label and the same `what_happens` meaning, and the batch card lists every covered decision with its options and their meanings so the person sees what the answer closes. If the covered decisions cannot be loaded, the card offers no answer form. A covered card closes only when the person picks a batch option that is one of its own options, label and meaning alike: a free-text batch answer closes none, and a covered card that does not offer the chosen option stays open for its own answer. The server refuses a batch option answer (400, `covers_ack_required`) unless it carries `covers_ack`, a SHA-256 digest of the batch id, the sorted covered ids and the chosen option: an older client that cannot show the covered decisions cannot answer for them, and nothing is closed. While a person is in passkey recovery and the workspace gate blocks, a batch answer is refused if it would close a covered `product_direction` card, exactly as that card's own answer would be. Any withdrawal of the batch answer also withdraws every covered answer and reopens those cards: the person disclaiming it, an agent vetoing it, its source being removed or its answering turn failing, a lifecycle cancel of the batch card, a raise past a delegate, and the batch card being removed with its issue. The call is refused if any id is not an open, eligible card of that person, or if a covered card lacks a batch option or gives it another meaning.

If a decision-intent comment is still open for the task, the older two-step flow applies: pass `--session` or `--new-dm --for`, and the ask replies under the intent comment. `--parent` is refused there.

`--recovers <event-id>` marks the request as the answer to an ask guard event, for example one named in a refused operation or a recovery notice. The server clears that event in the same transaction as the request, but only when the event is on this issue and was raised for the person the request asks. A request for one person never clears another person's event, and a request without `--recovers` clears nothing, even an unrelated one for the same person. An event for another issue or person is refused with `400`. A request recovers one event only: a retry of the same request that names a second event is refused with `400`.

`--wait` (on `multica decision request` and `multica decision ask`) asks the server to park the issue while the request is open. Pass it only when nothing else can proceed. The issue parks only when the workspace setting `decision_ask_park` is `on_wait`. With `always`, the default, every request parks and `--wait` changes nothing. A `blocked` issue parks either way. Without `--wait`, the issue keeps its status and assignee, and the answer wakes the asking agent.

Each option of a `decision` card can say who acts after it is picked. Set `after_choice` to `agent_run`, `human_steps` or `record_only`. An `agent_run` option lists `agent_commands`: one or more argv arrays, for example `["$MULTICA_CLI_PATH", "daemon", "restart"]`. A command given as one string is refused with the field name, because the server parses no shell text. An option that uses a console-only surface sets `agent_surface` to a catalog key instead. The check reads these typed fields only, never `what_happens`. It compares each command, after it is reduced to a tool and its leading words (the path, `.exe` and the global flags `--profile`, `--server-url`, `--workspace-id` and `--debug` are dropped), with the workspace setting `agent_cannot_do`: a list of `{key, tool, subcommand, human_step}` entries of things an agent run cannot do. Without that setting the entries are `daemon restart` and `daemon stop` of `multica`. A wrapper such as `env`, `sudo`, `nohup`, `timeout`, `xargs`, `bash`, `sh` or `zsh` hides the real command, so give the command itself as argv. The workspace setting `agent_cannot_do_mode` (`off`, `warn`, `block`; default `off`) decides the result. In `warn` the card is created and the response carries a hint. In `block` the server returns `400` with the option label, the catalog key and the human step to put in `human_steps`, and creates no card. In `warn` and `block`, an option with no `after_choice` adds one hint or is refused with the field name. Action cards and waiver-topic cards are not checked. A workspace settings save, or a settings patch approved with a passkey, that would leave `agent_cannot_do_mode` at `warn` or `block` with no `agent_cannot_do` list is refused with `400`: set the list first, or set the mode to `off`. A workspace that is already in that state stays writable.

In `warn` and `block`, two more refusals read the same typed fields. An option whose `agent_commands` only run `multica issue status` or `multica issue assign` is refused with the typed fix: send `after_choice` `server_action` with `options[].action` `issue.status.set` or `issue.assign` instead of a run that repeats the move. An option that runs `multica decision propose` or `multica issue budget raise|top-up` is refused with "attach the action with --action-file; the passkey goes on this card", because a second card would need a second passkey. `multica issue get` and other reads are accepted. A catalog entry may also set `allowed_agents` (a list of workspace agent ids): an `agent_run` command that matches the entry is refused unless the asking agent is listed, and the refusal names the entry's `human_step` or `issue.assign` to a listed agent. The built-in `c00_restart` (`docker container restart`) and `c00_compose_restart` (`docker compose restart`) entries list the C00 agent. A CI card has no asking agent, so an entry with `allowed_agents` refuses it. A settings write that names an agent outside the workspace in `allowed_agents` is refused with `400`.

A fourth value, `server_action`, makes the server act as the person who picks the option. Give the option `action {type, params}`: `issue.status.set` with `params.status` (a status key such as `in_review`), or `issue.assign` with `params.assignee_type` (`member` or `agent`) and `params.assignee_id` (a UUID). The server lower-cases and trims these values, stores them, and adds one line such as "On pick: the server moves CHE-123 to in_review as you." to `what_happens`. An option with `after_choice` `human_steps` may add `after_wait`, which names the one event the agent waits on: `until_pr {url, state}` (`checks`, `merged`, `conflicts` or `dequeued`), `until_status {status}` or `until_issue {issue, state}` (`done`, `ended`, `in_review` or `blocked`). The workspace setting `decision_server_actions` (`off` or `on`; default `off`) lets a card carry `server_action`. While it is off, or holds anything else, the server returns `400` with the code `server_actions_off` and the field path. A topic ask, an `--action-file` request, a `--kind action` card, a `--covers` batch card and a CI card refuse a typed option and name its field path. The workspace setting `standing_answers` (default `{"review_cap":"off"}`; `review_cap` is `off` or `split`) reads as `off` when malformed. Only a workspace owner can change `decision_server_actions` and `standing_answers`.

The workspace setting `decision_card_lint_mode` (`off`, `warn`, `block`; default `off`) checks the wording of an option card. In `warn` the card is created and the response carries one hint per finding. In `block` the server returns `400` with a reason code and the field path, and creates no card. The codes are: `weak_cons`, every con of an option is only your time ("takes 1 minute of your time") or one more check or review; `option_markdown`, a table, heading, image, HTML, fenced code or Mermaid block in `label`, `what_happens`, `pros` or `cons` (bold, italic, inline code, lists and links are allowed); `option_leak`, option text that marks the recommendation ("recommended", "(rec)", or bold on one label only); `default_leak`, on class `spend`, `deploy`, `publish`, `irreversible` or `product_direction`, a `default_if_no_reply` that names an option (write "No action until you pick."). English and Vietnamese phrases are matched. Action cards and waiver-topic cards are not checked. When the issue comment of a card does not mention the person it asks, the server adds the mention and logs `mention_missing`; this is never a refusal.

The workspace setting `decision_card_thread` (`off`, `on`; default `off`) gives each new card its own thread. With `on`, the issue comment of a card is a new root comment, and the server always adds the mention of the person it asks, whatever `decision_card_lint_mode` holds. The decision ping stays the only Inbox item; the added mention creates none. If you pass `--parent`, that thread becomes the source: the new thread records it, the source thread gets one system reply with a link, the source thread keeps its resolution, and the CLI prints `Card placed in a new thread <id>; thread <source root> got a link.` A decision-intent comment that has a parent opens a new thread the same way, and the card is placed in that thread. A re-ask and an ask a DM agent writes in its DM keep their place. With `off`, nothing changes.

The workspace setting `design_card_guard` is an object with `mode`, `doop_origin`, `design_url_property_id` and `design_workflow_id`. `mode` is `off`, `warn` or `block`; an absent key or a missing `mode` is `off`. With `warn` or `block`, `doop_origin` (an `https` origin without a path) and `design_url_property_id` (a UUID) are required; `design_workflow_id` (a UUID) is optional. The server refuses any other field, a `null` value or a wrong type with `400`. A settings change by decision action may name the key. The setting is only read and checked for now: it does not yet warn on or refuse any card.

### Decision proposals

A running task token proposes a governed action for a person to approve with a passkey. The proposal changes nothing itself.

```bash
multica decision propose issue.run_budget.raise --version 1 --issue MUL-123 \
  --for <user-id> --param window_id=<id> --param new_cap:=40 [--reason "..."]
multica decision propose <action-type> --version 1 --issue MUL-123 --params-file ./params.json
```

`--version` and `--issue` are required. `--param k=v` sends a string and `--param k:=<json>` sends raw JSON; `--params-file` takes one JSON object and cannot be combined with `--param`. The command prints the approve-card link. For a run-budget action that link opens the approval on the issue; for any other action it links to the card in the chat, where the person approves it. A plain option card (`multica decision request` without `--action-file`) cannot apply a change: Approve only records the answer. The server cannot read intent, so it does not refuse such a card; when the decision or an option reads like a workflow, agent, squad, workspace or budget change (or names an allowlisted action type) it adds an advisory hint. Send that change with `multica decision propose`. A refusal shows the server's status and error code. `multica issue budget raise` and `multica issue budget top-up` use the same route under a task token (add `--for <user-id>`); with a personal access token they open the spend request as before. Both commands take one or more issue IDs: `multica issue budget top-up CHE-1 CHE-2 CHE-3 --for <user-id> --goal "<goal>"`. One ID keeps the single proposal. Several IDs under a task token call the batch route once and print one card link; `--goal` names the batch (default: the action and the issue count) and `--output json` returns the batch id and one proposal id per issue. Under a personal access token each ID opens its own request. The batch route needs a chat task and takes up to 25 issues; the server approves a batch of raises with one passkey but refuses a batch of top-ups at approval, so approve top-ups one by one.

Run-budget next step: the 80 % notice on an issue carries the numbers and one ready command, for example `Run budget: 20 of 25 runs used on CHE-1234 (workflow Default, cap 25). Ask for more: multica issue budget raise CHE-1234 --runs 40`. A run the budget refuses returns the error code `run_budget_exhausted` with `runs_used`, `runs_limit`, `workflow_id`, `window_id`, `open_card` and `next_command`. `multica issue budget get <issue> --output json` returns `open_card` and `next_command` too. While a raise or top-up card is open for the issue's current window, `next_command` says to wait for that card, and a repeat `multica issue budget raise` returns the same card instead of opening another. Under a task token `--for` defaults to a workspace owner on an issue task, and the help lists `raise` only; `top-up` stays available to members. A task on any issue of the workspace can open a `raise` card for another issue, such as one over budget that cannot run a task of its own. The card still needs a person's passkey approval and nothing is applied before it. Each card the server, a member or an agent opens adds one `run_budget_ask` activity row that records the actor type, the actor and the action type.

A person can revoke an applied action while it is revocable. Run `multica decision revoke <request-id> --why "<reason>"`. An action is revocable only when it was applied, its type has an exact inverse, and nobody has revoked it. In this release only `agent.pause` has an inverse (`agent.resume`), and only when the approval paused the agent and nobody has changed its pause since. Every other action type stays non-revocable. Only the person the ask is for can revoke, with the same role rule as Approve; an action that needs a passkey is revoked in the app. The server records who revoked, when and why, runs the inverse, and wakes the asking agent with the outcome `revoked`. A revoke is refused for a rejected, expired, not applied, discussion-only or already revoked decision. `multica decision get <request-id>` shows `revocable` and, after a revoke, the `revoke` record (`at`, `by`, `reason`). For an answered decision it also shows `answer.woken_at` and `answer.wake_outcome` (when and how the answer reached the agent, null until it did) and `receipt_state` (`recorded`, `delivered`, `picked_up` or `disclaimed`). `receipt_state` is the receipt state of the answer, not the state the card displays: for an answered decision with no action, withdrawal or disclaimer, the card folds only at `picked_up`; at `recorded` or `delivered` it shows that state until two minutes after the answer, then "Not picked up", and stays unfolded.

`issue.project.set` moves the issue to another project: `multica decision propose issue.project.set --version 1 --issue MUL-123 --param project_id=<project-id>`. The card shows the project, workflow, run cap and runs used before and after, and says whether the move widens the run budget. A move that widens it is a `spend` card; any other move is `reversible`. Only a workspace owner can approve it. The card is refused if the issue left its project, or the target workflow's budget grew, after the request.

`issue.project.quick_set` and `project.workflow.quick_set` are opened by the server, not proposed: an agent with a task token that moves an issue into a project that follows Quick, or switches a project to Quick, gets an owner card instead of a refusal, and the move happens only after the owner approves with a passkey (`spend` class). The card shows the workflow, run cap and, for a project switch, how many issues move to another status. It ends as `stale_base` if the issue, the project or the run budget changed after the request.

Run-budget auto-approver: when an issue spends its run budget, the server approves the next window itself if the last window made progress, shows no anomaly, and the workspace daily envelope still has room. The audit comment on the issue names the rule (`auto-approver v1`) and the kill switch. An approved window also resumes the run the server refused, so the issue never parks in `blocked`. Progress means a run moved the issue's status, changed a linked PR's head or state (a PR comment does not count), or committed; a comment never counts, whatever it says, so a run with none of these is a no-op. A loop (the same failed check, failed CI workflow or run error on the heads or runs of 3 or more runs; comments are not read), a no-op window (80% or more of runs deliver nothing), a token spike (tokens per run above 3 times the workspace median), churn (3 or more top-ups on one issue in 24 hours) or an agent in the OpenAI pool while the OpenAI cut is in force is never auto-approved: the owners get at most one batch card per day; later anomalies that day arrive as messages in that card's chat, and the brief lists the held-back issues. Any other case, including an issue that is already `blocked` or a refused run that is not for the issue's agent assignee, falls back to the per-issue card. Workspace setting `run_budget_auto`: `enabled` (default `false`: the auto-approver ships off) and `daily_envelope` (extra runs per ICT day, default `300`) and `expected_checks` (each entry is `name@appid@workflow-path`: the check name, the numeric GitHub App id that produces it and, for GitHub Actions (app `15368`), the workflow file that runs it, for example `go-test@15368@.github/workflows/ci.yml`; an entry for another App may be `name@appid`; every pushed head must hold each, finished, before its CI counts as known; default empty, which holds every window that pushed a head). A snapshot with only some of the expected checks finished does not count as known. An entry counts only as a finished Checks API run of that name from that App and, when it names a workflow, from that workflow (the run must belong to a workflow run the server recorded for that head): the same name from another App or another workflow, a commit status, a GitHub Actions entry without a workflow, or an entry without a valid app id holds the window. A same-name run from another workflow that is still running also holds it. Turn it on (or back off with `"enabled":false`) with `multica config propose workspace.settings --set 'run_budget_auto:={"enabled":true}'` or a `workspace.settings` config proposal.

### Covered fields need a passkey action

A task token or cloud-node token cannot write these fields through the older routes: `agent.instructions`, `squad.instructions`, `workspace.context`, workflow steps and step instructions, and the workspace settings keys on the decision-action allow table (`compact_prompt`, `auto_compact`, `idle_started_guard`, `wakeups_paused`, `mermaid_orientation` and the other plain operational keys). The server answers 403 with `code: passkey_action_required` and an `action_type` naming the action to propose instead (`agent.instructions.set`, `squad.instructions.set`, `workspace.context.set`, `workflow.steps.set`, `workspace.settings.patch`). The stored value does not change. A vote receipt, a decision binding, a PASS receipt and the Hermes exception no longer lift this refusal. Propose the action with `multica decision propose <action-type>`; a person approves it with a passkey. Writes by a person, and `project.description`, work as before.

### Config change proposals

`multica config propose` builds the action file for a workspace config change. It reads the live value, computes `before_sha256` and `after_sha256` with the recipes the server recomputes, and writes the file that `multica decision request --action-file` takes. It sends nothing and writes no secret. A person still approves with a passkey.

Fields: `agent.instructions <agent-id>`, `squad.instructions <squad-id>`, `workspace.context`, `workflow.steps <workflow-id>`, `workflow.step.instructions <workflow-id> --status-key <key>`, `workflow.budget <workflow-id>` and `workspace.settings --set key=value|key:=<json>`. Text fields take `--file` (UTF-8, no NUL byte). `workflow.steps` takes the steps array as the workflow GET returns it; edit that output, because the server refuses the request (`after_digest_mismatch`) if it normalizes your steps differently. For `workflow.step.instructions` the server computes the after digest, so the file carries no `after_sha256` and the printed digest is for comparison only. Pass `--out <path>` to write the file or `--dry-run` to print both digests and the action without writing. `--expires-in <seconds>` sets the request expiry.

`workflow.budget <workflow-id>` takes `--max-runs <n>` (1 to 1000; 0 clears the cap) and `--include-child-prs=<true|false>` in place of `--file`; name at least one, and a field left out keeps its stored value. An agent cannot write these two fields on a workflow directly (`budget_requires_decision`): propose the change, request the decision, and the server applies it on approval if the workflow still matches the digest the CLI read.

An agent with a task token opens the card in one call: `multica workflow update <workflow-id> --max-runs-per-issue 40 --issue <issue> --for <user-id>` reads the live workflow, proposes `workflow.budget.set` with only the budget flags you name, prints the card URL and writes nothing until the owner approves. Repeating the call returns the same card. A budget call carries no `--name`, `--description`, `--steps-file`, `--start-status`, `--map` or `--dry-run`; the command refuses them before any request, so run two commands. `--print-hash` prints `before_sha256` and `after_sha256` of the budget change. `multica config propose workflow.budget` names the same flag `--max-runs`. `multica issue update <issue> --workflow <workflow-id>` and `multica issue create --workflow <workflow-id>` take the same `--print-hash` and `--decision-id` (field `issue.workflow`) when the workflow has a wider budget; both commands follow one rule, and an owner's interactive session needs no decision. From an agent run, `multica issue update <id> --workflow <workflow-id>` with a wider budget needs no decision: it opens an approval card for the workspace owners, prints its action id and URL, and leaves the issue unchanged until an owner approves it with a passkey. The approval fails with `stale_base` if the issue's workflow, its project's workflow or its budget changed after the card opened.

Any other field is refused with `denylisted` before the CLI reads anything: `project.description`, passkeys and the decision gate, members and roles, owner transfer, auth and integration secrets, workspace deletion, the action registry, and `delegated_governed_writes`. A settings key off the server allow table is refused the same way, and a patch that mixes allowed and refused keys is refused whole. The server checks again at request and at approval.

```bash
multica config propose workspace.context --file ./context.md --out ./action.json
multica config propose agent.instructions <agent-id> --file ./instructions.md --dry-run
multica config propose workflow.step.instructions <workflow-id> --status-key review --file ./step.md --out ./action.json
multica config propose workflow.budget <workflow-id> --max-runs 40 --include-child-prs=false --out ./action.json
multica config propose workspace.settings --set compact_prompt="..." --set wakeups_paused:=false --out ./action.json
multica decision request --issue MUL-123 --for <user-id> --class reversible --ask-file ./ask.md --action-file ./action.json
```

### Shadow report

Any workspace member reads the System 1 shadow report:

```bash
multica decision shadow-report [--since <RFC 3339>] [--until <RFC 3339>] --output json
```

The `decision` and `routing` blocks cover all time. The `route` block covers the window `[since, until)`: `--since` and `--until` take RFC 3339 times, `--until` defaults to now and `--since` to 24 hours before `--until`. The server refuses a bad time or a `--since` after `--until` with 400.

The `route` block counts one population of events: agent status changes marked as leaving a routing step (`eligible_exits`) and the route labels that carry the same event id (`matched_labels`). `label_coverage` is `matched_labels / eligible_exits` and never exceeds 1. `via_route_share` is the part of matched events whose first label came from `issue route`, not from the status fallback. `duplicate_labels` counts labels that share an event with an earlier label (target 0). `labels_total`, `owner_only_labels` (a route that kept the status, so it has no event) and `non_routing_labels` (a route from a step with no routing agent) sit outside coverage. `overridden` counts agent labels a person reversed within 1 hour, and `override_rate` is `overridden / labels_total`. The block also carries the per-class `decided`, `predicted`, `agreed`, `coverage` and `precision`.

### System 1 labelling

The assigned System 1 labeller agent reads its blind queue and writes labels from inside its own agent task. The server takes the agent and task from the task token; a member session or a PAT gets 403.

```bash
multica system1 label-queue --scope <scope> --kind burn_in|eval --output json
multica system1 label submit --observation <observation-id> --kind burn_in|eval --label <value> [--supersedes <label-id>] --output json
```

The queue holds observation ids and typed features, never a prediction. It holds at most 20 observations of the scope that have no live label of this kind. The server stores the sampled ids and the seed when it serves the queue, and a task that asks again gets the same sample. `--supersedes` takes the id of the live label to correct; without it a second label for the same observation gets 409.

Any workspace member reads the System 1 qualification state of each scope and predictor version:

```bash
multica system1 report [--scope <scope>] --output json
```

`--scope` is `test_first_waiver` or `ci:<repo>:<protocol>`. Each row covers the latest epoch of one predictor version. Only observations created at or after the epoch start count, and a new predictor version opens its own epoch. A case is one prediction with a label of record (the newest label that is not superseded). `denominator` counts cases with a non-abstaining prediction and a mapped label, `agreed` those where they match, `abstained` labelled cases the predictor skipped, and `unmapped` free-text answers. `status` is `qualified` at 7 days, a denominator of at least 20 and agreement of at least 90%. It is `insufficient_data` after 4 weeks with fewer than 20 counted cases, `demoted` once an epoch is demoted, and `collecting` otherwise.

## IDs and output formats

Issues use keys like `MUL-123` or full UUIDs; short UUID prefixes are not accepted.

`list` commands for other resources usually print copyable short IDs and support `--full-id` for the full UUID. When a short ID is ambiguous, the CLI asks for more characters or the full UUID. Short task IDs also require `--issue` to identify the owning issue.

Many commands support structured output:

```bash
multica issue list --output json
multica agent list --output json
```

Scripts should use JSON output rather than parsing the terminal-oriented tables. The output formats and pagination flags each command supports are defined by `multica <command> --help`.

## Profiles and configuration

The default configuration lives in `~/.multica/config.json`. Use `--profile <name>` to isolate a separate set of server address, token, default workspace, and daemon state:

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

Named profiles live in `~/.multica/profiles/<name>/config.json`. Inspect the current values:

```bash
multica config show
multica config show --profile staging
```

Do not set `MULTICA_DAEMON_PORT` in the host shell, Compose service, or container entrypoint that starts a daemon. The host daemon normally derives its health port from `--profile`; if that port cannot be bound, it uses an available loopback port and injects the actual port into agent tasks itself. Remove the variable from older startup environments entirely: versions 0.4.22 and 0.4.23 otherwise mistake that shell for a managed task and reject login. Newer versions let guarded human login and `daemon status` recover when the port is the only task signal, but ordinary API and profile-resolving commands intentionally remain fail-closed until the variable is removed.

When the CLI runs inside a daemon-managed agent task, it does not load or modify these human-owned profile files. Multica API commands authenticate with the task-scoped credential injected by the daemon. `config show` and `config set` use private task-local state; human/local commands such as `login`, `logout`, `setup`, `workspace switch`, local runtime profile path changes, `daemon start` / `stop` / `restart`, `daemon logs`, and `daemon probe-runtimes` are unavailable. `auth status` does not print token material in this context.

`daemon status` and `daemon disk-usage` stay available so an agent can inspect the runtime hosting it, scoped to that runtime: `status` probes the health port the daemon injected, and `disk-usage` scans the workspaces root the daemon injected. Neither accepts `--profile`, `disk-usage` also rejects `--all-profiles` and `--workspaces-root`, and its STATUS column is blank because resolving it would require the human's stored token. Use `du` and `df` for anything outside that scope.

This protects implicit Multica CLI profile resolution while preserving the normal `HOME` and XDG variables used by other provider tools. It is not an OS filesystem boundary: processes running as the same system user may still open an explicitly known path. Use a dedicated user, container, VM, or equivalent isolation when that stronger guarantee is required.

## Command reference

The tables below cover every current top-level command, grouped the way the CLI itself groups them. All commands accept the global flags `--server-url`, `--workspace-id`, `--profile`, and `--debug`. `--output` is registered per command, and the default format varies: `list` commands default to a table, while `get` and `create` commands mostly default to JSON. ### Issue attachments

For `issue create`, `issue update`, and `issue comment add`, each `--attachment` takes one literal file path, including any commas or double quotes in the filename. Repeat the flag for multiple files: `--attachment 'report,final.csv' --attachment notes.txt`. Omitting the flag attaches no files; an explicitly empty path is an error. All local paths are checked before any file is uploaded.

Migration from CSV parsing: replace `--attachment a,b` with `--attachment a --attachment b` to attach two files. The former now selects a single file named `a,b`. Remove extra CSV quotes from the old workaround `--attachment '"report,final.csv"'`; use `--attachment 'report,final.csv'` unless the filename itself contains those double quotes.

## Driving Multica from another coding agent

If most of your work already happens inside Codex, Claude Code, or Cursor, you can operate Multica from there instead of switching to a terminal. The [Multica CLI skill](https://github.com/multica-ai/multica-cli) teaches those agents to drive the commands on this page safely: reading issues and comment threads without burning tokens, writing comments through a file, and handling the side effects that mentions, status changes, and assignments carry.

It runs entirely through your authenticated CLI and grants no access of its own — permissions still come from your login, selected profile, and workspace. It requires CLI v0.4.26 or newer. The repository README covers installation for the Claude Code plugin marketplace, the Codex skill installer, Cursor, and any other tool that loads Markdown instructions.
