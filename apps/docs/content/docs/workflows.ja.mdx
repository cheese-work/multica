ワークフローは、プロジェクトのタスクが通るステップ、各ステップの担当者、そこで行うことを決めます。

たとえば、開発の流れを次のように組めます。

| ステップ | 担当 | 行うこと |
|---|---|---|
| 開発 | 開発エージェント | 変更を実装し、レビューの準備をする。 |
| レビュー | レビューエージェント | 結果を確認し、QA へ渡すか修正のために戻す。 |
| QA | チームのメンバー | 実際に試して、完了にしてよいか判断する。 |

タスクをレビューに移すと、レビューエージェントに引き継がれます。説明、議論、それまでの成果は同じタスクに残るので、次の担当者は続きから取り組めます。

**開発デリバリー**テンプレートはこの構成です。ワークフローを選んでいないプロジェクトは **Default** を使います。すべてのステータスを使え、自動の引き継ぎもなく、これまでどおりです。

## ワークフローを作る

ワークスペースの `owner` または `admin` が、Web またはデスクトップアプリで作成できます。

<Steps>
<Step>

**設定 → ワークフロー**で**新規ワークフロー**を選びます。空白から始めるか、**開発デリバリー**、**コンテンツ制作**、**コミュニティ運営**のテンプレートを使えます。

</Step>
<Step>

名前を付けて、必要なステータスの列を選びます。中央の列はドラッグで並べ替えられます。

</Step>
<Step>

列を選び、タスクが入ったときの動作を**引き継がない**、**エージェントに渡す**、**メンバーに渡す**から選びます。メンバーの一覧からは**プロジェクトリード**も選べます。

</Step>
<Step>

エージェントに渡す場合は、このステップで行うことを書き、**完了したら移動**する先（未設定なら次の列）と**差し戻す先**（受け取った作業が不十分でやり直しが必要なときに使います）を選びます。外部の理由で進められないときは、差し戻しではなく **Blocked** を使います。

</Step>
<Step>

エージェントが受け取る説明をプレビューして、保存します。

</Step>
</Steps>

新しいステータスを追加した場合は、一度保存してからそのステータスの引き継ぎを設定します。

引き継がない場合、担当者は変わりません。メンバーへの引き継ぎでは担当者だけが変わり、エージェントは起動しません。エージェントに渡す場合はそのステップの作業を依頼します。呼び出す権限が必要で、実行にはそのコンピューターがオンラインである必要があります。

`keep_other_assignee: true` を付けたステップは、現在の担当者が意図して選ばれた場合（このステップの担当でも、課題が離れるステップの担当でもない場合）に引き継ぎを行いません。その担当者が課題を持ち続け、担当者がエージェントならこのステップの実行が始まります。既定ではオフで、API または CLI で設定します。一時的な機能で、課題ごとのワークフロー（CHE-5024）で置き換えられます。

`chain_same_owner: true` を付けたステップは、エージェントが課題をそのステップへ移し、そのエージェント自身がステップの担当である場合、新しい実行を開始しません。ただし、そのエージェントの実行が始まったステップの担当の種類（エージェント、プロジェクトリードなど）が同じである場合に限ります。エージェントは同じ実行で作業を続け、ステータス変更のレスポンスにステップの指示が `step_brief` として含まれ、`multica issue status` がそれを表示します。別のエージェント、担当の種類の変更、または人による移動では、従来どおり実行が始まります。一括更新では連鎖しません。既定ではオフで、API または CLI で設定します。

## プロジェクトで使う

プロジェクトを開き、**ワークフロー**のプロパティで選びます。ワークスペースの `owner`、`admin`、およびメンバーであるプロジェクトのリードが切り替えられます。

確認画面には、今のステータスを保つタスクが表示されます。新しいワークフローにないステータスを使っているタスクは、移動先を選びます。ワークフローを切り替えるだけでは、担当者の引き継ぎやエージェントの起動は行われません。

プロジェクトのボードはワークフローの列に沿って表示されます。タスクで選べるステータスもそのステップに限られ、引き継ぐ相手が表示されます。別のワークフローを選んでいないプロジェクトは **Default** を使います。あとで Default に戻すこともできます。

## タイトルの種類からワークフローを選ぶ

ワークスペースのオーナーまたは管理者は、ワークスペース設定に `workflow_by_type` を設定できます。例: `{"design": "<ワークフローID>", "plan": "<ワークフローID>"}`。タイトルが `design(x): …` のように対応付けた種類で始まる新しい課題は、プロジェクトのワークフローではなくそのワークフローに従います。`--workflow`（CLI）や明示的な選択が常に優先されます。対応のない種類、またはワークフローが存在しない場合は、プロジェクトのワークフローのままです。`multica issue create` は選ばれたワークフローを表示します。タイトルに対応付けた種類があると、作成画面は選ばれるワークフローのステータスと引き継ぎを表示します。この対応付けはワークスペースのポリシーで、エージェントを含むすべての作成者に適用され、非対話の呼び出しが明示的な `--workflow` に受ける実行予算の確認は行われません。大文字小文字だけが異なるキーが複数ある場合は、アルファベット順で最初のものが使われます。後からタイトルを変えてもワークフローは変わりません。更新のレスポンスには 1 行の `workflow_hint`（`multica issue update` が表示）が含まれ、移すためのコマンドを示します。

## 能力でルーティングする

ワークスペース設定 `capability_routing` は、課題タイプを作成者エージェントと順序付きのレビュアーエージェント一覧に対応付けます。例: `{"feat": {"author": "<エージェント ID>", "reviewers": ["<エージェント ID>"]}}`。キーは小文字のタイプ、ID はワークスペースのエージェントで、`reviewers` は空にできず、作成者はレビュアーになれません。既定では未設定で、未設定なら動作は変わりません。読み取るのは **Author** ハンドラーだけです。変更は `workspace.settings` カード (`multica config propose workspace.settings --set 'capability_routing:=<json>'`) だけで行い、通常の設定保存は保存済みの値を保持します。`multica workspace capability-routing` で読み取れ、未設定なら `{}` を表示します。

**Author** は「進行中」などのステップに指定できるハンドラーです。ステップに入った課題は作成者に渡ります。作成者は、この課題を最後にこのステップへ移した人またはエージェントで、いなければ `capability_routing` が課題のタイプ (タイトルの Conventional Commit プレフィックス、例: `feat`) に対して指定する `author` です。テーブルを変更しても、課題がすでに持つ作成者は変わりません。人が課題を再割り当てすると、その人が次回の入場時の作成者になります。どちらもなければ、ステップは誰にも引き渡さず、ワークスペースが作成者をルーティングしていない場合はワークフロー lint が警告します (WF015)。`multica workflow handoff set <workflow> <status-key> --handler author` で設定します。

## 次のステップへ渡す

タスクのステータスを変えるか、カードを別の列へドラッグします。引き継ぎのあるステップでは、相手を確認します。エージェントの場合は、受け取る説明も確認できます。

<WorkflowDemo />

プロジェクトでタスクを作成し、そのステータスに引き継ぎがある場合、担当者を選んでいてもタスクはそのステップの担当者に直接渡ります。エージェントならすぐに作業を始めます。作成画面には「作成後に…に引き継ぎます」と引き継ぎ先が表示されます。まだ何も始めたくない場合は Backlog に作成します。

前の担当者がエージェントで、まだ実行中または開始待ちの場合は、確認画面にそれを停止またはキャンセルする選択肢が加わり、最初から選択されています。2 つのエージェントに同時に作業させたい場合以外はそのままで構いません。そのエージェントが投稿したコメントと保存済みの作業は残ります。

「完了したら移動」と「差し戻す先」は、次にタスクをどこへ移すかをエージェントに伝えます。実行が終わっただけではタスクは次に進まず、そのステップを担当するメンバーやエージェントがステータスを更新します。エージェントがタスクを次のステップに移した場合も、そのステップの引き継ぎが同じように行われます。

引き継ぎとその説明はタスクのタイムラインに残ります。プロジェクトのボードにあるワークフローメニューから、流れ全体を確認できます。

## PR がマージされたとき [#pr-merged]

マージによるステータス変更は、ワークスペースの 1 つの設定で決まります: **設定 → コード → PR マージ後のタスクのステータス**。[GitHub 連携](/github-integration)を参照してください。ワークフローのボードはこのルールを描きます。**PR merged** という名前の破線の矢印が「Any step」のマーカーから設定で指定したステップへ入り、そのステップのカードには**設定 → コードで設定**と表示されます。この矢印は読み取り専用です。エディターで選択、移動、削除はできず、ワークフローには保存されません。**変更しない**の場合、矢印は描かれません。設定がワークフローにないステータスを指している場合、エディターには、このワークフローでは PR のマージでステータスが変わらないことと、設定 → コードが指定しているステータスを示す 1 行が表示されます。

そのステップに担当者がいれば、マージによってタスクがその担当者に渡され、通常の移動と同じように実行が始まります。

### `pr.merged` 遷移は非推奨です

古いワークフローには、`pr.merged` をガードにした遷移が保存されていることがあります。設定が**変更しない**以外の間、保存された `pr.merged` 遷移は自分ではタスクを移動せず、設定と同じ判定を実行します。エディターのガード一覧には `pr.merged` が表示されなくなり、追加する保存は設定 → コードを案内するメッセージとともに拒否され、保存済みのものは非推奨として表示されます。**変更しない**の場合、保存済みの遷移は以前と同じように動きます。今後のリリースで削除されます。

## ワークフローを調整する

複数のプロジェクトで同じワークフローを使えます。**設定 → ワークフロー**で保存した変更は、それを使うすべてのプロジェクトに反映されます。1 つのプロジェクトだけ変えたいときは複製し、そのプロジェクトでコピーを選びます。

管理者はプロジェクトのボードからも引き継ぎを設定できます。列の見出しにカーソルを合わせて**引き継ぐ…**をクリックするか、表示されている担当者をクリックします。ほかのプロジェクトと共有しているワークフローでは、**この変更をどこに適用しますか？**と確認されます。現在のプロジェクトだけを選ぶと、そのプロジェクト用にワークフローが複製され、ほかのプロジェクトは変わりません。

列を削除する際、そこにタスクが残っている場合は移動先を選びます。それ以外のタスクは変わらず、この移動でエージェントは起動しません。ワークフロー一覧の下にあるステータスライブラリでは名前や色を変更でき、同じステータスを使う場所すべてに反映されます。

ワークフローエディターの**Issue あたりの最大実行数**で、ワークフローが Issue をブロックするまでに 1 つの Issue が開始できる実行数を制限できます（1〜1000。空欄の場合は既定値の 15）。変更にはサインイン済みの Web またはデスクトップのセッションが必要です。この欄を変更しない保存は、どのクライアントからでも行えます。隣の**子 PR を含める**スイッチは、PR ガードがサブ Issue の PR も読むかどうかを決め（既定はオン）、同じ規則に従います。エージェントやトークンはどちらの欄も直接変更できません。`budget_requires_decision` が返るので、`multica config propose workflow.budget` で変更を提案し、オーナーがパスキーで承認します。エージェントやトークンが、より広い予算のワークフローで Issue を作成または付け替える場合も同じ制限が適用されます（`budget_rebinding_requires_interactive`）。同じ決定で解除できます。`multica issue create` と `multica issue update` は `--workflow <id> --decision-id <id>` を受け付けます。 決定のクラスは `spend` で、オーナーがパスキー復旧中でないことが必要です。ワークスペースのパスキーゲートが `block` の間は、オーナーがパスキーで回答している必要もあります。満たさない場合は書き込みが拒否され、不足している条件が示されます。 エージェントの実行から、より大きな予算になる `multica issue update <id> --workflow <workflow-id>` を実行する場合、決定は不要です。ワークスペースのオーナー向けに承認カードを開き、そのアクション ID と URL を表示し、オーナーがパスキーで承認するまで課題は変更されません。カードを開いた後に課題のワークフロー、プロジェクトのワークフロー、または予算が変わった場合、承認は `stale_base` で失敗します。

実行予算のある Issue では、サイドバーに使用済み・残りの実行回数、80 % での警告、**実行予算を使い切りました** の状態を示すメーターが表示されます。**上限を上げる**と**追加する**は、ワークスペースのオーナーに追加実行の承認を依頼します。あなたがオーナーなら、その場でパスキーで承認できます。そうでなければ、依頼はオーナーに届きます。リストとボードでは、予算で停止した Issue のステータスの横に **予算を使い切りました** チップが表示されます。 オーナーが承認すると、決定済みカードと承認パネルに新しい上限と、停止していた Issue がどうなったか（実行がキューに入った、実行が開始した、ステータスが戻った、または再開しなかった理由）が表示され、再読み込みなしで更新されます。

ワークフローを削除するには、先に使用中のプロジェクトを別のワークフローに切り替えます。タスクは今のステータスのまま残ります。

**設定**に**ワークフロー**がない場合、このワークスペースではまだ利用できません。ステータスは引き続き**設定 → タスクステータス**で管理します。

## プロジェクトの新規依頼を保留する [#intake-hold]

ワークスペースは、一定の期間、新しいトップレベルの依頼を **Backlog** に留めておけます。エージェントが作業を始める前に、人が読んで解放するためです。ルールはワークスペース設定 `intake_hold` です。プロジェクトごとに 1 件のエントリを持つリストで、各エントリは `project_id`、`mode`、`starts_at`、`ends_at`、`exempt_types`、`exempt_labels`、`exempt_escalation_classes`、`exempt_autopilot_ids`、`exempt_issue_ids`、`source` を持ちます。エージェントはワークスペース設定のパッチで変更し、オーナーがパスキーで承認します。エントリのないプロジェクトは対象外です。 `source` は必須で、すべての ID はハイフン付きの小文字 UUID です。どちらかに反する値は保存時に拒否されます。

モードは `off`（何も保留しない）、`warn`、`block` です。次の条件がすべて成り立つ間、イシューは保留されます。エントリの期間が開いている（`starts_at` を含み、`ends_at` を含まない）。イシューが `starts_at` 以降に作成された。親がない。Backlog にある、または決定リクエストによって Backlog から保留状態に移された。人が解放していない。免除が当てはまらない。`block` モードでは、エージェントやトークンが保留中のイシューのステータスを変更する操作は、イシューが Backlog にあっても Backlog から保留状態に移されていても、HTTP 409 とコード `intake_hold` で拒否されます。レスポンス本文には `ends_at`、`fix`、`release_paths` が含まれます。`cancelled` への移動は拒否されません。プロジェクトでエージェントやトークンが `backlog` と `cancelled` 以外のステータスを指定して作成する操作も同様に拒否されます。ステータスを指定しない作成は Backlog に入り、新しいイシューにはメタデータキー `intake_hold` がエントリの `source` として設定されます。人による移動や作成は拒否されません。`warn` モードでは何も拒否せず、サーバーは `intake_hold_warn` のログを 1 行書きます。ステータス行への解放キーの記録は、このリリースには含まれません。

`GET /api/issues/{id}` は `intake_hold` フィールド（`source`、`held`、`owned`、`reason`、`ends_at`、`exempt_after`）を返します。`owned` は `ends_at` の後も true のままなので、保留の対象だったイシューと、対象外だったイシューを区別できます。親があるイシューと、エントリのないプロジェクトのイシューにはこのフィールドがありません。一覧エンドポイントは返しません。`reason` は `held`、`ended`、`not_started`、`mode_off`、`created_before_start`、`left_backlog`、`released_by_member`、`exempt_type`、`exempt_label`、`exempt_escalation_class`、`exempt_autopilot`、`exempt_issue_id` のいずれかです。`plain words` のようにタイトルに種別がないイシューは保留されます。優先度は何も免除しません。

エージェントが支出、デプロイ、公開、取り消せない操作、プロダクトの方向性について人の判断を必要とするときは、決定リクエストで尋ねます。エントリが `exempt_escalation_classes` にそのクラスを挙げていれば、人の回答は、回答から 10 分後にその 1 件のイシューの保留を解きます。それまで `held` は true のままで、`exempt_after` に免除が始まる時刻が入ります。撤回された回答は何も免除せず、`reversible` のリクエストも免除しません。 Issue が保留されている間も、リクエストの流れは変わりませんが、その回答やその他の判断イベント（取り下げ、期限切れ、再質問、撤回）の配信では実行が開始されません。配信は `skipped_ineligible` として確定し、再試行されません。`warn` モードでは、配信は通常どおり実行されます。 担当者待ちステップの待機エピソード（閉じて `skipped_ineligible` として確定し、再開の実行は行われません）、開いているアクションカードへの人のディスカッションメッセージ（コメントは保存され、ウェイクは `skipped_ineligible`）、実行済みアクションの人による取り消し（取り消しは保存され、実行は開始されません）も同様です。保留中のイシューを作成した実行は、その実行がまだ動いている間、そのイシューに対してもこのリクエストを開けます。イシューを作成していないエージェントは開けず、作成した実行からの `reversible` のリクエストは拒否されます。リクエストはそのイシューのコメントを引用するため、作成した実行は先にイシューへコメントを投稿しておく必要があります。

人がイシューを解放する方法は 2 つです。自分としてサインインした Web アプリ、デスクトップアプリ、CLI で Backlog から動かすか、Backlog から保留状態に移されたステータスから動かすかで、後者ではサーバーが解放を記録します。エージェントやクラウドランタイムのトークンは、イシューを解放しません。

## インテークまたは QA 証跡でステップを制限する [#intake-qa-gates]

ステップには入場ゲートを設定できます。ステップへのステータス移動が満たすべき条件です。2 つのゲートは、エージェントが課題に書いた内容を読みます。ステップの `entry` リストに `{"guard": "intake_simple", "mode": "warn", "param": "1"}` のように追加します。モードは `off`、`warn`、`block` です。リストにないゲートは無効で、すべて無効なら課題はこれまでどおり移動します。`warn` では移動は通り、課題に警告が 1 件付きます。`block` では原因となった事実と修正方法を示して拒否され、ゲートで `member_override` を `false` にしていない限り、人は理由を添えて通せます。

- `intake_simple` は、課題の説明またはコメントに `Estimate:`、`Repos:`、`Schema change:`、`Security change:`、`Human decision:` の行があり、回答が単純な課題を示すときに成立します。各行は最新のものが有効です。行がない、または読み取れない場合、見積もり（例: `1h`、`45m`）がゲートの `param`（時間単位、0 より大きく 24 以下）を超える場合、`Repos:` が複数のリポジトリを挙げる場合、はい/いいえの行が `yes` の場合、課題に未回答の意思決定リクエストがある間は失敗します。`param` は必須です。
- `qa_proof` は、移動を行うエージェントが、課題が現在のステップに入って以降に、リンク（`https://…`）を含む、またはフェンス付きコードブロックが続く `QA:` 行のあるコメントを書き、かつそのエージェント自身が課題の `post_close_work` メタデータを設定した（最新の書き込みである）ときに成立します。他のアクターや以前の実行が残した値は対象外です。`param` は取りません。他の人のコメントは対象外です。

どちらのゲートも安全側に倒れ、読み取れない値は失敗として扱います。どちらも遷移ガードとしては受け付けません。`intake_simple` を評価するたびに、課題のアクティビティに `intake_call` 行（`call` は `simple` または `rejected`、元の `estimate`、`step`）が記録されます。
