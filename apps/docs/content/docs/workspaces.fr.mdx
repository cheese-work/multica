Un espace de travail est la frontière de plus haut niveau de Multica. Les membres, les tâches, les projets, les agents, les skills et l'historique des exécutions appartiennent tous à un seul espace de travail, et rien ne circule d'un espace de travail à l'autre.

## Contenu d'un espace de travail

| Catégorie | Contenu |
|---|---|
| **Travail** | Tâches, projets, commentaires, pièces jointes, historique des exécutions |
| **Équipe** | Membres, rôles, invitations |
| **Agents** | Configuration des agents, skills, runtimes, automatisations |
| **Paramètres partagés** | Contexte, étiquettes, [propriétés personnalisées](/issues#propriétés-personnalisées), intégrations |

Le **Contexte** est fourni à chaque agent de l'espace de travail — c'est l'endroit où placer les informations générales sur l'équipe, les conventions produit et les exigences durables. Les exigences ponctuelles d'une exécution ont leur place dans la tâche correspondante.

## Créer un espace de travail

La création d'un espace de travail demande trois informations :

- **Nom de l'espace de travail** : affiché aux membres ; modifiable par la suite.
- **URL de l'espace de travail** : l'identifiant dans l'adresse — le `my-team` de `multica.ai/my-team`. Lettres minuscules, chiffres et tirets uniquement ; elle ne peut pas entrer en conflit avec un espace de travail existant ou une adresse réservée, et ne peut plus être modifiée après la création.
- **Préfixe des tâches** : prérempli à partir de l'URL de l'espace de travail et modifiable avant la création — avec le préfixe `MUL`, les numéros de tâches apparaissent sous la forme `MUL-1`, `MUL-2`, et la numérotation progresse indépendamment dans l'espace de travail. Lettres majuscules et chiffres, jusqu'à 10 caractères ; il peut être modifié plus tard dans les paramètres.

Le créateur devient automatiquement `owner`.

## Modifier les paramètres

`owner` et `admin` peuvent modifier le nom, le logo, la description, le contexte et le préfixe des tâches ; `member` peut seulement les consulter.

![Paramètres de l'espace de travail : nom, contexte, identifiant d'URL, préfixe des tâches et zone de danger](/images/docs/workspace-settings.webp)

<Callout type="warning">
Après un changement de préfixe des tâches, chaque tâche passe immédiatement au nouveau numéro (`MUL-5` devient `NEW-5`), mais les anciens numéros figurant dans les PR, les noms de branches et l'historique des discussions ne sont pas mis à jour.
</Callout>

### Fermeture automatique

Le paramètre d'espace de travail `auto_close` définit ce qui se passe quand une tâche enfant entre dans l'étape `agent_accepted` sans plus rien à faire. L'agent de l'étape ne ferait que la fermer ; le serveur peut donc emprunter lui-même l'arête `agent_done` de l'étape vers `done`.

| Valeur | Effet |
| --- | --- |
| `off` | Rien ne change. L'agent de l'étape s'exécute. |
| `warn` (par défaut) | L'agent de l'étape s'exécute comme avant. Chaque entrée enregistre aussi une ligne d'activité `auto_close_would_close` qui nomme les contrôles satisfaits et l'exécution qui a suivi. |
| `block` | Le serveur passe la tâche à `done`, enregistre une ligne d'activité `auto_closed` qui nomme les contrôles lus, et ne lance aucune exécution. |

Une fermeture exige tous les contrôles ci-dessous. Si l'un échoue ou ne peut pas être lu, l'agent de l'étape s'exécute comme avant.

- La tâche a un parent. Les tâches racines ne sont jamais fermées.
- Le dernier verdict de revue est un PASS sans constat P0 ni P1, et il porte sur le candidat actuel. Avec une PR, chaque PR liée est fusionnée au head que nomme le PASS. Sans PR, le candidat est le texte de la tâche : aucune pièce jointe, aucun changement de description, aucun commentaire (hors ceux du relecteur) n'est venu après le PASS, ni verdict CHANGES, marque périmée ou remplacée, ni retour à `in_progress`.
- Aucune tâche enfant ouverte, aucune demande de décision ouverte, et aucun réveil actif quand la tâche est entrée dans l'étape.
- La description n'a pas de ligne `Blockers: Cheese stop`, et la métadonnée `delivery_stop` du parent n'est pas `stopped`.
- La métadonnée de la tâche `post_close_work` vaut `none`. L'auteur l'écrit : `multica issue metadata set <issue> --key post_close_work --value none --type string`. Toute autre valeur, par exemple une courte description du travail restant, conserve l'exécution.
- Le workflow a une arête `agent_done` de `agent_accepted` vers `done`.

Définissez le mode avec `multica workspace update --auto-close-mode off|warn|block`. Une valeur illisible compte comme `off`.

### Garde des demandes

Le paramètre d'espace de travail `ask_guard_mode` définit ce qui se passe quand l'opération d'un agent demande à une personne d'agir sans ouvrir de demande de décision.

| Valeur | Effet |
| --- | --- |
| `off` (par défaut) | La garde ne fait rien. |
| `warn` | La garde enregistre un événement et une métrique. L'opération se poursuit. |
| `block` | La garde enregistre d'abord l'événement, puis refuse l'opération avec `422`. Seuls les événements `block` deviennent du travail de reprise. |

### Garde d'assignation d'autopilote

Le paramètre d'espace de travail `autopilot_assign_gate` définit ce qui se passe quand une issue qui nomme un autopilote (son id près du mot « autopilot ») est assignée à un agent ou une équipe alors que la personne pour qui le run agit ne peut pas écrire cet autopilote : ni son créateur, ni un admin de l'espace, ni un collaborateur autorisé.

| Valeur | Effet |
| --- | --- |
| `block` (défaut) | La création ou la mise à jour est refusée avec `403` et le code `autopilot_assign_no_write`. |
| `warn` | Le serveur journalise un avertissement. L'assignation a lieu. |
| `off` | La garde ne fait rien. |

Chaque événement garde le mode dans lequel il a été créé : passer de `warn` à `block` ne transforme pas les événements antérieurs en travail de reprise. Si l'événement ne peut pas être écrit, l'opération échoue avec `503` et un en-tête `Retry-After`, et rien n'est écrit.

Le paramètre d'espace de travail `reversible_ask_guard` (`off` par défaut, `warn`, `block`) couvre une demande de décision simple d'un agent dont la classe est `reversible` : l'agent demande à une personne d'approuver un travail que les agents peuvent déjà décider et faire eux-mêmes. `warn` l'enregistre dans les journaux. `block` la refuse avec `422`. Les demandes d'action, de proposition et de lot ne sont pas concernées. Remettez-le à `off` pour revenir en arrière ; aucune donnée ne change. Le même paramètre couvre une réponse simple d'un agent sous le commentaire d'un membre, sur une tâche en `blocked` ou `need_decision`, qui peut interroger cette personne sans demande de décision : `warn` l'enregistre et `block` la refuse avec `422`. Les commentaires de premier niveau, les réponses sous un agent, les commentaires qui mentionnent un agent ou une équipe, ceux avec `--notify-only` et les demandes de décision ne sont pas concernés.

Le paramètre d'espace de travail `owner_script_guard` (`off`, `warn`, `block` ; `warn` s'il n'est pas défini) couvre la demande de décision, la demande d'action et la carte `multica decision ask` d'un agent : le propriétaire ne lit pas de shell, donc une carte qui demande à la personne d'exécuter une commande est un défaut de la demande. Huit règles (R1 à R8, version 1 du jeu de règles) lisent le texte de la carte et ses étapes : un bloc de code shell, une commande dans un bloc ou dans du code en ligne, une commande de `human_steps`, une pièce jointe de script, et un mot d'exécution comme « run » ou « paste » à côté d'une commande ou juste après un message signalé. `warn` livre la carte et enregistre la détection. `block` la refuse avec `422`, nomme les règles et les champs touchés, et renvoie vers `multica config propose`, `multica decision propose <type>` ou une permission du bot. `off` ne vérifie rien. Chaque vérification écrit un événement, une ligne d'activité `owner_script_guard`, dans la même transaction que la carte, ou seule si la carte est refusée. L'événement contient les identifiants, le résultat, `delivered`, `rule_hits`, des empreintes à clé des commandes (`cmd_hmacs`) et `retry_of` ; il ne contient aucun texte de message. La chronologie de la tâche n'affiche pas ces lignes. Remettez `warn` ou `off` pour revenir en arrière ; aucune donnée ne change.

Le paramètre d'espace de travail `waiting_audience_guard` (`off` par défaut, `warn`, `block`) couvre un commentaire d'agent sur un ticket en `in_review`, `blocked` ou `need_decision`. Ce commentaire doit nommer son destinataire : une mention de membre, `notify_only`, un commentaire de décision, `ask` (le membre qui agit ensuite) ou `no_ask`. Une mention d'agent ou d'équipe, ou une réponse sous le commentaire d'un agent, compte aussi. Seuls ces champs typés et ces liens sont lus, jamais le texte du commentaire. `warn` enregistre un événement et publie le commentaire. `block` enregistre l'événement et refuse le commentaire avec `422`. Une exécution en canal de discussion ne fait qu'avertir. Remettez `off` pour revenir en arrière ; aucune donnée ne change.

Quand l'exécution qui a produit un événement `block` est terminée, le serveur envoie à la seule personne visée par la demande un avis de reprise automatique : un message de DM, un commentaire sur le ticket et un élément de boîte de réception, écrits dans une seule transaction. L'avis cite la demande enregistrée, renvoie au ticket et n'a ni options, ni recommandation, ni approbation : ce n'est jamais une demande de décision. Il n'est envoyé que si la source enregistrée contient le texte de la demande, désigne exactement un membre et que ce membre est toujours dans l'espace de travail ; sinon l'événement attend une réparation. Répondre dans le fil de commentaires de l'avis le marque `answered`. Un membre qui a quitté l'espace de travail ne peut plus le lire ni y répondre.

Un événement qui ne peut pas être envoyé comme avis va plutôt à l'agent dont l'exécution l'a produit : une exécution de reprise par racine de récupération, lancée par les garde-fous habituels (arrêts de projet, budget d'exécution, rôle et approbation). Le premier événement `block` est la racine, et un événement produit par une exécution de reprise en hérite : une reprise ne déclenche donc jamais une seconde reprise. Le message de l'exécution contient la commande exacte `multica decision request ... --recovers <event-id>` et aucun texte source. Une exécution refusée, un agent indisponible, une reprise qui se termine sans demande correspondante ou une nouvelle demande produite par la reprise font échouer la racine. L'agent en est le responsable : un commentaire système sur le ticket nomme l'agent sans mentionner de membre, et `multica decision brief` liste l'échec avec un extrait de la demande. Les exécutions d'une voie de discussion ne produisent que des événements `warn` et ne sont donc jamais reprises.

Le garde couvre aussi un agent qui enregistre un réveil qu'une personne peut déclencher. Liez-le avec `--decision`, marquez-le `--purpose observe` ou limitez-le aux agents ; voir [Réveils](/cli#wakeups).

### Écritures gouvernées déléguées

Le paramètre d'espace de travail `delegated_governed_writes` décide quels agents peuvent écrire dans les champs gouvernés, et si chaque écriture exige encore la décision d'une personne. Il se trouve dans les paramètres de l'espace de travail, sous **Écritures gouvernées déléguées**.

- **Qui peut modifier :** `owner` et `admin`. Un `member` voit le même tableau en lecture seule, avec une note de verrouillage et sans bouton Modifier.
- **Agents autorisés :** les agents qui peuvent écrire. Un agent archivé ne peut pas être ajouté.
- **Champs autorisés :** parmi `workflow.steps`, `workflow.instructions`, `workspace.context`, `squad.instructions`, `agent.instructions`, `project.description`, `workflow.budget`, `issue.workflow`. Les champs non cochés restent en lecture seule pour tous les agents.
- **Décision humaine requise :** activée par défaut. Un agent autorisé ouvre alors une demande de décision au lieu d'écrire. Si vous la désactivez, les agents autorisés écrivent directement ; l'enregistrement demande donc d'abord une confirmation.

Les modifications non enregistrées sont conservées si l'enregistrement échoue : rien de ce que vous avez saisi n'est perdu.

## Changer d'espace de travail et le quitter

Un même compte peut rejoindre plusieurs espaces de travail. Changer d'espace de travail change seulement ce que vous consultez ; les données ne bougent pas.

Après avoir quitté un espace de travail, il vous faut une nouvelle invitation pour y revenir. Quitter un espace de travail désactive aussi les runtimes dont vous êtes propriétaire, archive les agents qui y sont liés et annule leurs exécutions non terminées.

Le dernier `owner` ne peut pas quitter l'espace de travail ; promouvez d'abord un autre membre au rôle `owner`.

## Supprimer un espace de travail

Seul un `owner` peut supprimer un espace de travail. La suppression retire définitivement tout son travail, ses membres, la configuration de ses agents et l'historique de ses exécutions, et elle est irréversible. Si vous vous absentez seulement pour un temps, il suffit de quitter l'espace de travail.
