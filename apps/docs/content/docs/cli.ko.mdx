Multica CLI는 로컬 런타임을 연결할 뿐 아니라 터미널에서 워크스페이스, 태스크, 에이전트, 자동화를 관리할 수 있습니다. 이 페이지에서는 자주 사용하는 경로를 설명합니다. 현재 버전에서 지원하는 인수는 항상 명령 자체의 `--help`를 기준으로 확인하세요.

## 설치

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
```

Homebrew가 설치되어 있다면 다음 명령도 사용할 수 있습니다.

```bash
brew install multica-ai/tap/multica
```

</Tab>
<Tab value="Windows">

PowerShell에서 실행합니다.

```powershell
irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex
```

</Tab>
</Tabs>

설치 성공 여부를 확인합니다.

```bash
multica version
```

## 처음 연결

연결할 서비스를 선택합니다.

<Tabs items={["Multica Cloud", "자체 호스팅 인스턴스"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="자체 호스팅 인스턴스">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup`은 서비스 주소를 저장하고 브라우저를 열어 로그인을 완료한 뒤 데몬을 시작합니다. 완료 후 다음을 확인하세요.

```bash
multica auth status
multica daemon status
```

다른 설정을 덮어쓰지 않고 로그인만 다시 하려면 `multica login`을 실행합니다. 브라우저가 없는 환경에서는 Web 설정에서 개인 액세스 토큰을 먼저 만든 뒤 다음을 입력합니다.

```bash
multica login --token
```

명령이 터미널에서 token 붙여넣기를 요청하므로 전체 값이 shell history에 남지 않습니다.

## 워크스페이스 선택

기본 워크스페이스를 나열하고 전환합니다.

```bash
multica workspace list
multica workspace switch <slug>
```

이후 명령은 이 워크스페이스를 사용합니다. 한 번의 명령에서 `--workspace-id`로 임시 덮어쓸 수 있고 `MULTICA_WORKSPACE_ID`를 설정할 수도 있습니다.

멤버 초대:

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## 자주 사용하는 태스크 작업

```bash
# 확인 및 검색
multica issue list
multica issue get MUL-123
multica issue search "로그인 실패"

# 생성 및 수정
multica issue create --title "로그인 실패 수정"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# 댓글 및 실행 기록
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "회귀 테스트를 먼저 확인해 주세요"
multica issue comment update <comment-id> --expected-revision 2 --content "회귀 테스트와 릴리스 노트를 확인해 주세요"
multica issue runs MUL-123
```

긴 설명이나 댓글은 stdin에서 읽어 줄바꿈과 따옴표 처리를 피할 수 있습니다.

```bash
multica issue create --title "업그레이드 안내" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

특정 실행의 메시지를 확인하거나 실행을 중지 또는 재시도합니다.

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123 --fresh
```

후속 실행을 대기열에 넣는 대신 아직 진행 중인 실행에 댓글을 추가합니다(추가 메시지를 받을 수 있는 실행만 해당하며, 댓글로 시작할 수 있는 에이전트에만 가능합니다).

```bash
multica issue comment add MUL-123 --content-file note.md --steer <task-id>
multica issue comment add MUL-123 --content-file note.md --steer-active
```

에이전트 작업에서 멤버를 멘션(`[@이름](mention://member/<id>)`)하는 댓글은 결정 요청, `--decision-intent`·`--decision-record`·`--decision-veto` 댓글, 또는 `--notify-only` 댓글일 때만 허용됩니다. 답이 필요 없는 알림에는 `--notify-only`를 사용합니다. 대기를 시작하지 않으며 결정 요청으로도 계산되지 않습니다. 결정 관련 플래그와 함께 쓸 수 없습니다. 검사는 문구가 아니라 멘션 링크를 읽으며, 코드 안의 링크도 포함됩니다. 워크스페이스 설정 `ask_guard_mode`(`off`, `warn`, `block`)가 거부될 댓글을 기록만 할지 422를 반환할지 정합니다. 채팅 작업과 작업이 없는 호출은 기록만 합니다. 멤버 멘션을 추가하는 수정에도 같은 규칙이 적용됩니다.

```bash
multica issue comment add MUL-123 --content-file fyi.md --notify-only
```

`multica decision request`의 `--recovers <event-id>`는 요청이 ask 가드 이벤트(거부된 작업이나 복구 알림에 표시된 이벤트)에 대한 응답임을 나타냅니다. 서버는 이벤트가 이 이슈에 있고 요청이 묻는 사람을 위해 발생한 경우에만, 요청과 같은 트랜잭션에서 그 이벤트를 해제합니다. 한 사람에 대한 요청은 다른 사람의 이벤트를 해제하지 않으며, `--recovers`가 없는 요청은 아무것도 해제하지 않습니다. 다른 이슈나 다른 사람의 이벤트는 `400`으로 거부됩니다.하나의 요청은 이벤트 하나만 복구합니다. 같은 요청을 재시도하면서 두 번째 이벤트를 지정하면 `400`으로 거부됩니다.

같은 프로젝트, 같은 상위 태스크 아래에 제목이 같은(대소문자와 여분의 공백은 구분하지 않음) 닫히지 않은 태스크가 이미 있으면 `issue create`는 생성을 거부하고 그 태스크를 알려 줍니다. 그래도 만들려면 `--allow-duplicate`를 붙이세요. 한 태스크를 다른 태스크의 중복으로 표시하려면 `multica issue status MUL-124 cancelled --duplicate-of MUL-123`을 실행합니다.

여러 PR을 순서대로 만드는 태스크는 `issue create --title "..." --pr-auto-complete off` 또는 `issue update <id> --pr-auto-complete off`로 병합 후에도 상태를 유지할 수 있습니다. `--pr-auto-complete on`으로 워크스페이스 규칙을 복원하면 다음 PR 이벤트부터 적용됩니다. `issue pull-requests <id>`는 연결된 PR이 없어도 태스크 설정, 워크스페이스 설정, 대상 상태와 판단 결과를 표시합니다. 지원 서버는 생성 트랜잭션 안에서 설정을 저장하고, 이전 서버에는 추가 PUT을 보냅니다. 실패하면 생성된 태스크 ID와 재시도할 update 명령이 표시되므로 create를 반복하지 마세요.

### 이슈 라우팅

`issue route`는 이슈의 상태를 바꾸고 그 이유를 한 번의 호출로 기록합니다. 라우팅 단계가 이슈를 다음에 어디로 보낼지 정할 때 사용합니다. `--status`, `--reason`(1~500자), `--confidence`(0~1)는 필수입니다.

```bash
multica issue route MUL-123 --status in_review --reason "테스트 통과, 리뷰 필요" --confidence 0.8
multica issue route MUL-123 --status in_progress --owner "Backend Agent" --reason "백엔드 수정 필요" --confidence 0.6
multica issue route MUL-123 --status in_review --owner-id <agent-id> --no-start --reason "리뷰어가 나중에 가져감" --confidence 0.9
```

`--owner`가 없으면 `issue status`와 같이 프로젝트 워크플로가 담당자를 정합니다. 명시적인 `--owner`(멤버, 에이전트 또는 스쿼드. `--owner-id`는 이름 대신 UUID를 받습니다)는 워크플로의 담당자를 대체합니다. 현재 상태는 유지하고 담당자만 바꾸는 라우트는 허용됩니다. 상태와 담당자가 모두 같은 라우트는 HTTP 409로 거부되며 아무것도 기록하지 않습니다. `--no-start`는 `issue update`와 같이 에이전트 실행을 시작하지 않습니다. `--expected-revision`을 지정하면 그 사이에 이슈가 바뀐 경우 라우트를 거부합니다.

### 타임라인

`issue get`은 태스크의 현재 상태를 보여 줍니다. `issue timeline`은 상태, 우선순위, 담당자, 제목, 날짜 변경과 실행 결과를 시간순으로 나열하고 댓글도 섞어 보여 줍니다. "언제 in_review로 바뀌었나", "지금 상태에 얼마나 머물러 있나"를 확인할 때 씁니다.

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only`는 댓글을 빼고 모든 활동 기록을 남깁니다. `--action`은 지정한 동작만 반환하며 반복해서 쓸 수 있고 `--activity-only`를 포함합니다. 서버가 읽는 기록에는 한도가 있어 잘린 경우 stderr에 경고가 출력됩니다. 이때는 그 결과로 머문 시간을 추정하지 마세요.

```bash
multica issue description history MUL-123
multica issue description diff MUL-123 --from 30 --to 35
```

`issue description history`는 이슈 설명의 기록된 리비전을 오래된 순으로 리비전 번호, 시각(ICT), 실행자와 함께 나열합니다. `issue description diff`는 그중 두 리비전 사이의 unified diff를 출력합니다. 리비전 번호는 이슈 자체의 리비전 카운터입니다. 기록 기능이 도입된 이후에 기록된 리비전만 존재하며, 각 이슈의 첫 항목은 그 시점의 설명을 기준으로 저장한 것입니다. 설명을 바꾸지 않은 리비전은 그 이전의 가장 최근 텍스트로 처리됩니다. 존재하지 않는 리비전은 404를 반환합니다. 둘 다 `--output json`을 지원합니다.

### 긴 댓글 스레드 읽기

댓글이 많은 태스크를 하나씩 읽으면 에이전트가 토큰을 많이 씁니다. 먼저 스레드를 훑어보고 필요한 스레드만 펼치세요.

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only`는 최상위 댓글만 반환하며 각 댓글에 답글 수와 마지막 활동 시각이 붙습니다.
- `--summary`는 각 댓글을 짧은 미리보기로 자릅니다.
- `--compact`는 JSON 출력에만 적용되며 정보가 없는 필드(반복되는 `issue_id`, 빈 배열 등)를 뺍니다.
- `--recent N`은 최근 활동이 있었던 스레드 N개를 모든 답글과 함께 반환하므로 답글이 많으면 출력이 길어집니다.
- 해결된 스레드는 기본적으로 첫 댓글과 결론으로 접힙니다. 전체 내용이 필요하면 `--full`을 붙이세요.

목록도 필요한 필드만 받을 수 있습니다: `multica issue list --output json --fields id,identifier,title,status`. 필터링은 CLI에서 이루어지므로 줄어드는 것은 출력과 컨텍스트이고 요청량은 그대로입니다.

마지막 업데이트 시각으로 태스크를 필터링하려면 RFC3339 타임스탬프로 `--updated-since`와 `--updated-until`을 함께 지정하세요. 서버는 현재 `updated_at`이 `since` 이상, `until` 미만인 태스크를 반환합니다: `[since, until)`. 기존 필터, 정렬, 페이지네이션과 함께 사용할 수 있습니다. 페이지를 넘길 때 같은 범위를 유지하세요. 페이지네이션은 스냅샷을 제공하지 않으므로 동시에 업데이트가 발생하면 결과가 달라질 수 있습니다.

```bash
multica issue list --updated-since 2026-11-05T10:00:00Z \
  --updated-until 2026-11-05T10:01:00Z \
  --sort created_at --direction asc --limit 100 --offset 0 \
  --output json --fields id,workspace_id,project_id,title
```

### 깨우기

깨우기는 이벤트가 생기거나 조건이 충족되거나 지정한 시각이 되면 에이전트의 일반 실행을 시작합니다. 전체 규칙은 [태스크 깨우기](/issue-wakeups)를 참고하세요.

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "답장이 오면 그 내용으로 견적서를 업데이트"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "공급업체가 회신했는지 확인"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

터미널에서 멤버로 만들 때는 `--agent-id`가 필요합니다. 에이전트가 자기 실행 안에서 만들면 기본적으로 자기 자신을 깨웁니다.

사람이 트리거할 수 있는 규칙은 댓글, 이슈, 반응, 첨부 변경에 대한 이벤트 규칙 중 행위자 필터가 멤버를 제외하지 않는 것입니다. 워크스페이스 설정 `ask_guard_mode`가 `warn` 또는 `block`이면, 에이전트는 다음 중 하나가 없는 한 이런 규칙을 스스로 등록할 수 없습니다.

- `--decision <request-id>`는 규칙을 이 이슈의 결정 요청에 묶습니다. 요청은 질문됨 또는 응답됨 상태여야 하고, `--filter-actor-id`를 지정했다면 그 멤버의 요청이어야 합니다. 요청 하나는 활성 웨이크업 하나에만 묶입니다.
- `--purpose observe`는 사람을 기다리지 않는 규칙을 나타냅니다. 멤버가 일으킨 실행마다 감사 이벤트가 기록됩니다.
- `--filter-actor-id` 없는 `--filter-actor-type agent`는 모든 에이전트와 일치하고 멤버와는 일치하지 않습니다.

`block` 모드에서는 수정 명령이 담긴 메시지와 함께 422로 거부됩니다. `warn` 모드에서는 규칙이 만들어지고 이벤트만 기록됩니다.

### 웨이크업 규칙

워크스페이스 및 프로젝트 웨이크업 규칙([이슈 웨이크업](/issue-wakeups) 참고)에는 전용 명령이 있으며, `create`와 `get` 외에 다음을 쓸 수 있습니다.

```bash
multica wakeup-definition list [--project <project>] [--output json|table]
multica wakeup-definition preview [--project <project>] [--rule <rule>] [--output json|table] --config-file rule.json
multica wakeup-definition update <rule> [--project <project>] --revision <n> --config-file rule.json
multica wakeup-definition delete <rule> [--project <project>] --revision <n>
```

`--revision`은 `list`가 보여 주는 리비전입니다. `update`에 `--revision 0`을 주면 오버라이드를 만듭니다. `preview`는 아무것도 저장하지 않고 최종 적용된 규칙을 출력합니다. 조건 규칙에서는 `already_satisfied`가 즉시 일치할 이슈 수를 알려 주고 `issues`가 그 이슈를 나열합니다(`--output table`은 목록으로 출력). 미리보기는 범위의 처음 200개 이슈를 살펴 그중 열려 있고 백로그가 아닌 이슈를 평가합니다. 범위에 그보다 많으면 `truncated`가 `true`이며 더 많은 이슈가 일치할 수 있습니다. 이벤트 규칙은 조건이 없으므로 미리보기에 `already_satisfied`가 없고 기존 이슈와 일치하지 않습니다. 규칙 편집과 삭제는 소유자나 관리자만 할 수 있습니다. 미리보기는 사람 멤버라면 누구나 할 수 있고, 에이전트 등 머신 자격 증명은 `403`을 받으며, 에이전트가 만든 규칙은 사람이 활성화할 때까지 비활성 상태로 남습니다.

### DM에서 진행 상황 팔로우

DM은 에이전트가 사용자를 위해 만든 이슈를 팔로우합니다. 멤버는 자신이 만든 DM에서만 `--chat`으로 팔로우를 관리할 수 있습니다. 에이전트는 `--chat` 없이 `multica issue follow <issue>`를 실행합니다. DM은 자신의 작업에서 정해지며, DM이 없는 작업은 거부됩니다. 하위 이슈는 부모의 활성 팔로우를 상속합니다.

```bash
multica issue follow MUL-123 --chat <chat-session-id>
multica issue mute-follow MUL-123 --chat <chat-session-id>
multica issue unmute-follow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id>
multica issue unfollow MUL-123 --chat <chat-session-id> --scope root
multica issue follows --chat <chat-session-id>
```

`unfollow`는 해당 이슈의 팔로우를 종료합니다. `--scope root`를 함께 쓰면 하위 이슈가 그 이슈에서 상속한 팔로우도 종료합니다. 직접 수동으로 팔로우한 하위 이슈는 계속 팔로우됩니다. 팔로우를 해제한 하위 이슈는 이후 하위 이슈가 생성되어도 다시 팔로우되지 않습니다.

## 에이전트와 스킬

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

가져올 때 같은 이름의 스킬이 있으면 기본적으로 중지하고 기존 내용을 수정하지 않습니다. 의도에 맞는 방식을 선택하세요.

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite`는 스킬 생성자만 사용할 수 있으며 기존 ID와 에이전트 연결을 유지합니다.

환경 변수와 MCP 설정에는 토큰이 들어 있는 경우가 많습니다. 명령줄에 값을 직접 쓰면 셸 기록과 `ps` 출력에 남으므로 `-file` 또는 `-stdin` 형태로 전달하세요.

```bash
multica agent create --name "운영 도우미" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- `--custom-env` 계열 플래그는 `agent create`에만 있습니다. 나중에 바꿀 때는 `agent env set`을 쓰며, 전체를 교체하고 값이 `****`인 키는 기존 값을 유지합니다.
- `agent update --mcp-config null`은 MCP 설정을 지웁니다.
- `--custom-args`는 JSON 배열이며 실행 인수의 맨 끝에 붙습니다. 모델은 `--model`로 고르세요. 사용자 지정 인수 안의 `--model`을 거부하는 도구도 있습니다.
- 에이전트를 호출할 수 있는 사람은 `--permission-mode`로 정합니다. `private`은 소유자만, `public_to`는 `--public-to-workspace` 또는 `--public-to-member <user-id>`와 함께 씁니다. `--visibility private|workspace`는 예전 방식이며 `--permission-mode`로 변환됩니다. 둘 다 지정하면 `--permission-mode`가 우선합니다.

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

```bash
multica daemon autostart enable
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "사내 Claude 래퍼" \

```

`daemon autostart`는 현재 profile이 로그인할 때 시작되도록 등록합니다. 플랫폼별 차이는 [로그인 시 자동 시작](/daemon-runtimes#autostart)을 참고하세요. `runtime usage`는 기본적으로 90일을 집계하며 `--days`는 최대 365입니다. `runtime update`는 해당 컴퓨터의 데몬이 CLI를 지정한 버전으로 업데이트하게 하고, `--wait`를 붙이면 업데이트가 끝날 때까지 기다립니다. `runtime profile create`는 호환 도구를 `--runtime-type`으로 지정합니다(예전 `--protocol-family`도 쓸 수 있음). 고정 인수는 현재 웹 앱에서만 설정할 수 있습니다.

활성 에이전트가 계속 연결된 런타임을 삭제하면 명령이 기본적으로 거부됩니다. `multica runtime delete <id> --cascade`는 에이전트의 런타임 연결을 해제하고 설정과 기록을 보존하며 활성 실행을 취소합니다.

`multica runtime breaker list`는 프로바이더별 서킷 브레이커를 보여 주고, `multica runtime breaker reset <provider>`는 강제로 닫습니다(소유자 또는 관리자만). [프로바이더 서킷 브레이커](/daemon-runtimes#provider-breaker)를 참고하세요.

실행 메커니즘과 사용자 지정 profile은 [데몬과 런타임](/daemon-runtimes)을 참고하세요.

## 프로젝트, 워크스페이스, 오토파일럿

```bash
multica project create --title "여름 캠페인" --lead "리레이" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "운영팀" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "주간 매출 보고" --agent "운영 도우미" \
  --mode create_issue --issue-title-template "매출 보고 {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Asia/Seoul
```

- `--lead`에는 멤버나 에이전트의 이름을 씁니다. `--default-branch-hint`는 저장소의 기본 브랜치를 에이전트에게 알려 줄 뿐 브랜치를 바꾸지는 않습니다.
- 워크스페이스의 `--context`는 워크스페이스의 모든 에이전트에게 제공됩니다. `--slug`는 만든 뒤 바꿀 수 없습니다. `--issue-prefix`는 대문자로 바뀌며, 변경하면 기존 태스크 번호가 모두 다시 매겨져 외부에서 참조하던 예전 번호는 더 이상 연결되지 않습니다.
- `multica workspace update --routing-agent <agent-id> [--routing-fallback-agent <agent-id>]`는 라우팅만 하는 워크플로 단계(기본값 `todo`, `blocked`, `merged`, `need_decision`; `--routing-statuses`로 변경하고, `--routing-overrides todo=<agent-id>`로 특정 상태를 다른 에이전트에 보냅니다)를 맡을 에이전트를 지정합니다. 이 에이전트가 보관 처리되거나 실행이 공급자 오류로 실패하면 대체 에이전트가 이어받습니다. 재정의 키를 `<workflow-id>:<status>`로 쓰면 해당 재정의는 한 워크플로로 한정됩니다. `none`은 해당 항목을 끕니다. 사람 소유자나 관리자만 변경할 수 있으며, 모든 변경은 활동 로그에 기록됩니다. 설정은 `background_agents`의 `routing` 작업으로 저장됩니다. 이 플래그는 `multica workspace background-agents set routing`의 별칭이며, 기존 `/routing-agent` API 경로도 한 릴리스 동안 별칭으로 남습니다.
- `--issue-title-template`은 `{{date}}`(UTC, `YYYY-MM-DD`)만 치환하며 다른 `{{...}}`는 거부합니다. 일정 트리거의 `--timezone` 기본값은 UTC입니다.
- `--mode script --script <name> [--arg <value>]...`은 모델 세션 없이 에이전트의 작업 토큰으로 허용 목록의 스크립트 하나를 실행합니다. `--script`와 `--arg`에는 `--mode script`가 필요하고, `--mode script`에는 `--script`가 필요합니다. `--description`은 실행되지 않습니다. 데몬에 허용 목록이 없으면 모든 스크립트 작업이 안전하게 실패합니다. `--output json`은 스크립트 이름과 인자를 `script_config`로 보여 줍니다. `autopilot update --mode <다른 모드>`는 스크립트를 지웁니다. 작업이 끝나면 서버는 최선을 다해 작업 토큰을 삭제합니다. 삭제에 실패하면 토큰은 만료될 때까지 유효하며, 더 일찍 폐기하는 수단은 없습니다. 실행 결과의 `script` 아래에 스크립트 이름, 인수 목록의 SHA-256, 종료 코드, 소요 시간이 기록되고, 삭제에 실패하면 `token_revoke_failed`가 설정됩니다.

### 설정 변경 제안

`multica config propose` 는 워크스페이스 설정 변경용 액션 파일을 만듭니다. 현재 값을 읽고, 서버가 다시 계산하는 것과 같은 방식으로 `before_sha256` 과 `after_sha256` 을 계산해서 `multica decision request --action-file` 이 받는 파일을 씁니다. 아무것도 전송하지 않으며 시크릿도 쓰지 않습니다. 승인은 여전히 사람이 패스키로 합니다.

필드: `agent.instructions <agent-id>`, `squad.instructions <squad-id>`, `workspace.context`, `workflow.steps <workflow-id>`, `workflow.step.instructions <workflow-id> --status-key <key>`, `workflow.budget <workflow-id>`, `workspace.settings --set key=value|key:=<json>`. 텍스트 필드는 `--file`(UTF-8, NUL 바이트 없음)을 받습니다. `workflow.steps` 는 워크플로 GET 이 돌려주는 steps 배열을 받습니다. 이 출력을 편집하세요. 서버가 steps 를 다르게 정규화하면 요청이 거부됩니다(`after_digest_mismatch`). `workflow.step.instructions` 는 서버가 after 다이제스트를 계산하므로 파일에 `after_sha256` 이 없고, 출력되는 다이제스트는 비교용입니다. `--out <path>` 는 파일을 쓰고, `--dry-run` 은 아무것도 쓰지 않고 두 다이제스트와 액션을 출력합니다. `--expires-in <초>` 로 만료를 지정합니다.

`workflow.budget <workflow-id>` 는 `--file` 대신 `--max-runs <n>`(1~1000, 0 이면 상한 해제)과 `--include-child-prs=<true|false>` 를 받습니다. 하나 이상 지정해야 하며, 생략한 필드는 저장된 값을 유지합니다. 에이전트는 이 두 필드를 워크플로에 직접 쓸 수 없습니다(`budget_requires_decision`). 변경을 제안하고 결정을 요청하면, 워크플로가 CLI 가 읽은 다이제스트와 여전히 같을 때 승인 시 서버가 적용합니다.

작업 토큰을 가진 에이전트는 한 번의 호출로 카드를 엽니다. `multica workflow update <workflow-id> --max-runs-per-issue 40 --issue <issue> --for <user-id>` 는 현재 워크플로를 읽고, 지정한 예산 플래그만으로 `workflow.budget.set` 을 제안하며, 카드 URL 을 출력합니다. 소유자가 승인하기 전에는 아무것도 쓰지 않습니다. 같은 호출을 반복하면 같은 카드가 돌아옵니다. 예산 호출에는 `--name`, `--description`, `--steps-file`, `--start-status`, `--map`, `--dry-run` 을 함께 쓸 수 없습니다. 명령이 요청 전에 거부하므로 두 개의 명령으로 나누어 실행하세요. `--print-hash` 는 예산 변경의 `before_sha256` 와 `after_sha256` 를 출력합니다. `multica config propose workflow.budget` 에서는 같은 플래그를 `--max-runs` 라고 부릅니다. 워크플로 예산이 더 넓어지면 `multica issue update <issue> --workflow <workflow-id>` 와 `multica issue create --workflow <workflow-id>` 도 같은 `--print-hash` 와 `--decision-id`(필드 `issue.workflow`)를 받습니다. 두 명령은 하나의 규칙을 따르며, 소유자의 대화형 세션에는 결정이 필요 없습니다. 에이전트 실행에서 더 큰 예산이 되는 `multica issue update <id> --workflow <workflow-id>`는 결정이 필요 없습니다. 워크스페이스 소유자를 위한 승인 카드를 열고 그 액션 ID와 URL을 출력하며, 소유자가 패스키로 승인할 때까지 이슈는 변경되지 않습니다. 카드를 연 뒤 이슈의 워크플로, 프로젝트의 워크플로 또는 예산이 바뀌면 승인은 `stale_base`로 실패합니다.

그 밖의 필드는 아무것도 읽기 전에 `denylisted` 로 거부됩니다: `project.description`, 패스키와 결정 게이트, 멤버와 역할, 소유자 이전, 인증·연동 시크릿, 워크스페이스 삭제, 액션 레지스트리, `delegated_governed_writes`. 서버 허용 표에 없는 설정 키도 같은 방식으로 거부되며, 허용 키와 거부 키가 섞인 패치는 전체가 거부됩니다. 서버는 요청 시점과 승인 시점에 다시 확인합니다.

```bash
multica config propose workspace.context --file ./context.md --out ./action.json
multica config propose agent.instructions <agent-id> --file ./instructions.md --dry-run
multica config propose workflow.step.instructions <workflow-id> --status-key review --file ./step.md --out ./action.json
multica config propose workflow.budget <workflow-id> --max-runs 40 --include-child-prs=false --out ./action.json
multica config propose workspace.settings --set compact_prompt="..." --set wakeups_paused:=false --out ./action.json
multica decision request --issue MUL-123 --for <user-id> --class reversible --ask-file ./ask.md --action-file ./action.json
```

## 명령 개요

| 명령 | 용도 |
| --- | --- |
| `issue` | 태스크 생성, 업데이트, 할당, 검색. 댓글, 구독, 라벨, 속성, 깨우기, 타임라인, 실행 기록 관리 |
| `project` | 프로젝트와 프로젝트 리소스 관리 |
| `label`, `property` | 워크스페이스 라벨과 사용자 지정 속성 관리 |
| `view` | 저장된 뷰를 읽고 뷰에 보이는 태스크 나열 |
| `agent`, `skill`, `squad` | 에이전트, 스킬, 스쿼드 관리 |
| `autopilot` | 자동화, 트리거, 실행 기록 관리 |
| `workspace` | 워크스페이스 생성, 확인, 전환 및 멤버 초대 |
| `repo` | 워크스페이스 저장소 관리 및 로컬 checkout |
| `daemon`, `runtime` | 로컬 데몬 시작 및 중지, 런타임 확인 및 관리 |
| `attachment` | 첨부 파일 업로드 또는 다운로드 |
| `user profile` | 현재 사용자 profile 확인 또는 업데이트 |

| `guard` | 에이전트의 도구 호출을 워크스페이스 정책에 따라 검사 |

`multica chat`은 **에이전트가 현재 처리 중인 외부 채팅 대화**를 읽으며 주로 채팅 연동의 에이전트가 사용합니다. 워크스페이스의 임의 대화를 탐색하는 일반 명령이 아닙니다.

### 섀도 리포트

워크스페이스 멤버는 누구나 System 1 섀도 리포트를 읽을 수 있습니다:

```bash
multica decision shadow-report [--since <RFC 3339>] [--until <RFC 3339>] --output json
```

`decision` 블록과 `routing` 블록은 전체 기간을 다룹니다. `route` 블록은 `[since, until)` 구간을 다룹니다. `--since`와 `--until`은 RFC 3339 시각을 받고, `--until`의 기본값은 현재, `--since`의 기본값은 `--until` 24시간 전입니다. 잘못된 시각이나 `--until`보다 늦은 `--since`는 서버가 400으로 거부합니다.

`route` 블록은 하나의 이벤트 집합을 셉니다. 라우팅 단계를 떠난 것으로 표시된 에이전트의 상태 변경(`eligible_exits`)과, 같은 이벤트 ID를 가진 route 라벨(`matched_labels`)입니다. `label_coverage`는 `matched_labels / eligible_exits`이며 1을 넘지 않습니다. `via_route_share`는 첫 라벨이 상태 폴백이 아니라 `issue route`에서 온, 일치한 이벤트의 비율입니다. `duplicate_labels`는 더 이른 라벨과 이벤트를 공유하는 라벨의 수입니다(목표 0). `labels_total`, `owner_only_labels`(상태를 유지한 route라 이벤트 없음), `non_routing_labels`(라우팅 에이전트가 없는 단계에서의 route)는 커버리지에 포함되지 않습니다. `overridden`은 1시간 안에 사람이 되돌린 에이전트 라벨 수이고, `override_rate`는 `overridden / labels_total`입니다. 블록에는 클래스별 `decided`, `predicted`, `agreed`, `coverage`, `precision`도 들어 있습니다.

### System 1 라벨링

지정된 System 1 라벨러 에이전트는 자신의 에이전트 작업 안에서 블라인드 큐를 읽고 라벨을 기록합니다. 서버는 작업 토큰에서 에이전트와 작업을 가져오며, 멤버 세션이나 PAT는 403을 받습니다.

```bash
multica system1 label-queue --scope <scope> --kind burn_in|eval --output json
multica system1 label submit --observation <observation-id> --kind burn_in|eval --label <value> [--supersedes <label-id>] --output json
```

큐에는 관찰 ID와 타입이 지정된 특성만 들어 있고 예측은 절대 들어 있지 않습니다. 이 범위에서 같은 종류의 유효한 라벨이 아직 없는 관찰을 최대 20개 담습니다. 서버는 큐를 제공할 때 샘플링한 ID와 시드를 저장하며, 같은 작업이 다시 요청하면 같은 샘플을 받습니다. `--supersedes`에는 정정할 유효한 라벨의 ID를 넣습니다. 없이 같은 관찰에 두 번째 라벨을 쓰면 409가 됩니다.

워크스페이스 멤버는 누구나 스코프와 예측기 버전별 System 1 자격 상태를 읽을 수 있습니다:

```bash
multica system1 report [--scope <scope>] --output json
```

`--scope`는 `test_first_waiver` 또는 `ci:<repo>:<protocol>`입니다. 각 행은 예측기 버전 하나의 최신 에포크를 다룹니다. 에포크 시작 이후에 만들어진 관측만 세고, 새 예측기 버전은 자체 에포크를 엽니다. 케이스는 기준 라벨(교체되지 않은 가장 최근 라벨)이 있는 예측 하나입니다. `denominator`는 기권이 아닌 예측과 매핑된 라벨이 있는 케이스, `agreed`는 둘이 일치한 케이스, `abstained`는 예측기가 기권한 라벨 케이스, `unmapped`는 자유 텍스트 답변 수입니다. `status`는 7일 이상, `denominator` 20 이상, 일치율 90% 이상이면 `qualified`입니다. 4주 뒤에도 센 케이스가 20 미만이면 `insufficient_data`, 강등된 에포크는 `demoted`, 그 외는 `collecting`입니다.

## ID와 출력 형식

태스크에는 `MUL-123` 같은 key 또는 전체 UUID를 사용하며 UUID 짧은 접두사는 허용하지 않습니다.

다른 리소스의 `list` 명령은 일반적으로 복사 가능한 짧은 ID를 표시하고 `--full-id`로 전체 UUID를 출력할 수 있습니다. 짧은 ID가 고유하지 않으면 CLI가 더 많은 글자를 입력하거나 전체 UUID를 사용하도록 요청합니다. 실행의 짧은 ID에는 `--issue`로 소속 태스크도 지정해야 합니다.

많은 명령이 구조화 출력을 지원합니다.

```bash
multica issue list --output json
multica agent list --output json
```

스크립트에서는 터미널용 표를 parsing하지 말고 JSON 출력을 사용하세요. 각 명령이 지원하는 출력 형식과 pagination 인수는 `multica <command> --help`를 기준으로 확인합니다.

## Profile과 설정

기본 설정은 `~/.multica/config.json`에 저장됩니다. `--profile <name>`을 사용하면 별도의 서비스 주소, token, 기본 워크스페이스, 데몬 상태를 격리할 수 있습니다.

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

이름 있는 profile은 `~/.multica/profiles/<name>/config.json`에 저장됩니다. 현재 값을 확인합니다.

```bash
multica config show
multica config show --profile staging
```

<Callout type="warning">
CLI 설정 파일에는 사용자를 대신해 Multica에 접근할 수 있는 token이 들어 있습니다. 저장소에 commit하거나 로그에 올리거나 다른 사람과 공유하지 마세요.
</Callout>

### 결정 제안

작업 토큰은 사람이 패스키로 승인하는 관리 대상 작업을 제안할 수 있습니다. 제안 자체는 아무것도 변경하지 않습니다.

```bash
multica decision propose issue.run_budget.raise --version 1 --issue MUL-123 \
  --for <user-id> --param window_id=<id> --param new_cap:=40 [--reason "..."]
multica decision propose <action-type> --version 1 --issue MUL-123 --params-file ./params.json
```

`--version`과 `--issue`는 필수입니다. `--param k=v`는 문자열, `--param k:=<json>`은 원시 JSON을 보냅니다. `--params-file`은 JSON 객체 하나를 받으며 `--param`과 함께 쓸 수 없습니다. 명령은 승인 카드 링크를 출력합니다. 실행 예산 액션의 링크는 이슈에서 승인을 열고, 다른 액션의 링크는 채팅의 카드로 연결되어 그곳에서 승인합니다. 일반 선택지 카드(`--action-file` 없는 `multica decision request`)는 변경을 적용할 수 없습니다. 승인해도 답변만 기록됩니다. 서버는 의도를 읽을 수 없어 그런 카드를 거부하지 않고, 결정이나 선택지가 워크플로·에이전트·스쿼드·워크스페이스·예산 변경처럼 보일 때(또는 허용 목록의 액션 유형을 담을 때) 참고용 힌트를 붙입니다. 그 변경은 `multica decision propose`로 보내세요. 거부되면 서버의 상태와 오류 코드를 보여 줍니다. `multica issue budget raise`와 `multica issue budget top-up`은 작업 토큰에서 같은 경로를 사용하며(`--for <user-id>` 추가), 개인 액세스 토큰에서는 기존처럼 지출 요청을 엽니다. 두 명령 모두 하나 이상의 issue ID를 받습니다: `multica issue budget top-up CHE-1 CHE-2 CHE-3 --for <user-id> --goal "<목표>"`. ID가 하나면 기존 단일 제안 그대로입니다. 작업 토큰에서 여러 ID를 주면 배치 경로를 한 번만 호출하고 카드 링크를 하나 출력합니다. `--goal`은 배치 이름이며(기본값: 작업과 issue 수) `--output json`은 배치 id와 issue별 제안 id를 반환합니다. 개인 액세스 토큰에서는 ID마다 별도 요청을 엽니다. 배치 경로는 채팅 작업이 필요하고 issue는 최대 25개입니다. 서버는 raise 배치를 패스키 하나로 승인하지만 top-up 배치는 승인 시 거부하므로 top-up은 하나씩 승인하세요.

실행 예산 다음 단계: issue의 80 % 알림에는 수치와 바로 실행할 수 있는 명령이 함께 나옵니다. 예: `Run budget: 20 of 25 runs used on CHE-1234 (workflow Default, cap 25). Ask for more: multica issue budget raise CHE-1234 --runs 40`. 예산이 거부한 실행은 오류 코드 `run_budget_exhausted`와 `runs_used`, `runs_limit`, `workflow_id`, `window_id`, `open_card`, `next_command`를 반환합니다. `multica issue budget get <issue> --output json`도 `open_card`와 `next_command`를 반환합니다. issue의 현재 윈도우에 상향 또는 추가 윈도우 카드가 열려 있는 동안 `next_command`는 그 카드를 기다리라고 알려 주고, `multica issue budget raise`를 다시 실행해도 새 카드를 열지 않고 같은 카드를 반환합니다. 작업 토큰에서는 issue 작업의 `--for` 기본값이 워크스페이스 소유자이며, 도움말에는 `raise`만 표시됩니다. `top-up`은 멤버가 계속 사용할 수 있습니다. 서버, 멤버, 에이전트가 카드를 열 때마다 행위자 유형, 행위자, 액션 유형을 기록하는 `run_budget_ask` 활동 행이 하나 추가됩니다.

적용된 작업은 되돌릴 수 있는 동안 요청 대상자가 되돌릴 수 있습니다. `multica decision revoke <request-id> --why "<사유>"`를 실행하세요. 작업이 되돌릴 수 있는 경우는 적용되었고, 해당 유형에 정확한 역작업이 있으며, 아직 되돌려지지 않았을 때뿐입니다. 이번 릴리스에서 역작업이 있는 유형은 `agent.pause`(역작업은 `agent.resume`)뿐이며, 승인으로 에이전트가 일시 중지되었고 그 뒤 아무도 일시 중지 상태를 바꾸지 않은 경우에만 해당합니다. 다른 모든 작업 유형은 되돌릴 수 없습니다. 요청 대상자만 되돌릴 수 있고 승인과 같은 역할 규칙이 적용됩니다. passkey가 필요한 작업은 앱에서 되돌립니다. 서버는 누가, 언제, 왜 되돌렸는지 기록하고 역작업을 실행한 뒤 요청한 에이전트를 결과 `revoked`로 깨웁니다. 거절됨, 만료됨, 적용되지 않음, 논의만 있음, 이미 되돌려진 결정은 거부됩니다. `multica decision get <request-id>`는 `revocable`을 보여 주고, 되돌린 뒤에는 `revoke` 기록(`at`, `by`, `reason`)도 보여 줍니다.

`issue.project.set`은 이슈를 다른 프로젝트로 옮깁니다: `multica decision propose issue.project.set --version 1 --issue MUL-123 --param project_id=<project-id>`. 카드에는 이동 전후의 프로젝트, 워크플로, 실행 한도, 사용한 실행 횟수가 표시되고 이동이 실행 예산을 넓히는지도 알려 줍니다. 예산을 넓히는 이동은 `spend` 카드이고, 그 밖의 이동은 `reversible`입니다. 워크스페이스 소유자만 승인할 수 있습니다. 요청 뒤에 이슈가 원래 프로젝트를 떠났거나 대상 워크플로의 예산이 늘었으면 카드는 거부됩니다.

Run 예산 자동 승인: issue가 run 예산을 다 쓰면, 직전 창에 진전이 있고 이상이 없으며 워크스페이스 일일 한도에 여유가 있을 때 서버가 다음 창을 직접 승인합니다. issue의 감사 댓글에 규칙 이름(`auto-approver v1`)과 끄는 방법이 적힙니다. 승인된 창은 서버가 거부했던 run도 다시 시작하므로 issue가 `blocked`에 머물지 않습니다. 진전은 run이 issue 상태를 바꿨거나, 연결된 PR의 head나 상태를 바꿨거나(PR 댓글은 해당하지 않음), 또는 커밋한 경우입니다. 댓글은 내용과 상관없이 진전이 아니며, 이 중 하나도 없는 run은 헛도는 run입니다. 루프(같은 실패 검사, 실패한 CI 워크플로 또는 run 오류가 3개 이상의 run에서 반복됨, 댓글은 읽지 않음), 헛도는 창(run의 80% 이상이 아무것도 전달하지 못함), 토큰 급증(run당 토큰이 워크스페이스 중앙값의 3배 초과), 반복 증액(한 issue에서 24시간 안에 3회 이상), OpenAI 제한 중인 OpenAI 풀 에이전트는 자동 승인하지 않습니다. 소유자는 하루 최대 한 장의 묶음 카드를 받습니다. 같은 날의 이후 이상은 그 카드의 채팅에 메시지로 도착하고, 브리프에 보류된 issue가 나열됩니다. 그 밖의 경우(이미 `blocked`인 issue, 거부된 run이 issue의 에이전트 담당자 대상이 아닌 경우 포함)는 issue별 카드로 돌아갑니다. 워크스페이스 설정 `run_budget_auto`: `enabled`(기본 `false`: 자동 승인은 꺼진 상태로 출시됩니다)와 `daily_envelope`(ICT 하루당 추가 run 수, 기본 `300`)와 `expected_checks`(푸시한 head가 CI를 확정된 것으로 인정받기 위해 완료된 상태로 갖춰야 하는 체크 이름. 기본값은 비어 있으며, head를 푸시한 모든 윈도우를 보류합니다). 기대하는 체크 중 일부만 완료된 스냅샷은 확정된 것으로 보지 않습니다. 이름은 완료된 Checks API run이 정확히 하나일 때만 인정됩니다. 같은 이름의 커밋 상태나 같은 이름의 두 번째 run이 있으면 해당 윈도우는 보류됩니다. `multica config propose workspace.settings --set 'run_budget_auto:={"enabled":true}'` 또는 `workspace.settings` 설정 제안으로 켤 수 있습니다(`"enabled":false`로 다시 끕니다).

### 대상 필드는 패스키 작업이 필요합니다

작업 토큰과 클라우드 노드 토큰은 기존 경로로 다음 필드에 쓸 수 없습니다: `agent.instructions`, `squad.instructions`, `workspace.context`, 워크플로 단계와 단계 지침, 결정 작업 허용 표에 있는 워크스페이스 설정 키(`compact_prompt`, `auto_compact`, `idle_started_guard`, `wakeups_paused`, `mermaid_orientation` 등 단순 운영 키). 서버는 403과 `code: passkey_action_required`를 반환하고, 대신 제안할 작업을 `action_type`으로 알려 줍니다(`agent.instructions.set`, `squad.instructions.set`, `workspace.context.set`, `workflow.steps.set`, `workspace.settings.patch`). 저장된 값은 바뀌지 않습니다. 투표 영수증, 결정 바인딩, PASS 영수증, Hermes 예외로는 이 거부가 풀리지 않습니다. `multica decision propose <action-type>`으로 작업을 제안하면 사람이 패스키로 승인합니다. 사람의 쓰기와 `project.description`은 이전과 같습니다.

## 다른 코딩 에이전트에서 Multica 조작하기

작업 대부분이 Codex, Claude Code, Cursor 안에서 이루어진다면 터미널로 전환하지 않고 그곳에서 바로 Multica를 조작할 수 있습니다. [Multica CLI skill](https://github.com/multica-ai/multica-cli)은 이 페이지의 명령을 안전하게 다루는 방법을 해당 에이전트에게 가르칩니다. 토큰을 낭비하지 않고 태스크와 댓글 스레드를 읽고, 댓글은 파일을 통해 작성하며, 멘션·상태 변경·할당이 유발하는 부수 효과를 올바르게 처리합니다.

인증된 CLI를 통해서만 동작하며 그 자체로는 어떤 접근 권한도 부여하지 않습니다. 권한은 여전히 로그인, 선택한 profile, workspace에서 나옵니다. CLI v0.4.26 이상이 필요합니다. Claude Code 플러그인 마켓플레이스, Codex skill 설치 도구, Cursor를 비롯해 Markdown 지침을 읽어들이는 다른 도구의 설치 방법은 저장소 README를 참고하세요.
